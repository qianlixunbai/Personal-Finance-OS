## 2. 已核实的公开能力

前端 Axios `baseURL` 为 `/api/v1`。未来 wrapper 必须使用下列相对路径，不更名、不合并：

| 命令 | 后端公开 endpoint | 前端 wrapper path |
| --- | --- | --- |
| First BUY | `POST /api/v1/investment/positions` | `/investment/positions` |
| Subsequent BUY | `POST /api/v1/investment/positions/{assetId}/buy` | `/investment/positions/{assetId}/buy` |
| SELL | `POST /api/v1/investment/positions/{assetId}/sell` | `/investment/positions/{assetId}/sell` |
| DIVIDEND | `POST /api/v1/investment/positions/{assetId}/dividends` | `/investment/positions/{assetId}/dividends` |
| Standalone reversal | `POST /api/v1/investment/transactions/{transactionId}/reversal` | `/investment/transactions/{transactionId}/reversal` |
| Same-type replacement | `POST /api/v1/investment/transactions/{transactionId}/replacement` | `/investment/transactions/{transactionId}/replacement` |

所有六类命令都要求 Bearer JWT 和 `Idempotency-Key`。Key 规则为：在各自后端幂等存储域内按用户唯一、1–100 字符、非空、不得有首尾空格。First BUY / BUY / SELL / DIVIDEND / standalone reversal 使用 `investment_transactions` 的 `(user_id, idempotency_key)` 域；replacement 使用 `investment_transaction_corrections` 的独立 `(user_id, idempotency_key)` 域。服务端不保证 replacement 与其他命令之间存在一张用户级全局 key namespace；前端仍对每个 intent 生成全新 UUID，并用全局 pending 锁避免跨命令复用。服务端在命令所属存储域内将 key 与 canonical request hash 配对：

```text
same key + same request
→ 返回已保存的 immutable receipt
→ idempotentReplay=true

same key + different request
→ 409
→ 不执行第二次 effect
```

First BUY、BUY、SELL 当前使用 `BigDecimal(String)` 解析；DIVIDEND 与 replacement 明确拒绝 JSON number、科学计数法和未知字段。前端统一采用更严格的 plain fixed-point decimal string，不利用旧解析差异。

## 3. 产品与真值原则

1. `/investments` 是个人财务账本的手工事实录入与审计工作区，不是券商交易终端。文案使用“记录买入 / 记录卖出 / 记录分红”，不使用“下单”。
2. Java 后端是金融计算、事务、权限和当前 Position 的唯一权威。前端不计算或提交 gross/net/cash delta、released cost、realized PnL、average cost、total cost、balanceAfter 或最终 Position。
3. Write response 是命令提交时的 immutable receipt；read API 返回请求时的 current truth。成功后必须重新读取 read model，不以本地数组或 `finalPosition` 建立第二套真值。
4. Reversal 是追加式纠正，不是删除。Replacement 是 grouped reversal + same-type replacement fact + immutable correction envelope，不是编辑 original。
5. 所有金融写请求禁止自动重试。Axios interceptor、generic retry library 和组件 effect 均不得自动重新 POST。
6. 前端校验只改善体验，不能替代服务端所有权、状态、并发、replay 或数据库约束。
7. 当前没有 insufficient cash 规则；BUY 可以使账户余额为负，UI 不得增加“资金不足”阻断。
8. 记录时间由服务端在提交时生成；表单不提供交易日期、结算日期或历史回填时间。

## 4. 命令状态机

核心状态机冻结为：

```text
DRAFT
  └─ 用户进入复核 → CONFIRMING
       ├─ 返回编辑 → DRAFT
       └─ 首次真正提交：取得跨 tab exclusive lock、复查 pending、生成一个 key、冻结并持久化请求 → SUBMITTING
            ├─ 200 → SUCCEEDED_AWAITING_REFRESH → GET refresh 成功 → 清理 marker
            ├─ 明确未提交的 400/403/404 → REJECTED → 清理 pending → 返回 DRAFT/列表
            ├─ 首次提交 409 → REJECTED_AWAITING_RECONCILE → GET reconcile 成功 → 清理 marker
            ├─ 401 → AUTH_REQUIRED(resumeState=SUBMITTING) → 重新登录 → 用户确认后使用原 key/原请求继续首次 POST
            └─ 已发出请求后的 5xx/timeout/network reset → OUTCOME_UNKNOWN
                                                        └─ 用户选择“恢复原提交” → RECOVERING
                                                             ├─ 200 replay/new execute → SUCCEEDED_AWAITING_REFRESH
                                                             ├─ 401 → AUTH_REQUIRED(resumeState=OUTCOME_UNKNOWN)
                                                             └─ 4xx/5xx/transport unresolved → OUTCOME_UNKNOWN
```

状态不变量：

| 状态 | payload 可编辑 | 可生成新 key | 必须保留旧 key / endpoint / body | 可发 POST |
| --- | --- | --- | --- | --- |
| `DRAFT` | 是 | 否 | 否 | 否 |
| `CONFIRMING` | 返回 DRAFT 后可编辑 | 否 | 否 | 否 |
| `SUBMITTING` | 否 | 否 | 是 | 仅首次请求 |
| `OUTCOME_UNKNOWN` | 否 | 否 | 是 | 仅用户触发同请求恢复 |
| `RECOVERING` | 否 | 否 | 是 | 仅一次 in-flight 恢复 |
| `AUTH_REQUIRED` | 否 | 否 | 是，并持久化唯一合法的 `resumeState` | 同 user 重新认证后仍保持本状态；用户动作在 Web Lock 内、紧邻实际请求才原子切换，POST 仍须显式触发，GET 来源只恢复 GET |
| `REJECTED` | 原 intent 已结束；重新编辑形成新 intent | 下一次确认时才可 | 仅首次 400/403/404，可立即清理 | 否 |
| `REJECTED_AWAITING_RECONCILE` | 否 | 否 | 是，直到 GET reconcile 成功 | 仅 GET |
| `SUCCEEDED_AWAITING_REFRESH` | 否 | 否 | 是，直到必要 GET refresh 成功 | 仅 GET |
| `RECOVERY_RECORD_INVALID` | 否 | 否 | 是；不得自动修改或删除 | 否，fail-closed |

只有在用户完成确认、准备首次真正 POST，且已取得跨 tab exclusive lock 并再次确认当前用户没有 pending record 时，才调用 `crypto.randomUUID()`。页面 render、字段输入、打开 modal、恢复请求和 retry 都不得生成 key。

## 5. Pending command 存储契约

### 5.1 选择

采用 `localStorage`，不采用 memory-only 或仅 `sessionStorage`：刷新、导航、tab 崩溃和浏览器重启后仍需恢复 unknown outcome；`sessionStorage` 的 tab 隔离和关闭即丢失会增加重复金融事实风险。代价是请求内容在本机持久化，因此只保存恢复所需最小数据，不保存 JWT、响应、账户余额、计算结果或完整显示快照。

### 5.2 Key 与 record

```text
storage key:
finance-os:investment-command:pending:v1:{userId}:{idempotencyKey}
```

```ts
interface PendingInvestmentCommandV1 {
  schemaVersion: 1
  userId: number
  state:
    | 'SUBMITTING'
    | 'OUTCOME_UNKNOWN'
    | 'RECOVERING'
    | 'AUTH_REQUIRED'
    | 'SUCCEEDED_AWAITING_REFRESH'
    | 'REJECTED_AWAITING_RECONCILE'
  resumeState?:                    // 仅 AUTH_REQUIRED 必填；其他状态禁止
    | 'SUBMITTING'                 // 首次 POST 收到 401，已知未提交
    | 'OUTCOME_UNKNOWN'            // recovery POST 收到 401，早先 outcome 仍 unknown
    | 'SUCCEEDED_AWAITING_REFRESH' // success marker 后的 GET 收到 401
    | 'REJECTED_AWAITING_RECONCILE'// 首次 409 marker 后的 GET 收到 401
  commandType: 'FIRST_BUY' | 'BUY' | 'SELL' | 'DIVIDEND' | 'REVERSAL' | 'REPLACEMENT'
  method: 'POST'
  path: string                 // /investment/... relative to /api/v1
  idempotencyKey: string
  bodyJson: string             // 首次发送时的 exact serialized body
  target: {
    assetId?: number
    logicalTransactionId?: number
    accountId?: number
    instrumentId?: number
  }
  refresh?: {                  // 200 后写入；success-refresh AUTH_REQUIRED 必须原样保留
    assetId: number
    logicalTransactionId: number
  }
  submittedAt: string          // 客户端恢复元数据，不进入 request body
  updatedAt: string
}
```

`target` 不是可随意省略的提示字段，而是按 commandType 校验的恢复输入：FIRST_BUY 必须保存 `accountId + instrumentId`；BUY / SELL / DIVIDEND 必须保存 `assetId`；REVERSAL / REPLACEMENT 必须保存从 logical transaction detail/list context 取得的 `logicalTransactionId + assetId`。首次 POST 前不得存在 `refresh`；200 receipt 到达后，FIRST_BUY / BUY / SELL / DIVIDEND 用 response 的 `assetId + transactionId`，REVERSAL / REPLACEMENT 用 response 的 `assetId + originalTransactionId` 形成 `refresh`。

写入顺序固定为：构造并序列化 body → 生成 key → 同步写入 localStorage → 成功后才调用 Axios POST。若存储写入失败，不发送请求。恢复必须直接复用 `bodyJson`，不得从可变表单重新序列化。业务 method/path、`Content-Type: application/json`、`Idempotency-Key` 与 body 必须不变；`Authorization` 不属于冻结的命令内容，必须在每次发送时由 Axios 注入当前已认证会话的 Bearer token，不保存或复用旧 JWT。`submittedAt` 只是本地元数据，不进入请求。

载入或恢复前必须运行 runtime validation，而不只依赖 TypeScript：JSON 必须可解析；`schemaVersion`、userId、state、method 和 commandType 必须在 allowlist；storage key 后缀必须与 record key 一致；key 必须满足 1–100/trim 规则；path 必须与 commandType、必填 target 和允许的六个 endpoint pattern 匹配；`bodyJson` 必须是对象并符合对应字段 allowlist/type；success state 还必须具有合法 `refresh`。`AUTH_REQUIRED` 必须具有且只能具有上述四个 `resumeState` 之一；其他 state 禁止 `resumeState`；`resumeState = SUCCEEDED_AWAITING_REFRESH` 必须同时具有合法 `refresh`。校验只用于 fail-closed，不重新序列化 body。任何损坏、未知版本、user mismatch、path/body/key/resumeState mismatch 都不得 POST、不得自动删除。Coordinator 派生只读的内存状态 `RECOVERY_RECORD_INVALID`，保留原 localStorage key 与 raw value bytes 不覆盖，reload 时重新校验；该 marker 只存在于内存或独立 sidecar，不得写回并替换损坏原文。

`RECOVERY_RECORD_INVALID` 不提供 UI 删除或解锁流程。用户可以把原 storage key、raw value 和导出时间下载为本地 recovery evidence，并以当前登录用户只读刷新 Portfolio、Position list、transaction list；若原文仍可安全解析出 allowlist target，可同时读取对应 Position detail、logical transaction detail 与 audit，但这些 GET 和人工确认都不能证明 ambiguous POST 没有提交。只有两类外部结果可解除：从原始证据恢复出通过 runtime validation 的 exact key/path/body 后回到 same-key recovery，或未来由权威 server/operator 机制按 idempotency record 明确裁决并留下可审计结果。当前公开 API 没有按 key 查询/裁决能力，因此无法满足时必须永久 fail-closed 并转人工支持；不得因导出、只读核对、确认短语或浏览器存储清理而删除原 record、生成新 key或恢复写入口。

### 5.3 生命周期、隐私与清理

- unresolved record 不自动过期；服务端幂等记录没有公开 TTL，静默删除客户端恢复材料会重新引入重复事实风险。
- 任意 200 到达后，先以一次同步 `localStorage.setItem` 把 `state = SUCCEEDED_AWAITING_REFRESH` 与 response-derived `refresh` IDs 原子写入，再展示 receipt 并启动 read refresh。刷新全部成功后删除 record；刷新失败时保留 marker、显示“写入已成功，当前数据尚未刷新”与“重新刷新”动作，不得再次 POST，且在刷新成功前保持投资写入全局禁用。刷新 GET 收到 401 时原子改为 `AUTH_REQUIRED + resumeState=SUCCEEDED_AWAITING_REFRESH` 并保留 `refresh`；同 user 重登后仍保持该组合，用户触发刷新时才按第 154 行规则紧邻 GET 转换，只能继续 GET。若页面在 200 到达后、success marker 落盘前崩溃，旧 `SUBMITTING/RECOVERING` record 在 reload 后按 unknown 处理并用 same-key recovery 取回 receipt；marker 已落盘后则只能发 GET。
- 首次提交收到 400/403/404 时，当前 attempt 明确未提交：删除 record；400 返回可编辑 DRAFT，403 显示无权执行且不泄露细节，404 返回可用列表。只有首次提交 409 写入 `REJECTED_AWAITING_RECONCILE`；成功核对当前 read model 后删除，失败时保留 marker 并继续全局禁用。reconcile GET 收到 401 时原子改为 `AUTH_REQUIRED + resumeState=REJECTED_AWAITING_RECONCILE`；同 user 重登后仍保持该组合，用户触发核对时才紧邻 GET 转换，绝不重发已明确回滚的旧 POST。
- 已进入 `OUTCOME_UNKNOWN` 后的恢复 attempt 若返回 400/403/404/409，不能据此反推更早 attempt 未提交；保留原 record，回到 `OUTCOME_UNKNOWN` 并显示“恢复被拒绝，原提交结果仍未确认”。允许刷新 read model 辅助核对，但不得清理、生成新 key 或解除全局禁用。
- 初次设计审查发现 First BUY 在可变 ACTIVE precondition 之后才查询 same-key receipt，形成实施前 P1 blocker。该 finding 已由后端提交 `4c0831aa63f48e398c7c74f0476f21917f370e75` 关闭：当前顺序先按 `userId + Idempotency-Key` 查询持久化 receipt；命中时先校验 canonical request hash，再返回 immutable receipt；未命中才按 Account → Instrument 加锁并执行 fresh receipt lookup，仍未命中时才校验当前 ACTIVE 等新命令前置条件。PostgreSQL 回归证据覆盖 committed 后 Account inactive、Instrument inactive、两者同时 inactive仍以 `200 + idempotentReplay=true` 恢复；same key + different hash 在 ACTIVE 状态变化前返回 `409` 且无第二次 effect；actually-uncommitted attempt 无 receipt，retry 仍按 genuinely new command 遵守当前 ACTIVE 条件。已提交 same-key recovery 与 genuinely new First BUY 的状态语义因此同时成立。
- 401、token 自动清理和跳转登录不得删除 record。进入 `AUTH_REQUIRED` 时必须在同一次 `setItem` 中写入来源：首次 POST 的 401 保存 `SUBMITTING`；recovery POST 的 401 保存 `OUTCOME_UNKNOWN`；success refresh GET 与 409 reconcile GET 分别保存对应 GET-only state。登录成功后若 userId 相同，返回 `/investments`，但 record 继续保持 `AUTH_REQUIRED + resumeState`，不得仅因登录成功提前恢复或移除来源；reload、新 tab 与 storage event 也保持该组合。用户选择对应动作时必须先取得同一 Web Lock、重读并验证 record，然后在紧邻实际请求前原子转换：`SUBMITTING` 来源 → `SUBMITTING` 后发送原首次 POST，`OUTCOME_UNKNOWN` 来源 → `RECOVERING` 后发送 same-key recovery，两个 GET-only 来源 → 各自原 state 后只发对应 GET。转换后的 POST 在崩溃/reload 时才按 unknown 处理；若转换落盘失败则 zero request。不同用户只能看到自己的 namespace。
- 主动 logout 若存在 unresolved record，显示明确提示；继续退出会保留 record，且不保留 JWT。正常 UI 不提供删除 unresolved record 的动作；用户必须先通过 same-key recovery 获得成功或明确拒绝结果。
- 不复制保存 JWT；允许保存非敏感的 userId 以完成 namespace 匹配。

页面载入时，当前用户 namespace 中任何普通 `SUBMITTING` / `RECOVERING` record 一律降级显示为 `OUTCOME_UNKNOWN`，因为它们已经紧邻或开始 POST，刷新后无法知道先前网络请求结果；合法 `AUTH_REQUIRED` 始终保持原 state 与 `resumeState` 配对，不得按普通 SUBMITTING 降级，即使同 user 已重新认证但尚未执行恢复动作。`SUCCEEDED_AWAITING_REFRESH` 只执行 GET refresh，`REJECTED_AWAITING_RECONCILE` 只执行 GET reconcile，二者及其 AUTH_REQUIRED 形式绝不重新 POST。顶部 `PendingCommandRecoveryBanner` 必须持续可见。只要当前用户存在任何 unresolved/awaiting-refresh/invalid investment record，全部投资写入口全局禁用，不得在其他 Position 或 transaction 上创建新 intent；若因旧版本或异常发现多条 record，只能按 `submittedAt` 升序逐条处理，全部解决后才能重新写入。

### 5.4 多标签页

`localStorage` 使 pending record 跨 tab 可见，但 `storage` event 不是原子互斥。首次提交必须使用 Web Locks API 取得 origin-wide exclusive lock：

```text
finance-os:investment-command-submit:v1:{userId}
```

锁内固定执行：重新扫描并 runtime-validate 当前 user namespace → 若存在任何 record 则拒绝新 intent → 生成 key → 写入 `SUBMITTING` record。record 成功落盘后即可释放锁，再发送 POST；第二个 tab 随后取得锁时会同步读到 record，因此不能生成第二个 key。Web Locks 已覆盖项目面向的现代 Chrome、Edge、Firefox 与 Safari；若实际浏览器不支持或锁请求失败，investment write 仍须 fail-closed、zero POST，并明确显示“当前浏览器无法提供安全的跨标签提交保护，请使用受支持的新版浏览器”，不得退化为非原子的 localStorage check-and-set。

Recovery 同样使用该锁：锁内重读 record，将 `OUTCOME_UNKNOWN` 原子改为 `RECOVERING` 后释放并 POST；其他 tab 看到 `RECOVERING` 不得再发 recovery。tab 崩溃或 reload 后按既定规则将其降级为 `OUTCOME_UNKNOWN`。

此外监听 `storage` event：其他 tab 写入 pending 后，本 tab 展示 banner 并全局禁用投资写入口；完成/清理后同步刷新。每个 intent 仍有独立 key，服务端所有权、行锁、replay 和 409 是最终业务边界，但不能替代不同 key 的客户端互斥。

## 6. Double-click、离页与重复提交防护

1. 确认按钮 handler 首行检查现有 in-flight promise/command；已存在则返回，不生成 key；随后必须经过 Web Locks 原子 claim。
2. 生成 key 和 pending record 后立即禁用确认、取消和全部投资写入口，并显示 progress；一次 intent 最多一个 POST。
3. React Strict Mode、重复 render 和 effect 不得触发 POST；写请求只能来自显式用户 event。
4. `SUBMITTING` 时关闭 modal、路由跳转或刷新需要 `beforeunload` warning；即使用户离开，localStorage record 仍存在。
5. `OUTCOME_UNKNOWN` 可关闭 dialog，但不能关闭 banner 或解除全局写禁用；恢复按钮一次只能有一个 in-flight request。
6. 恢复动作唯一行为是使用相同 path、`bodyJson` 和 `Idempotency-Key` 重新 POST。

## 7. 错误分类与恢复

公开错误当前没有稳定的细粒度 machine-readable error code；不得依赖英文 message 字符串区分 oversell、already corrected、idempotency conflict、lock timeout 或 deadlock。

| 情况 | Commit 判断 | UI 状态与动作 |
| --- | --- | --- |
| 提交前检测到 offline，尚未调用 POST | 明确未发送 | 留在 DRAFT/CONFIRMING，不生成命令；提示联网后提交 |
| 首次提交 400 | 明确拒绝、未提交 | 删除 pending，返回 DRAFT；显示字段/输入错误，允许修正后形成新 intent |
| 首次 POST 收到 401 | 认证层拒绝；当前 attempt 未提交 | `AUTH_REQUIRED + resumeState=SUBMITTING`；保留原 record，同 user 登录后恢复首次提交语义，须用户确认才同 key/同 body POST |
| recovery POST 收到 401 | 本次 recovery 未提交；更早 attempt 仍 unknown | `AUTH_REQUIRED + resumeState=OUTCOME_UNKNOWN`；同 user 登录后回到 unknown，只允许用户触发 same-key recovery |
| success refresh GET 收到 401 | write 已成功；本次只读刷新未完成 | `AUTH_REQUIRED + resumeState=SUCCEEDED_AWAITING_REFRESH`；保留 refresh IDs，登录后只继续 GET，zero POST |
| 409 reconcile GET 收到 401 | 原 POST 已明确回滚；只读核对未完成 | `AUTH_REQUIRED + resumeState=REJECTED_AWAITING_RECONCILE`；登录后只继续 GET，zero POST |
| 首次提交 403 | 明确拒绝、未提交 | 删除 pending，进入 `REJECTED`；显示无权执行且不泄露安全细节，不自动 retry |
| 首次提交 404 | 目标不存在或不可访问，未提交 | 删除 pending，进入 `REJECTED`；返回可用列表，可 best-effort 刷新只读列表但不以刷新成败阻塞清理 |
| 首次提交 409 | 当前 attempt 明确冲突并回滚 | `REJECTED_AWAITING_RECONCILE`；统一提示“当前投资状态已变化或请求发生冲突，请刷新后检查”，不自动 retry |
| 收到 500 或其他命令 5xx | 客户端无法可靠区分事务回滚、commit 后响应失败或中间层错误 | `OUTCOME_UNKNOWN`；仅允许恢复原提交 |
| timeout / connection reset / attempted POST 后 network error | 不可判断 | `OUTCOME_UNKNOWN`；仅允许恢复原提交 |
| 首次 attempted POST 的其他未列明 status（如 408/422/429） | 公开契约没有证明一定在执行前拒绝 | 保守进入 `OUTCOME_UNKNOWN`；不得按 status 名称猜测未提交 |
| 恢复返回 200 + `idempotentReplay=true` | 原提交此前已成功 | `SUCCEEDED`；显示“已恢复此前提交结果，系统没有重复执行该操作。” |
| 恢复返回 200 + `idempotentReplay=false` | 此前未提交，本次安全执行一次 | `SUCCEEDED`；显示“原提交此前未完成，本次恢复已安全记录一次。” |
| 恢复返回 400/403/404/409 | 只知道本次 recovery 未执行；更早 attempt 仍可能已提交 | 回到 `OUTCOME_UNKNOWN`；保留原 record，全局阻止新写入，允许只读核对但不宣告失败 |

仅对**首次提交明确收到的 409**，保守流程为：不重发 → 写入 `REJECTED_AWAITING_RECONCILE` → 按第 11 节的逐命令 409 集合读取当前权威状态。所有 collection GET 必须返回 200；target GET 返回 200，或在对应 collection 已成功刷新且不再包含该 target 时返回 404，才算 reconcile 成功。401 转 `AUTH_REQUIRED + resumeState=REJECTED_AWAITING_RECONCILE` 并保留 marker，重登后只恢复 GET；403、5xx、network error 或不能与 collection 一致解释的 404 都不算成功，继续全局写禁用。成功后原 attempt 已知未提交，删除 marker，用户可基于当前真值形成新 intent、新 key。已进入 unknown recovery 后收到的 409 不适用本流程，必须继续 `OUTCOME_UNKNOWN` 和全局写禁用。未来若后端增加稳定 error code，可在新契约中细分提示，但仍不得自动 retry。

## 8. 命令资格与入口

### 8.1 入口决策

- Empty portfolio 在 `/investments` 主区显示“记录第一笔投资”。非空时工具区显示“新增持仓 / 首次买入”。
- Position list row 只提供“查看详情”，避免把写操作铺在每一行；Position detail header 的 `InvestmentCommandMenu` 统一提供“记录买入”“记录卖出”“记录分红”。不要求用户输入 assetId。
- Transaction detail 提供“冲正交易”“更正交易”；普通 transaction list 不直接放高风险 correction 按钮。
- 高风险 action 使用文字按钮，不使用仅图标按钮。

### 8.2 Instrument prerequisite 决策

当前存在 `GET/POST /api/v1/investment/instruments`，但没有 Instrument 创建前端。未来写 UI 必须把最小 Instrument 创建与选择能力纳入范围：FirstBuyForm 的 selector 展示 symbol、name、market、assetClass、quoteCurrency、status，并提供“新建投资标的”子流程。Account 使用现有账户 API 和可读名称/类型选择。普通用户不得手填 accountId、instrumentId 或调用 API 才能完成 first BUY。

Instrument 创建不是投资写命令，不使用本文 pending command 状态机；创建成功后刷新 selector 并自动选中。genuinely new First BUY 仍只有在 ACTIVE CNY Account、ACTIVE Instrument、账户类型与 assetClass 兼容时可提交；已提交的 same-key/same-request recovery 先恢复 immutable receipt，不受 Account / Instrument 后续状态变化影响。

## 10. 确认与结果 UX

### 10.1 确认层级

- First BUY / BUY：使用轻量 review step，显示 Account、Instrument、quantity、unitPrice、fee、tax；不展示计算 preview。
- DIVIDEND：使用轻量 review step，显示 gross、fee、tax、reference、note，并说明 quantity/cost/status 不由前端改变。
- SELL：强制二次确认，显示 Instrument、Account、当前 quantity、sell quantity、unit price、fee、tax；提示最终 released cost、realized PnL 和余额由后端计算。若输入等于当前读取 quantity，只提示“本次卖出可能关闭当前 Position”。

- Replacement：强制高风险确认，按字段显示“原值 → 新值”和 reason；明确 original 不修改、系统追加 correction facts、logical transaction 将展示替换后的有效值。按钮为“确认更正”，不使用“保存修改”。

## 11. Refresh policy

当前继续使用 React hooks + Axios，不引入 React Query。成功响应先把 storage state 与 response-derived `refresh` IDs 一次写为 `SUCCEEDED_AWAITING_REFRESH`，使 reload/其他 tab 不会误发 recovery且能够重建准确 GET 集合。随后 invalidate 现有 latest-request gate，保留当前 filter 值但把 Position 与 transaction cursor 都重置为 `null`，并用下列实际 GET wrapper 各请求一次：

| Read model | Wrapper / path | ID / query 规则 |
| --- | --- | --- |
| Portfolio | `fetchInvestmentPortfolio()` → `GET /investment/portfolio` | 无 |
| Position list | `fetchInvestmentPositions(query)` → `GET /investment/positions` | 保留 status/filter，cursor 重置为 null |
| Position detail | `fetchInvestmentPosition(assetId)` → `GET /investment/positions/{positionId}` | write receipt/target 的 assetId 即 positionId |
| Transaction list | `fetchInvestmentTransactions(query)` → `GET /investment/transactions` | 保留 filter，cursor 重置为 null |
| Logical transaction detail | `fetchInvestmentTransaction(originalTransactionId)` → `GET /investment/transactions/{logicalTransactionId}` | 新 command 用 transactionId；correction 用 originalTransactionId |
| Audit timeline | `fetchInvestmentAuditTimeline(originalTransactionId)` → `GET /investment/transactions/{logicalTransactionId}/audit-timeline` | correction 必须刷新 |

同一命令的必要 GET 可在 gate invalidation 后并行；所有必要请求成功才删除 marker 并解除全局写禁用。任何必要 GET 失败都保留 `SUCCEEDED_AWAITING_REFRESH`，receipt 仍明确显示写成功，banner 只提供 GET“重新刷新”，绝不重新 POST。首次提交 409 的 reconcile 除下表明示的 First BUY 精确 binding query 外，使用同一 cursor/filter 规则；成功条件遵循第 7 节，成功后删除 `REJECTED_AWAITING_RECONCILE`。

逐命令准确集合为：

| Command | 必须刷新 |
| --- | --- |
| First BUY | Portfolio、Position list、新 Position detail、transaction list |
| BUY / SELL / DIVIDEND | Portfolio、Position list、affected Position detail、transaction list |
| Reversal / Replacement | Portfolio、Position list、affected Position detail、transaction list、original logical transaction detail、audit timeline |

首次提交 409 的准确 reconcile 集合单独冻结如下；它不能假装拥有失败响应未返回的 ID：

| Command | 首次 409 必须读取 |
| --- | --- |
| First BUY | Portfolio；另发 `status=ALL + accountId=target.accountId + instrumentId=target.instrumentId + cursor=null` 的精确 Position list，以及相同 account/instrument filter、`cursor=null` 的 transaction list；唯一 binding 结果不会被当前页面 filter 或分页遗漏，且不调用未知的新 Position detail。若结果已有 Position，明确提示“该账户与标的已存在持仓”，导航到其 detail，只提供“记录买入”的 subsequent BUY，不再提供 First BUY；零结果才允许回到 First BUY draft |
| BUY / SELL / DIVIDEND | Portfolio、Position list、record `assetId` 的 affected Position detail、transaction list |
| Reversal / Replacement | Portfolio、Position list、record `assetId` 的 affected Position detail、transaction list、record `logicalTransactionId` 的 logical detail 与 audit timeline |

若当前 filter 为 OPEN，全卖后 Position 从列表消失是正常筛选结果；结果页同时说明“该持仓已关闭，记录未删除”。Replacement 后 transaction list 仍只有 original logical slot，status 为 `REPLACED`；Reversal 后 status 为 `REVERSED`，audit 增长。前端不得手工模拟这些结果。

## 12. User Journeys

1. Empty portfolio → “记录第一笔投资” → 选择/新建 Instrument 与选择 Account → 填写 First BUY → review → submit → receipt → 刷新并打开新 Position。
2. OPEN Position → “记录买入” → review → submit → 以服务端结果刷新 quantity/cost。
3. OPEN Position → partial SELL → 高风险确认 → submit → 刷新 quantity/cost/PnL。
4. OPEN Position → full SELL → 提示“可能关闭” → 成功后显示 CLOSED；OPEN filter 下列表消失但记录仍在 CLOSED/ALL。
5. CLOSED Position → “记录买入并重新打开” → ACTIVE 校验 → 成功后从后端读取 OPEN。
6. OPEN/CLOSED Position → DIVIDEND → 轻量确认 → 现金与 audit 更新；Position quantity/cost/status 保持服务端结果。
7. UNCHANGED transaction detail → reversal → 确认追加式纠正 → original 保留，logical status 变 REVERSED，audit 增长。
8. UNCHANGED transaction detail → replacement → 完整同类型字段 + reason → before/after 确认 → logical slot 变 REPLACED。
9. Attempted POST → network/500 ambiguity → persistent banner → “恢复原提交” → same key/path/body → 200 replay 或安全执行一次 → receipt/read refresh；若恢复 4xx 则保持 unknown。First BUY 已由 `4c0831aa63f48e398c7c74f0476f21917f370e75` 保证 persisted receipt recovery 先于可变 ACTIVE precondition，能够按同一状态机收敛。
10. 首次提交 409 → 不自动重发 → 按逐命令集合刷新并核对当前 Position/transaction；First BUY 若发现 binding，导航到 Position detail 并仅允许 subsequent BUY，若无 binding 才回 First BUY draft；其他命令在 reconcile 成功后按当前真值形成新 intent。unknown recovery 的 409 不得解锁。
11. 401 → pending 保留 → 登录 → 同 user 返回 `/investments` → 原请求继续恢复；不同 user 看不到其他 namespace。

## 14. Authentication、导航与可访问性

- 当前 Axios 401 interceptor 会删除 token 并跳转 `/login`；未来实现必须在该动作前按请求来源原子写入 `AUTH_REQUIRED + resumeState`、保留 pending record，并保存非敏感 return target `/investments`。若无法可靠识别请求来源或持久化失败，则保持 fail-closed、zero POST，不得猜测恢复路径。
- 登录响应包含 userId；成功登录时把它以 decimal string 写入 `localStorage` 的非敏感 session binding `finance-os:auth-user-id:v1`，覆盖任何旧值，用于 reload、浏览器重启和独立新 tab 后选择 pending namespace。它不是授权凭据，所有请求仍只以当前 JWT principal 为准；不得从 pending record 或旧 binding 推定已认证身份。各 tab 监听该 key 的 `storage` event 并重新扫描匹配 namespace。
- 401/主动 logout 删除 auth-user binding，但不得删除各 user namespace 的 pending record。下一次登录以认证响应 userId 覆写重建 binding，只扫描匹配 namespace；合法 AUTH_REQUIRED 继续持久保留 `resumeState`，直到用户动作在 Web Lock 内紧邻对应请求才转换，不跨 POST/GET 边界。binding 缺失、非 positive integer、与认证响应不一致或现存 token 缺少可信 userId binding 时，investment write fail-closed 并要求重新登录。binding 不设置独立 TTL，其生命周期只随成功登录覆盖以及 401/logout 清理。
- 不只靠颜色表达风险；warning、unknown 和 correction 同时使用文字、图标语义和 `role=alert/status`。
- Modal 打开后 focus 进入标题/首个字段，启用 focus trap；关闭后回到触发按钮。错误 summary 可聚焦，并以 label/description 关联字段。
- 375px 下 modal body 可纵向滚动，footer 固定或保持可见；取消与提交按钮具有足够间距，危险主按钮不与取消并排挤压到易误触宽度。
- 高风险 action 与 recovery 使用完整可读按钮文本和 screen-reader label，不用仅图标按钮。

## 15. 未来实现测试契约

### 15.1 状态与幂等

- one intent → one key；进入确认和编辑字段不生成 key。
- double click / Enter 重复触发 → one POST、same key、button disabled。
- 两个真实 tab 同时确认 → Web Locks 只允许一个 tab 完成 atomic claim 和 POST；另一个 tab 读到 pending 后 zero key / zero POST。Web Locks unavailable → zero POST。
- unknown → localStorage 保留 same key、same path、same exact `bodyJson`；表单不可编辑。
- recovery `idempotentReplay=true` → recovered success 文案；`false` → safe new execution 文案；两者都刷新 read model。
- recovery 400/403/404/409 → 仍为 OUTCOME_UNKNOWN、record 不清理、全部写入口继续禁用。
- unknown 后修改 payload、生成新 key或自动 retry 必须测试为禁止。
- localStorage 写失败 → zero POST。
- reload：`SUBMITTING/RECOVERING` → `OUTCOME_UNKNOWN`；banner 可恢复。
- 401：分别覆盖首次 POST → `AUTH_REQUIRED/SUBMITTING`、recovery POST → `AUTH_REQUIRED/OUTCOME_UNKNOWN`、success refresh GET → `AUTH_REQUIRED/SUCCEEDED_AWAITING_REFRESH`、409 reconcile GET → `AUTH_REQUIRED/REJECTED_AWAITING_RECONCILE`；token 与 auth-user binding 清理但 pending 不清。同 user 登录后、用户动作前的 reload/new tab/storage event 必须仍保持 AUTH_REQUIRED/source 配对、zero request；动作时在 Web Lock 内原子转换并紧邻请求，断言前两类只有用户动作可 POST、后两类永远 zero POST；不同 user 与 invalid binding 均 fail-closed。
- storage event：其他 tab 的 pending/cleanup 可见；服务端 409 后刷新。
- 200 → state 与 response-derived `assetId + logicalTransactionId` 一次写为 `SUCCEEDED_AWAITING_REFRESH`；必要 GET 全成功后清理；任一 GET 失败时 marker 保留且 reload 后只重试 GET。
- 崩溃窗口：200 后、success marker 前 reload 必须回到 unknown 并 same-key recovery；marker 落盘后 reload 必须 zero POST，并完全由持久化 refresh IDs 执行准确 GET。
- 首次 400/403/404 进入 `REJECTED` 并清理；只有首次 409 → `REJECTED_AWAITING_RECONCILE`。分别断言 First BUY 的 `status=ALL + accountId + instrumentId + cursor=null` 精确 binding query、已有 binding 时导航 detail 且只提供 subsequent BUY、零 binding 才返回 First BUY draft，以及 Position command/correction 的准确 reconcile GET 集合、200/一致 404 成功条件和 401/403/5xx 时 marker 保留。
- storage runtime validation 覆盖 malformed JSON、未知 schema/state、user/key/path/body mismatch、AUTH_REQUIRED 缺失/非法 `resumeState`、非 AUTH_REQUIRED 携带 `resumeState`、GET-only resume 缺失 refresh IDs 与非 allowlist path，全部 zero POST / fail-closed。
- invalid record 测试必须断言 raw key/value 不被 marker 覆写；导出 evidence、read-model 核对、确认短语或普通 storage cleanup 都不能删除/解锁。只有恢复出 valid exact request 后的 same-key recovery，或模拟权威 server/operator 裁决，才可解除；否则持续 fail-closed。
- storage assertion 明确验证不包含 JWT、Authorization、receipt、balance、final Position、requestHash 或内部 response；只保存 schema 中列出的恢复字段。

### 15.2 金融字符串

测试至少覆盖 `0`、`0.00`、`-0.01`、`1.00000000`、`12345678901234567890.12` 的原样保存/传输，不经过 floating point；拒绝 `1e3`、`1E-2`、`NaN`、`Infinity`、JSON number 和超 scale。字段正负规则单独验证，不能把“语法可表示”误当“业务可提交”。

### 15.3 Eligibility 与确认

自动化覆盖 No Position、OPEN、CLOSED、OPENING、UNCHANGED BUY/SELL/DIVIDEND、REVERSED、REPLACED，以及 ACTIVE/INACTIVE Account/Instrument；验证 BUY、SELL、DIVIDEND、REVERSE、REPLACE 的显示、启用、endpoint、确认内容和 reason 规则。

还必须覆盖 empty portfolio 的“记录第一笔投资”、最小 Instrument 创建/刷新/选择、Position list 只读入口、Position detail command menu、CLOSED SELL disabled reason、各确认 modal 的 focus trap/return focus、screen-reader label，以及 375px 下可滚动内容和不误触 footer。

### 15.4 Refresh assertions

每个命令测试准确 GET 集合与 call count：成功 First BUY 为 portfolio + position list + response `assetId` 的 new position detail + transaction list 各一次；BUY/SELL/DIVIDEND 为 portfolio + position list + affected detail + transaction list 各一次；reversal/replacement 额外要求 original transaction detail + audit timeline 各一次。两个列表必须保留 filter、cursor 重置 null；迟到的旧 GET 不得覆盖新结果；refresh failure 不得触发任何 POST。首次 409 则严格使用第 11 节的 reconcile 表，特别断言 First BUY 不调用未知 detail ID。
