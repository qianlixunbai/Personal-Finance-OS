## 2. Scope

首版 Confirm 只执行 Phase 3A 和 Phase 3C 已冻结的普通流水 plan：

- `INCOME`；
- `EXPENSE`；
- `ADJUSTMENT`；
- 服务端保存的 CSV / XLSX canonical plan；
- 整批原子写入；
- `Transaction` 与 `Account.balance` 同事务；
- Session / Batch / Item 审计；
- 用户域幂等、权威 receipt、unknown-commit 恢复；
- Confirm、Cancel、cleanup 与普通 Transaction 并发的确定性结果。

Confirm 不接受客户端重新提交 canonical rows，不允许按行跳过，也不创建 Account 或 Category。

## 3. Non-goals

本阶段不包含：

- Import Frontend；
- `TRANSFER`、`REFUND`；
- `InvestmentTransaction`、`BUY`、`SELL`、`DIVIDEND`、opening、reversal、replacement；
- partial success、Batch Undo 或后台分段 Confirm；
- 多币种、汇率换算、AI 分类、银行/券商 API；
- Redis、MQ、Kafka、Saga、微服务或分布式事务；
- 长期保存原始 CSV/XLSX 或完整 canonical staging table；
- Architecture 修改、ADR、V16 SQL 或任何业务代码实现。

## 4. Existing Baseline

### 4.1 Phase 3A 冻结事实

Phase 3A 已冻结：

- Import 是现有普通流水的批量创建入口，不是第二套账务系统；
- 支持 `INCOME`、`EXPENSE`、`ADJUSTMENT`，明确排除 `TRANSFER` / `REFUND` 与投资流水；
- Preview 只读，Confirm 执行服务端 plan；
- warning 必须显式确认，probable duplicate 不是绝对重复；
- Confirm 是 `All-or-Nothing`；
- Session 预分配 Batch ID，Batch 持久化用户域幂等 identity；
- 成功重试返回权威 receipt，same key / different intent 冲突；
- Account 按 ID 升序锁定，Transaction 与 balance 同事务；
- Session TTL 为 15 分钟，Confirm 事务上限为 60 秒；
- 最大 plan 为 10,000 个数据行。

本设计不推翻上述决定。

### 4.2 V14 / V15 与 Foundation

当前数据库已提供：

- `transaction_import_sessions`：用户域 Session、预分配 Batch ID、状态、revision、四类 digest、raw/plan reference、TTL 与终态时间；
- `transaction_import_batches`：用户域 idempotency key、request hash、exact-batch digest 唯一约束和 `CONFIRMED` 基础审计；
- `transaction_import_items`：source row、canonical fingerprint、warning codes 与 created Transaction FK；
- `FOR UPDATE` Session guard；
- `(user_id, idempotency_key)`、exact batch digest 和跨用户 FK 约束；
- V15 允许 cleanup 清空 Session raw reference。

当前 Batch 只足以返回基础 status，尚不足以长期重建完整权威 receipt。

### 4.3 Phase 3C 实现事实

当前 Preview 流程为：

```text
upload → private raw storage → parse → mapping → canonical rows
→ validation → probable duplicate → private PreviewPlan JSON
→ mappingDigest / normalizedRowsDigest → PREVIEW_READY
```

重要事实：

- plan 保存在服务端私有、最大 64 MiB 的 plan storage；客户端分页不是真值；
- plan 包含 mapping、rows、errors、warnings 与 summary；
- `normalizedRowsDigest` 按 row number、normalized values 和 warning IDs 计算；
- Account 在 Preview 时按 owner、`ACTIVE`、`CNY` 校验；
- Category 按 owner 或 `user_id IS NULL AND is_system = true` 校验；
- database probable duplicate 当前只保存布尔 warning，没有候选 Transaction ID；
- Preview response 当前尚未生成 Phase 3A 要求的签名 `previewToken`；
- cleanup 每分钟处理 expired/cancelled payload；当前不会重试清理 `CONSUMED` Session；
- Confirm 不依赖原始 CSV/XLSX，只需要服务端 frozen plan。

### 4.4 普通 Transaction 写路径

当前正式写路径已经提供必须复用的不变量：

- `TransactionService` 支持 `INCOME`、`EXPENSE`、`ADJUSTMENT`；
- Account 必须属于当前用户、为 `ACTIVE` 且币种为 `CNY`；
- Category 必须属于当前用户或是严格系统分类，并满足 type 兼容性；
- `INCOME` / `EXPENSE` 保存正 amount；`ADJUSTMENT` 保存非零有符号 amount；
- balance effect 为 `INCOME +amount`、`EXPENSE -amount`、`ADJUSTMENT amount`；
- `AccountBalanceService` 要求现有事务，按去重后的 account ID 升序 `FOR UPDATE`；
- `applyDeltas` 在锁定 Account 上聚合 `BigDecimal` delta；
- Account metadata update/deactivate 与普通 Transaction 共用 Account row lock；
- PostgreSQL `55P03` / `40P01` 映射为 `409`，数据库不可用映射为 `503`；
- 普通 Transaction 的 create/update/delete 已有真实 PostgreSQL 并发与 rollback 回归。

Confirm 不逐行调用公开 `TransactionService.create`，因为那会重复锁定 Account 并产生 N+1。实现阶段应提取一个由普通写路径与 Import 共用的内部 Transaction validation/effect primitive；`AccountBalanceService` 仍是 balance 的唯一生产写入者。

### 4.5 既有 unknown-commit 经验

Investment write / correction 已验证以下模式：

- 在金融事务内持久化 idempotency key、request hash 与 immutable receipt facts；
- 提交后响应丢失时，相同 key / hash 从持久化结果恢复；
- 提交前 rollback 时，不留下 key binding，重试安全执行一次；
- 只识别明确命名的 idempotency unique constraint；未知 unique violation 不伪装成 replay；
- replay 返回原命令时的 receipt，不从后来变化的 Account / Position 重算历史结果。

Confirm 沿用该恢复原则。

## 5. 方案比较

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 有界 plan 预读 + 单一 PostgreSQL 金融事务 | 采用 | 不在锁内做文件 IO；仍能在 Session guard、Account locks 和 digest 再验证下原子写入 |
| 在事务内重新解析 CSV/XLSX 或读取大型 raw payload | 拒绝 | 延长锁持有时间，并可能出现 Preview A / Confirm B |
| 逐行调用 `TransactionService.create` | 拒绝 | 重复 Account lock、N+1 查询，难以一次构造 Batch receipt |
| 每行独立事务 / partial success | 拒绝 | 破坏整批原子性、余额一致性与可恢复性 |
| 异步 job、queue、Saga | 拒绝 | 超出冻结架构和首版范围，无必要复杂度 |

## 6. Contract Clarifications 与实现前置

以下是对 Phase 3A 的实现级明确化，不改变其 Scope 或金融语义：

1. Confirm 先在 DB transaction 外读取有界 server plan 到内存；金融事务内再次比对 Session revision 与全部 digest。该顺序避免在锁内做文件 IO。
2. `previewToken` 使用独立的 Transaction Import HMAC secret，绑定 user、Session、Batch、revision、四类 digest、warning-set digest、contract version 与 `expiresAt`。
3. token 的签名与 binding 始终先验证；是否过期只在 committed receipt lookup 之后决定，使提交成功但响应丢失的重试可在 Session TTL 后恢复。
4. Phase 3C 的 database probable duplicate evidence 必须从布尔值升级为稳定候选 identity，至少包含 candidate Transaction ID；warning ID / digest 必须绑定该 evidence。
5. `contractVersion` 冻结为 `TRANSACTION_IMPORT_CONFIRM_V1`。实现上线时，旧 Preview Session 因 version/options binding 不匹配而 fail closed，用户重新 Preview。
6. 不新增持久化 `CONFIRMING` 状态；数据库 Session row lock 就是 in-flight mutex，rollback 后状态仍为 `PREVIEW_READY`。
7. 过期状态不能采用“同一事务中 `markExpired` 后抛异常”的方式，因为异常会回滚状态更新。事务方法应提交一个 typed expired outcome，再由事务外映射为 `409`，或使用等价的独立持久化边界。

## 7. Domain Model

### 7.1 Preview Session

Session 是短生命周期 Confirm guard，不是金融批次。它持有：

- owner user ID；
- preallocated Batch ID；
- status / revision / expiresAt；
- file、mapping、options、normalized rows digest；
- raw / plan storage reference；
- consumedAt / cancelledAt。

### 7.2 Import Batch

Batch 只在金融 Confirm 成功的同一事务中出现，且 ID 必须等于 Session 的 `preallocated_batch_id`。一个 Session 最多对应一个 committed Batch。

### 7.3 Import Item

成功 Batch 的每个 canonical row 恰好对应一个 Item：

```text
batchId + sourceRowNumber + canonicalRowFingerprint
→ createdTransactionId + warningCodes
```

原子 Confirm 失败时不持久化失败 Item，也不留下部分成功 Transaction。失败审计使用脱敏 operational event，不创建误导性的金融 Batch。

### 7.4 Receipt

Receipt 是 Batch、Item 与 account impact 的不可变服务端视图。当前 Account.balance 或后来修改过的 Transaction 不能用于重算历史 Confirm receipt。

## 8. Session State Machine

沿用现有状态：

```text
MAPPING_REQUIRED
  └─ valid mapping/revision → PREVIEW_READY

PREVIEW_READY
  ├─ successful atomic Confirm → CONSUMED
  ├─ cancel wins Session lock/update → CANCELLED
  ├─ expiry wins before Confirm guard → EXPIRED
  └─ financial rollback → PREVIEW_READY

CONSUMED / CANCELLED / EXPIRED
  └─ terminal
```

规则：

- 只有 `PREVIEW_READY` 且 guard 获取时尚未过期的 Session 可首次 Confirm；
- `CONSUMED` 不得再创建金融事实；same key / same intent 返回原 receipt；
- `CANCELLED` / `EXPIRED` 在没有 committed Batch 时永久拒绝 Confirm；
- 两个并发 Confirm 由 Session row lock 串行；只有一个能执行写入；
- 不持久化 `CONFIRMING`，避免 crash 后遗留无法判定的中间状态；
- 如果 Batch 已 committed，Batch receipt 是权威事实；POST replay 必须先恢复 receipt，再判断 Session TTL 或 payload 是否已清理。

## 9. API Contract

### 9.1 Confirm

```http
POST /api/v1/imports/transactions/{importSessionId}/confirm
Authorization: Bearer <JWT>
Idempotency-Key: <1..100 chars, no surrounding spaces>
Content-Type: application/json
```

请求体采用 closed schema：

```json
{
  "previewToken": "opaque-signed-token",
  "acknowledgedWarningIds": ["warning-id"]
}
```

要求：

- `previewToken` 必填；
- `acknowledgedWarningIds` 必填，可为空数组；服务端按去重后字典序集合计算 intent；
- 客户端不得提交 rows、digest、account/category override、amount、userId、balance 或 receipt；
- user ID 只来自 JWT principal；
- 成功首次提交与成功 replay 均返回 HTTP `200`，沿用项目现有 API 风格。

POST response：

```text
ApiResponse<TransactionImportConfirmResponse>
  receipt
    importSessionId
    importBatchId
    status = CONFIRMED
    sourceFileName
    fileDigest
    totalRows
    acceptedRows
    createdCount
    skippedCount = 0
    warningCount
    transactions[]
      rowNumber
      transactionId
    accountImpacts[]
      accountId
      rowCount
      balanceBefore

      balanceAfter
    confirmedAt
    contractVersion = TRANSACTION_IMPORT_CONFIRM_V1
    resultDigest

```

所有 money 字段均使用 scale-2 plain decimal string。`idempotentReplay` 是本次 HTTP 调用的恢复 metadata，不进入 immutable receipt 或 `resultDigest`。

### 9.2 Receipt lookup / reconcile

```http
GET /api/v1/imports/transactions/batches/{importBatchId}
Authorization: Bearer <JWT>
```

- 只按当前 user 查询；missing 与 foreign Batch 都返回安全 `404`；
- 已提交返回完整 `TransactionImportReceipt`；
- `404` 只表示当前没有可见 committed Batch，不证明没有 in-flight Confirm；
- 客户端随后必须用同一 Session、token、key 与 body 重试 POST。

### 9.3 结构化错误

实现阶段新增 Import 专用异常 data，不改变 `ApiResponse` 外层：

```text
errorCode
retryable
outcome = NOT_COMMITTED | UNKNOWN
importSessionId
importBatchId
existingBatchId
```

字段按上下文可空。不得返回 SQL、堆栈、服务器路径、raw rows、request hash、完整 idempotency key 或 token 内容。

主要状态码：

| HTTP | 语义 |
| --- | --- |
| `200` | 首次 committed receipt 或 same-intent replay |
| `400` | 请求体、header、warning list 或字段格式错误 |
| `404` | Session / Batch 不存在或属于其他用户 |
| `409` | stale/expired/cancelled、warning 未确认、same-key conflict、exact duplicate、并发锁冲突 |
| `500` | committed state/receipt 不一致、未知约束或内部一致性失败 |
| `503` | 数据库暂时不可用；结果可能未知，必须 reconcile |

## 10. Idempotency Contract

### 10.1 Key scope

- `Idempotency-Key` 在 `(user_id, key)` 内唯一；不同用户相同 key 不冲突；
- key 必须原样满足 1–100 字符、非空、无首尾空白；服务端不静默 trim；
- key 持久化但不在响应或日志中回显。

### 10.2 Canonical request hash

`request_hash` 使用 SHA-256，canonical input 冻结为：

```text
operation=TRANSACTION_IMPORT_CONFIRM
contractVersion=TRANSACTION_IMPORT_CONFIRM_V1
userId
importSessionId
importBatchId
revision
fileDigest
mappingDigest
optionsDigest
normalizedRowsDigest
acknowledgedWarningIds(sorted distinct)
```

短生命周期 token 文本不进入 hash；token claims 进入。任何 intent 字段变化都会形成不同 hash。

### 10.3 结果

- same user + same key + same hash + committed Batch：HTTP `200`，返回同一 receipt，`idempotentReplay=true`；
- same user + same key + different hash：`409 IMPORT_IDEMPOTENCY_CONFLICT`，当前请求不写账；
- same Batch + different key：`409 IMPORT_BATCH_ALREADY_CONFIRMED`；
- different user：完全隔离；
- 提交前 rollback：Batch/key binding 不存在，原请求可安全重试；same-key/different-intent 的冲突规则只针对 durable committed binding，rollback attempt 不制造事务外幽灵占位；
- 只识别 V16/V14 中明确命名的 idempotency、session-binding 或 exact-batch constraint；未知 `23505` 进入 consistency failure，不得误报 replay。

### 10.4 Named Constraint Recovery Contract Amendment（2026-08-22）

#### 原要求与新发现

原冻结文本中“Batch unique violation 后事务外 reconcile”、`named unique recovery` 与 `unique loser rollback` 的组合，曾被解释为 Implementation 必须通过正常业务 API 制造：

```text
真实 named unique constraint race
→ expected constraint violation
→ lookup committed Batch
→ reconstruct authoritative receipt
```

实现阶段确认，该解释不适用于同一 Confirm intent 的正常并发路径：

- 同一 Session 的并发 Confirm 先由 Session `FOR UPDATE` 串行；
- 后到请求取得 Session lock 后，必须再次查询 committed Batch，并直接进入 replay/conflict resolution；
- committed Batch 使用 Session 的 `preallocated_batch_id`，一个 Session 只允许一个 committed Batch；
- `request_hash` 绑定 user、Session、preallocated Batch、revision、四类 digest 与 warning acknowledgment；
- 不同 Session 即使使用相同 `Idempotency-Key`，也具有不同 Confirm intent；它们的正常 unique race 结果是 conflict 或 exact-duplicate loser rollback，不是 same-intent successful replay。

因此，不得把“通过正常业务 API 触发真实 named unique violation 并成功 replay”继续作为 Phase 3D P1 GO Gate。不得为制造该场景而绕过 Session lock、跳过锁内 committed lookup、伪造 committed persistence，或让测试替代权威持久化 receipt 证据。

#### 修订后的 authoritative concurrency guarantee

正常 exactly-once financial effect 的硬保证由以下各层共同承担：

1. Session `FOR UPDATE`：序列化同一 Session 的 Confirm，并与 Cancel/cleanup 的 Session 终态竞争形成互斥；
2. 锁内 committed Batch lookup：后到 Confirm 在执行任何金融写入前完成 replay/conflict resolution；
3. preallocated Batch identity：把 Session、Batch、Items、account impacts 与 retry/reconcile 固定到同一 Batch identity；
4. 单一 PostgreSQL transaction：Transactions、balance、Batch、Items、account impacts 与 Session consume 要么全部 commit，要么全部 rollback；
5. database constraints：作为 user ownership、one-session-one-batch、idempotency key、exact duplicate、FK、check 与 receipt immutability 的最终一致性保护。

Implementation 必须以真实 PostgreSQL 的 Confirm-vs-Confirm concurrency 证明：同一 Session 只有一个 committed Batch、一次金融 mutation，后到 same-intent 请求返回同一 authoritative receipt；并以 unknown-commit retry 证明响应丢失后仍从 committed persistence 恢复而不重复写账。

#### Named Constraint Recovery 的定位与 fail-closed 规则

Named Constraint Recovery 定位为 **defense-in-depth fallback**，不是正常同 Session 并发实现幂等的核心机制，也不是应删除的 dead code。其契约为：

- 只允许识别 V14/V16 中明确命名、且与当前 Import 操作语义匹配的预期 constraint；
- 任何成功 replay 必须发生在 loser transaction 完整 rollback 之后，并只查询已经 committed 的 authoritative Batch；
- committed Batch 必须属于当前 user 与 Session，Batch ID 必须等于当前 Session 的 preallocated Batch ID，`Idempotency-Key` 与 `request_hash` 必须与当前 intent 完全一致；
- receipt 必须从 committed Batch、Items 与 account impacts 重建，不得从异常、内存 plan 或当前 Account 状态伪造；
- expected constraint 已命中但不存在可信 committed result，或 owner、Session、Batch、key、hash、status、receipt facts 任一不匹配时，必须 fail closed；
- `uk_transaction_import_batches_exact_duplicate` 只产生 exact-duplicate conflict，不得映射为 successful replay；
- unrelated unique constraint、FK violation、check constraint 与 unknown named constraint 必须原样进入一致性失败路径，绝不能映射为 successful replay。

#### 修订后的验收语义

- 正常 exactly-once / replay correctness 的 P1 Gate：Session row lock、锁内 committed replay、真实 Confirm-vs-Confirm PostgreSQL concurrency、one committed Batch、one financial mutation、transaction atomicity 与 unknown-commit recovery；
- defense-in-depth 的 P1 Gate：预期 constraint 的精确名称分类、rollback 后 authoritative lookup、完整 intent/ownership 校验、receipt persistence reconstruction，以及无可信 committed result 时 fail closed；
- negative constraint P1 Gate：分别证明 unrelated unique constraint、FK violation、check constraint 与 unknown named constraint 不会成为 successful replay；
- 可以用窄范围 matcher/reconciler 测试或其他不破坏生产序列化语义的测试证明 fallback；不要求通过正常业务 API 人为制造同 Session successful-replay unique race；
- different Sessions 的 same-key 或 exact-plan 自然竞争仍可用于验证 conflict / loser rollback，但不能替代同 Session Confirm serialization 与 authoritative replay 证据。

这是对验收模型与实际并发架构之间矛盾的 Contract correction，不是降低质量门槛：正常路径的 exactly-once、原子性、authoritative receipt 与 unknown-commit Gate 全部保留，同时把异常 fallback 的正向与负向边界冻结得更严格。

## 11. Frozen Preview Plan / Digest Contract

Confirm 的唯一事实来源是 Session 指向的 server-side `PreviewPlan`。

### 11.1 DB transaction 外 preflight

1. 校验认证、path、header 与 closed request schema；
2. 按 user + Session ID 读取非锁定 Session metadata；missing/foreign 返回 `404`；
3. 验证 token HMAC、user、Session、Batch、revision、digests、warning-set digest 与 contract version，但暂不因 expiry 终止，并由 claims 与 acknowledgment 集合计算 request hash；
4. 按 user/key 与 preallocated Batch ID 查询 committed receipt；找到时立即执行 replay/conflict 判断，不要求 plan 仍存在；
5. 没有 committed receipt 时，plan reference 必须存在，并按 64 MiB 边界一次性读取到内存；不读取或重解析原始 CSV/XLSX；
6. 重新计算 mapping/options/normalized rows/warning evidence digest；
7. 验证 row count `1..10,000`、没有 ERROR、所有 row importable、warning acknowledgment 恰好覆盖要求集合；
8. 收集并去重 Account / Category IDs，为事务内批量校验准备 immutable snapshot。

只有在 committed receipt 不存在时，plan missing、无法读取、反序列化失败或 digest 不一致才 fail closed 并禁止进入金融事务。事务外 receipt lookup 只是快速恢复路径；首次写入的金融事务在 Session guard 下必须再次查询，以关闭并发窗口。

### 11.2 金融事务内 binding 再验证

Session guard 获取后必须再次比较：

- owner；
- preallocated Batch ID；
- status / revision；
- expiresAt；
- file/mapping/options/rows digest；
- plan reference identity；
- token claims；
- preflight snapshot digest。

任何变化返回 `409 IMPORT_PREVIEW_STALE` 或 `IMPORT_PREVIEW_UNAVAILABLE`，不写任何金融事实。

## 12. Transaction Boundary

### 12.1 DB transaction 外

- HTTP/JWT 已有认证；
- key/body/token syntax；
- 有界 plan IO 与反序列化；
- digest 计算；
- 非权威结构校验和 ID 收集；
- committed 后的 payload cleanup；
- 不调用第三方 API，不重新解析 XLSX/CSV。

### 12.2 唯一金融 DB transaction 内

事务 timeout 固定 60 秒。顺序冻结为：

```text
configure local lock timeout
→ SELECT Session FOR UPDATE by user/session
→ lookup committed Batch by key and preallocated batch ID
→ replay/conflict resolution
→ verify PREVIEW_READY, expiry, revision, token/digest/plan snapshot
→ lock all owned Accounts in accountId ASC order
→ revalidate user, Accounts, Categories and row domain rules
→ bulk recheck exact batch and database probable duplicate evidence
→ create Transactions in sourceRowNumber ASC order
→ apply per-account aggregated balance deltas through AccountBalanceService
→ build canonical receipt and resultDigest from generated IDs, locked balances and one confirmedAt
→ insert confirmed Batch with resultDigest
→ insert one Item per row
→ insert immutable account impacts
→ CAS Session PREVIEW_READY → CONSUMED with consumedAt
→ COMMIT
```

任何一步失败，Transaction、balance、Batch、Items、account impacts 与 Session consume 全部 rollback。

Batch unique violation 发生时，当前金融事务必须先完整 rollback；事务外 orchestration 只针对明确约束查询 committed Batch 并执行 replay/conflict 判断。

## 13. Transaction / Account.balance Strategy

### 13.1 共享业务不变量

实现阶段提取共享内部 primitive，供 manual create 与 Import 使用，至少统一：

- supported type；
- amount sign / zero；
- `ADJUSTMENT` description；
- Category visibility / type；
- Account owner / `ACTIVE` / `CNY`；
- currency；
- `balanceDelta(type, amount)`；
- `NUMERIC(18,2)` 范围。

Import orchestration 可以批量调用该 primitive，但不得复制一份独立规则表。

### 13.2 Balance

- 每个 row 恰好贡献一次 delta；
- 同一 Account 的 delta 使用 `BigDecimal` 精确聚合；
- receipt 的 `balanceBefore` 来自已锁定 Account；
- 只调用一次 `AccountBalanceService.applyDeltas`，使用同一 `LockedAccounts`；
- `balanceAfter = balanceBefore + delta`，并由数据库更新结果与内存结果交叉检查；
- Account balance 可为负，沿用当前系统语义；
- overflow / scale 失败使全批 rollback。

### 13.3 Transaction order

Transactions 按 `sourceRowNumber ASC` 创建。批量/chunk insert 只用于减少 round trip，不改变顺序、不拆分事务、不提前 commit。生成 ID 必须稳定回绑到对应 Item。

## 14. Deterministic Locking

全局顺序：

```text
Session row
→ Account rows by accountId ASC
→ Batch/Item/account-impact insert
```

规则：

- Account IDs 先去重、升序，再由 `AccountBalanceService.lockOwnedAccounts` 一次获取；
- Confirm A `1→2` 与 Confirm B `2→1` 最终都按 `1→2` 锁定；
- manual create 只锁 Account；Import 不锁既有 Transaction，因此不会与 manual update/delete 的“Transaction → Account”形成反向依赖；
- Account update/deactivate 共用 Account lock，谁先获得锁谁的状态成为后续权威输入；
- Category 当前没有公开 update/delete 写路径，Confirm 在事务中重新读取即可；未来若新增 Category mutation，必须先冻结共享锁/CAS 规则；
- Session、Account lock 均使用当前可配置 lock timeout（默认 4 秒），整体事务仍受 60 秒 timeout；
- lock timeout / deadlock 返回 retryable `409`，服务端不在未知结果上自动换 key 重试。

## 15. Confirm-time Revalidation

在 Account locks 后重新校验：

- JWT user 仍为 active 用户；
- Session / Batch / plan 全部 user-scoped；
- Account 存在、属于用户、`ACTIVE`、`CNY`；
- Category 存在且属于用户，或严格满足 `user_id IS NULL AND is_system = true`；
- Category type 与 `INCOME` / `EXPENSE` 匹配；`ADJUSTMENT` 可使用可见收入或支出分类；
- type 仍为 `INCOME` / `EXPENSE` / `ADJUSTMENT`；
- amount 是 scale-2 `BigDecimal`，符号、零值与 `NUMERIC(18,2)` 合法；
- currency 为 `CNY` 且与 Account 一致；
- date/time、description 与业务不变量仍合法；
- 账户最终余额在 `NUMERIC(18,2)` 范围；
- database probable duplicate evidence 与 Preview binding 一致。

Preview 校验不能替代上述最终校验。任何环境变化按 stale/conflict 处理，不静默换 Account、Category 或金额。

## 16. Duplicate Semantics

### 16.1 Probable duplicate

- `IN_FILE_PROBABLE` 与 `DATABASE_PROBABLE` 是 warning，不是 blocker 或自动去重；
- 用户必须确认当前 revision 的全部 warning IDs；
- Confirm 在 Account locks 后用批量查询重算 database candidate IDs；
- warning evidence 以 `code + row fingerprint + candidate IDs` 绑定；
- evidence 与 Preview 不同返回 `409 IMPORT_PREVIEW_STALE`，要求重新 Preview；
- evidence 相同且已确认时，每行仍创建独立 Transaction。

### 16.2 Exact batch duplicate

相同 user 下 file、mapping、options、normalized rows 四类 digest 全部相同，命中 `EXACT_BATCH_DUPLICATE`：

- 返回 `409 IMPORT_EXACT_BATCH_DUPLICATE`；
- 可返回同用户的 `existingBatchId` 供 GET receipt；
- 不提供 bypass；
- 并发最终由 named unique constraint 兜底，loser 全事务 rollback。

## 17. Session → Batch Atomic Binding

- Batch ID 在 `PREVIEW_READY` 前由服务端预分配；
- Confirm 成功 Batch 必须使用该 ID，不能生成第二个 ID；
- V16 增加显式 `session_id` 与 user-scoped FK / unique binding；
- Batch、Items、account impacts 与 Session `CONSUMED` 同事务；
- rollback 后没有 Batch，Session 仍 `PREVIEW_READY`；
- retry 先按 user/key 与 preallocated Batch ID 查找 committed receipt；
- 一个 Session 永远最多产生一个 committed Batch。

## 18. Receipt 与 Import Item Contract

### 18.1 Authority

Receipt 由持久化 Batch、Items 与 account impacts 生成。以下字段不可从当前 Account 或前端重算：

- created Transaction IDs；
- imported/accepted count；
- balanceBefore/delta/balanceAfter；
- confirmedAt；
- resultDigest。

`resultDigest` 使用版本化 canonical serialization 计算，排除 `idempotentReplay`，replay 与 GET 必须返回相同 digest。

### 18.2 Item

- 成功 Item 的 `created_transaction_id` 必须非空；
- `(batch_id, source_row_number)` 唯一；
- 保存 canonical fingerprint 与 warning codes；
- 不保存完整 source values、description 或原文件；
- 不需要 `FAILED` Item、error code 或 error message，因为失败全批 rollback。

### 18.3 Internal idempotency identity

Batch 内部持久化原始 idempotency key 与 request hash；响应只暴露 Batch ID、receipt digest 和 replay flag，不回显 key/hash。

## 19. Unknown Commit / Retry / Reconcile

### 19.1 COMMIT 成功，响应丢失

```text
same batch ID GET
→ receipt found: definite success

GET 404
→ same Session + same token + same key + same body POST retry
→ Session lock waits or returns retryable conflict
→ committed Batch found
→ same receipt, no duplicate Transaction
```

Session 已过期或 plan 已清理不影响 committed replay，因为 receipt lookup 先于 expiry/plan requirement。

### 19.2 COMMIT 前失败

- PostgreSQL 回滚全部事实；
- Session 保持 `PREVIEW_READY`，除非已由独立 Cancel/expiry 获胜；
- 没有 Batch/key binding；
- 同一 intent/key 重试可以安全执行一次。

### 19.3 客户端状态

| 客户端状态 | 证据 | 行为 |
| --- | --- | --- |
| definitely succeeded | Confirm `200` 或 GET receipt `200` | 展示 receipt，停止写入重试 |
| definitely failed | 结构化 `400/404/409` 且 `outcome=NOT_COMMITTED` | 按 errorCode 修正、重新 Preview 或停止 |
| outcome unknown | 网络超时、连接中断、`500/503`、retryable lock conflict | GET preallocated Batch；随后同 key/body POST retry；绝不换 key 盲重试 |

## 20. Cancel Race

```text
Request A: Confirm
Request B: Cancel
```

- Confirm 首先在事务内锁 Session；Cancel 的条件 UPDATE 必须等待该 row lock；
- Confirm 先赢并 commit：Session 为 `CONSUMED`，Cancel 更新 0 行并返回 `409`；
- Cancel 先赢并 commit：Session 为 `CANCELLED`，Confirm guard 返回 `409`，不写账；
- Confirm rollback 后，等待中的 Cancel 可以成功；
- 不允许 Cancel 返回成功同时又出现 committed Batch。

## 21. Cleanup Race

- Confirm 只在事务外读取 plan 到内存；不在 Session/Account lock 下读取 raw/plan 文件；
- cleanup 在 plan 读取前删除成功：Confirm fail closed，不进入金融事务；
- plan 已完整读入内存后被 cleanup 删除：事务内仍必须通过 Session status/expiry/digest guard；
- Confirm 在 Session guard 时尚未过期并开始金融事务后，事务执行期间跨过 TTL 不自动中止；内存 plan 仍可完成，cleanup 的 `markExpired` 条件更新在 `CONSUMED` 后影响 0 行；
- Confirm 成功后，外层 service 立即 best-effort 删除 raw/plan 并清空 reference；删除失败不回滚金融事实，由 scheduler 重试；
- cleanup query 必须覆盖仍有 reference 的 `CONSUMED` Session；
- Batch、Items、account impacts 与 receipt 不参加 15 分钟 payload cleanup。

## 22. Security / User Isolation

- JWT principal 是唯一 user identity；
- Session、Batch、Account、Category、Transaction、Item 与 receipt 查询全部 user-scoped；
- foreign Session / Batch 与不存在统一 `404`；
- token 必须 HMAC-SHA-256 签名，使用独立、至少 32 字符的 secret；
- token 不替代数据库 ownership check；
- Session/Batch/Item/account-impact 使用 composite FK / unique 保护 user ownership；
- 客户端不得提交 userId、ownerId、Transaction user ID 或 balance；
- 日志只记录脱敏 session/batch identity 与 errorCode，不记录 key、token、raw row、description 或完整 mapping source value。

## 23. Amount / Precision

- 使用 `BigDecimal`，禁止 `double` / `float`；
- canonical amount 必须 scale 2，不执行 rounding；
- `INCOME` / `EXPENSE`：正数；
- `ADJUSTMENT`：非零有符号数且 description 非空白；
- Transaction 与 Account.balance 均受 `NUMERIC(18,2)` 范围约束；
- expense effect 只在 balance delta 中取负，Transaction.amount 仍保存正数；
- 当前只允许 `CNY`；
- receipt money 使用 scale-2 string。

## 24. Batch Size / Performance Boundary

- 沿用 Phase 3A / Phase 3C 最大 10,000 个非空数据行；Confirm 不得接受更大的 plan；
- Preview 分页仅是响应分页，不改变物理 plan 大小；
- Confirm 不重新解析 CSV/XLSX，不做外部 IO；
- Account、Category、probable duplicate 查询必须 set-based / bounded chunk，不允许逐行 N+1；
- Transaction 与 Item 可以 bounded chunk insert，但仍位于同一事务；
- 所有内存工作应为 O(n)，不得 O(n²) 重扫 duplicate；
- PostgreSQL bind parameter 上限决定内部 chunk 大小，不能把 chunk 误解为 partial commit；
- 实现 Closing Gate 必须以 10,000 行、单账户和多账户两类 plan 做真实 PostgreSQL 基准，证明在 60 秒事务上限内完成；若不能通过，必须回到 Contract 明确降低上限，不能静默上线。

## 25. Schema Impact — V16 Required

V14 / V15 不足以长期重建完整权威 receipt，因此 Confirm Implementation 必须新增前向 migration `V16`。本阶段不创建 SQL。

V16 schema contract：

1. `transaction_import_batches.session_id UUID NOT NULL`；
2. Session 增加 `(user_id, id)` composite unique，Batch 增加 `(user_id, session_id)` FK 与 unique，确保一 Session 一 committed Batch；
3. `transaction_import_batches.result_digest CHAR(64) NOT NULL` 及 SHA-256 check；
4. 新增 `transaction_import_batch_account_impacts`：`user_id`、`batch_id`、`account_id`、`row_count`、`balance_before`、`delta`、`balance_after`、`created_at`；
5. account impact 对 Batch 与 Account 使用 user-scoped composite FK，`(batch_id, account_id)` 唯一，money 为 `NUMERIC(18,2)`；
6. `transaction_import_items.created_transaction_id` 改为 `NOT NULL`；
7. Batch / Item / account impact 增加不可变保护；不得通过普通 UPDATE/DELETE 改写 committed receipt；
8. 保留现有 user-scoped idempotency、exact-batch unique 与 Batch `CONFIRMED` 单状态；
9. `request_hash` 已满足 idempotency payload digest，不新增第二个同义字段；
10. 不新增 `PENDING` / `FAILED` Batch，不新增完整 staging rows。

`previewToken`、warning evidence 和 cleanup query 属于 Java/Mapper 实现变化，不需要数据库列。V16 必须包含 fresh migration 与 V15→V16 upgrade 集成验证。

## 30. Frozen Decisions

Implementation 必须严格遵守：

1. Confirm 只执行服务端 frozen PreviewPlan；客户端 rows 永远不是事实来源。
2. Scope 只含 `INCOME`、`EXPENSE`、`ADJUSTMENT`。
3. 一个 Session 最多产生一个 committed Batch，Batch 使用预分配 ID。
4. Confirm 是同步、整批、单 PostgreSQL 事务；不允许 partial financial success。
5. Transactions、Account.balance、Batch、Items、account impacts、receipt 与 Session consume 全部同事务。
6. `AccountBalanceService` 是 balance 唯一生产写入者；Import 不写第二套余额 SQL。
7. Account locks 按去重 account ID 升序获取，锁顺序为 Session → Accounts。
8. plan IO 在 DB transaction 外完成；事务内重新验证 revision、token、digest 与 snapshot。
9. Confirm 时重新校验 user、Account、Category、type、amount、currency 与业务不变量。
10. probable duplicate 仍是 warning；evidence 改变必须重新 Preview，不静默跳过。
11. exact batch duplicate 返回 `409`，首版无 bypass。
12. same user/key/hash 返回同一 immutable receipt；same key/different hash 返回 `409`。
13. committed receipt lookup 先于 Session expiry/plan availability 判断，保证 unknown-commit 恢复。
14. expired/cancelled Session 在无 committed Batch 时永久禁止 Confirm。
15. 不持久化 `CONFIRMING`、`PENDING` 或 `FAILED` financial Batch。
16. Confirm 不重新解析原始 CSV/XLSX，不在锁内做文件 IO 或第三方调用。
17. 最大 Confirm plan 为 10,000 rows，事务 timeout 60 秒，Implementation 必须实测边界。
18. V16 是进入 Confirm Implementation 的必需 migration；本设计轮未创建 V16。
19. Receipt 必须持久化 enough facts，不能从后来变化的余额重算。
20. foreign resource 一律安全 `404`，user ID 只来自 JWT。

## 31. Deferred / Non-goals

- Import Frontend；
- investment import 与 BUY / SELL / DIVIDEND；
- `TRANSFER` / `REFUND`；
- partial import、row exclusion、Batch Undo；
- background/asynchronous financial Confirm；
- AI category、bank/broker API、mobile client；
- multi-currency redesign；
- Redis、MQ、distributed transaction；
- failed-attempt durable audit；
- Category mutation 的未来并发协议；
- probable duplicate index 的额外优化，仅在 10,000-row PostgreSQL 基准证明需要时单独评审。
