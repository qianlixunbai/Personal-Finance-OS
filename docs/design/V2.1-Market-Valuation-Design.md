## 2. 问题背景

v2.0 的行情快照可以返回 USD 等原始报价，但现有 Asset 人工估值与 Dashboard 仍是 CNY。直接把 USD price 写入 CNY `current_price`，或把 USD market value 写入 CNY `market_value`，会让同一字段同时表示不同币种并破坏所有既有汇总。

v2.1 要解决的不是“完整多币种账本”，而是一个更窄的问题：在不改变账务真值的前提下，用可追溯行情和汇率向用户提供 CNY 市场参考估值。

---

## 3. v2.1 目标

1. 为外币行情建立最新成功、可追溯的 FX 快照。
2. 用持仓数量、原始行情和 FX 快照生成 CNY 参考估值。
3. 保持 Account、Transaction、Asset 人工字段与 Dashboard 的 CNY 语义。
4. 复用 v2.0 的显式刷新、TTL、single-flight、额度和 stale fallback 模式。
5. 对单 Asset 和 Asset list/page 提供可批量计算、可测试、无 N+1 的后端能力。
6. 在 Assets UI 清楚区分“人工估值”和“市场参考估值”。

最小业务可交付范围是方案 B 的完整闭环：FX Foundation、FX Refresh、Reference Valuation Backend 和 Assets UI。各 Phase 可独立验收，但只有 Phase 1-4 完成后才构成用户可见的 v2.1。

---

## 4. 非目标

v2.1 不实现：

- 用户基础币种配置；
- 外币 Account、外币 Transaction、跨币种转账；
- 汇兑流水、汇兑损益或历史流水重估；
- 用 FX 刷新修改账户余额；
- 用参考估值修改 Transaction 或 Asset 人工估值；
- Dashboard 参考总资产；
- 历史行情、历史 FX、历史估值曲线；
- 定时、自动或批量刷新；
- BUY、SELL、DIVIDEND、手续费、税费和实现盈亏；
- 新市场、微服务、Redis、MQ 或分布式额度协调。

## 5. 术语

| 术语 | 定义 |
|---|---|
| 基础币种 | 跨币种参考总额使用的输出币种；v2.1 固定为 CNY |
| 人工估值 | 用户通过现有 Asset 字段确认的 CNY 成本、价格与市值 |
| 行情币种 | `market_quotes.currency`，Provider 报价所属币种 |
| FX base currency | 被换算的一单位源币种，例如 USD |
| FX quote currency | 换算后的目标币种，例如 CNY |
| 原生参考市值 | `quantity × quotePrice`，币种为行情币种 |
| CNY 参考估值 | 原生参考市值乘以到 CNY 的 FX rate |
| 最新成功快照 | 最近一次通过校验并成功持久化的 Provider 数据 |
| 账务真值 | Account、Transaction 和用户确认的 Asset 人工数据 |
| Reference Valuation | 只读派生结果，不是账务真值 |

## 7. 三种方案比较

| 维度 | 方案 A：完整多币种账本 | 方案 B：外币资产参考估值 | 方案 C：外币资产正式估值 |
|---|---|---|---|
| Account / Transaction | 全面放开 | 保持 CNY | 保持或被迫联动调整 |
| 余额联动 | 需汇兑、跨币种转账与历史口径 | 不变 | 风险扩散到 Dashboard / 现金链路 |
| 核心表 migration | 大规模修改与回填 | 只新增 exchange_rates | 修改 assets 并回填 |
| 旧字段语义 | 大量变化 | 完全保持 | currentPrice / marketValue 被重解释 |
| API 兼容 | 高风险 | additive DTO 可兼容 | 响应金额含义改变 |
| Dashboard | 全面重做 | v2.1 不改 | 直接切换为折算估值 |
| 双重真值 | 取决于完整账本设计 | 最终值不持久化，可控制 | 原生值与 CNY 值易不一致 |
| 测试规模 | 跨账本、汇兑、余额、历史 | 可按 FX / valuation 独立测试 | migration、回填、Dashboard 大范围回归 |
| v2.1 风险 | 极高 | 可控 | 高 |
| 结论 | 延期至 v3+ 专项设计 | 推荐 | 不进入 v2.1 |

### 7.1 方案 A

完整多币种账本要求定义外币现金、汇兑交易、跨币种转账、手续费、历史 rate、余额重估与汇兑损益。Transaction 当前会直接联动 Account balance，任何多币种开放都会触及事务一致性和历史数据语义。因此方案 A 不是“小版本扩展”，应延期到完整账本设计。

### 7.2 方案 B

方案 B 只在参考数据域新增 FX 和派生 DTO，不改变账务真值。最终估值不持久化，所有输入带来源和时间，既可避免第二套真值，也能在 Provider 失败时安全降级。它与当前行情隔离模式和批量查询模式一致，是 v2.1 的最小可信范围。

### 7.3 方案 C

方案 C 会让现有 `current_price`、`market_value` 和 `currency` 从 CNY 变为“有时 CNY、有时外币”，除非新增整套原生字段并回填。即使新增字段，同时持久化原生值和 CNY 值也需要严格版本、一致性和历史 rate 设计。该方案不应放在 v2.1 后半段，应在更大版本重新立项。

## 8. 推荐方案

采用方案 B：

```text
Asset.quantity
        ×
MarketQuote.price + MarketQuote.currency
        ↓
nativeMarketValue
        ×
ExchangeRate(quoteCurrency → CNY)
        ↓
CNY Reference Valuation
```

四类数据保持独立：持仓是用户数据；行情是 Provider 原始快照；FX 是 Provider 原始快照；Reference Valuation 是请求时派生结果。

## 9. 基础币种

v2.1 基础币种固定为 CNY，不增加 `users.base_currency`，也不增加用户配置 API。

理由：

- Account、Transaction、Asset 人工估值与 Dashboard 已围绕 CNY。
- 用户基础币种配置会迫使所有总额、缓存键、API 和历史数据加入新的维度。
- v2.1 目标是参考估值，不是国际化账本。
- 固定 CNY 使旧数据、现有测试和 Dashboard 完全不变。

---

## 10. Account / Transaction 范围

### 10.1 Account

`Account.currency` 继续仅允许 CNY。v2.1 不增加外币现金 Account，不使用 FX 修改 balance，不对余额做实时重估。

### 10.2 Transaction

`Transaction.currency` 继续仅允许 CNY，且必须与所属 Account 一致。v2.1 不增加外币收入支出、跨币种转账、汇兑流水、汇兑损益或历史流水重估。

这些能力会改变当前事务内余额回滚/应用规则，必须与完整投资交易和多币种账本一起设计，而不是由参考行情功能隐式引入。

---

## 11. Asset 语义

`Asset.currency` 在 v2.1 继续表示人工估值币种 CNY，不表示交易所报价币种。市场报价币种只来自 `market_quotes.currency`。

这意味着一个 US AAPL Asset 可以同时具有：

```text
Asset.currency = CNY              # 用户人工估值币种
MarketQuote.currency = USD        # 原始行情币种
ReferenceValuation.baseCurrency = CNY
```

Phase 1 不修改 assets 表。`avg_cost`、`current_price` 与 `market_value` 的现有持久化/响应一致性 gap 也不在本任务顺手修复。

## 12. Exchange Rate 模型

汇率方向固定为：

```text
base_currency = USD
quote_currency = CNY
rate = 7.25

1 USD = 7.25 CNY
```

即 `1 base_currency = rate quote_currency`。Reference Valuation 需要的 pair 是 `market_quotes.currency → CNY`，不得把 rate 反向使用。

### 12.1 表结构

计划 migration：`backend/src/main/resources/db/migration/V3__exchange_rates.sql`。

| 字段 | PostgreSQL 类型 | 规则 |
|---|---|---|
| `id` | `BIGSERIAL` | PRIMARY KEY |
| `base_currency` | `VARCHAR(3)` | NOT NULL；大写三字母 |
| `quote_currency` | `VARCHAR(3)` | NOT NULL；大写三字母 |
| `rate` | `NUMERIC(24,12)` | NOT NULL；大于 0 |
| `rate_time` | `TIMESTAMPTZ` | NOT NULL；Provider 的报价/生效时间 |
| `fetched_at` | `TIMESTAMPTZ` | NOT NULL；系统成功获取时间 |
| `provider` | `VARCHAR(30)` | NOT NULL；标准化 Provider ID |
| `created_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT CURRENT_TIMESTAMP |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT CURRENT_TIMESTAMP |

约束：

- `UNIQUE(base_currency, quote_currency)`；
- 两个 currency 均满足 `^[A-Z]{3}$`；
- `base_currency <> quote_currency`；
- `rate > 0`。

唯一约束产生的索引覆盖按货币对的唯一查询。Phase 1 不增加 `fetched_at`、`provider` 或冗余货币对索引。

### 12.2 存储策略

- 只保存最新成功快照，不保存历史表。
- 不保存 `user_id`，同一货币对由所有用户公共复用。
- v2.1 只写入“行情币种 → CNY”的直接 rate。
- 不保存反向倒数；如未来需要任意方向，由新设计决定。
- `CNY/CNY = 1` 在 Service 内作为恒等转换返回，不持久化。
- 不需要 status 字段：表中只存在成功快照，状态由 `fetched_at` 与 TTL 派生。
- Provider 失败、持久化失败或响应校验失败不得更新任何列。

### 12.3 upsert 规则

冲突键为 `(base_currency, quote_currency)`。只有下列情况可覆盖：

```text
new.rate_time > old.rate_time
OR
new.rate_time = old.rate_time AND new.fetched_at >= old.fetched_at
```

这样可以拒绝更旧的市场时间，同时允许周末或休市期间 Provider 对同一有效 rate 的重新获取更新 freshness。

## 13. Provider 抽象

### 13.1 接口

```java
interface ExchangeRateProvider {
    ExchangeRateQuote fetchRate(String baseCurrency, String quoteCurrency);
}
```

`ExchangeRateQuote` 至少包含：

```text
baseCurrency
quoteCurrency
rate
rateTime
provider
```

`fetchedAt` 由 Service 使用注入的 `Clock` 生成，不能信任 Provider 填写。

### 13.2 异常分类

`ExchangeRateProviderException` 应携带内部 error type：

- `DISABLED`
- `CONFIGURATION`
- `AUTHENTICATION`（401/403）
- `RATE_LIMITED`（429）
- `UPSTREAM_ERROR`（5xx）
- `TRANSPORT`（连接失败或 timeout）
- `RESPONSE_FORMAT`（malformed payload）
- `UNSUPPORTED_PAIR`
- `INVALID_RATE`
- `INVALID_TIME`
- `CURRENCY_MISMATCH`

异常只能暴露统一、安全的客户端信息；Provider URL、API Key、原始响应或内部堆栈不得返回前端。

### 13.3 配置与 Secret

- 使用独立 `fx-data.*` 配置，不复用行情 API Key 或额度字段。
- `fx-data.enabled` 默认 `false`。
- 启用但缺 API Key 时启动 fail-fast。
- connect timeout、read timeout、TTL、用户额度和全局额度必须为正数并有配置测试。
- API Key 只来自环境变量或 Secret Store，不进入数据库、日志、DTO 或仓库。
- Phase 0 不选择真实 Provider；实施前核实价格、许可证、覆盖货币对、时间字段、rate 方向和额度。

## 14. 精度与舍入

### 14.1 输入精度

| 数据 | 精度 | 来源 |
|---|---|---|
| quantity | `DECIMAL(18,8)` | 现有 assets |
| quotePrice | `NUMERIC(20,8)` | 现有 market_quotes |
| fxRate | `NUMERIC(24,12)` | 新 exchange_rates |

`NUMERIC(24,12)` 为 rate 提供 12 位整数和 12 位小数，足以覆盖 v2.1 的法币到 CNY 直接汇率，并与现有 8 位行情精度保持安全余量。

### 14.2 Java 运算

```text
nativeExact = quantity.multiply(quotePrice)
cnyExact = nativeExact.multiply(fxRate)
cnyResult = cnyExact.setScale(2, RoundingMode.HALF_UP)
```

- 不使用 `doubleValue()`、`floatValue()` 或浮点中转。
- 两次乘法均使用 BigDecimal 精确乘法，不在中间阶段舍入。
- 因数据库已限制输入精度，不额外使用会提前截断有效数字的固定 MathContext。
- `nativeMarketValue` 以精确乘积返回，最多 16 位小数。
- CNY 最终 API 金额固定 scale 2，使用 `HALF_UP`，与当前 AssetService / Dashboard 的显式舍入习惯一致。
- `quotePrice` 和 `fxRate` 按快照存储值返回，不由前端改变。
- 前端可按展示规则隐藏尾随零，但不得重算最终 CNY 金额。

## 15. TTL 与 freshness

### 15.1 独立 freshness

行情与 FX 分别计算：

```text
FRESH          fetchedAt 存在，now <= fetchedAt + TTL
STALE          fetchedAt 存在，now > fetchedAt + TTL
NEVER_FETCHED  没有成功快照
```

TTL 边界沿用当前行情语义：恰好等于过期时刻仍为 FRESH，只有 `now` 严格晚于过期时刻才为 STALE。

### 15.2 TTL 建议

- Quote TTL 保持当前 15 分钟。
- FX TTL 建议默认 1 小时，并保持可配置。
- 两种 TTL 不合并为一个字段，因为市场时效和 Provider 额度不同。
- 周末、美股休市或 FX 休市不伪装为 FRESH；仍按 fetchedAt 计算，并保留 quoteTime / rateTime 供用户解释。
- v2.1 不引入交易日历。重复获取相同 rateTime 但新的 fetchedAt 可以恢复 FRESH。

### 15.3 组合状态

| Quote | FX | 是否可计算 CNY | valuationFreshness |
|---|---|---|---|
| FRESH | FRESH | 是 | FRESH |
| FRESH | STALE | 是 | STALE |
| STALE | FRESH | 是 | STALE |
| STALE | STALE | 是 | STALE |
| 存在 | NEVER_FETCHED | 否 | PARTIAL |
| NEVER_FETCHED | 存在 | 否 | PARTIAL |
| NEVER_FETCHED | NEVER_FETCHED | 否 | UNAVAILABLE |

当 quote currency 为 CNY 时不需要外部 FX；系统恒等转换视为 FRESH。

`PARTIAL` 只表示“恰有一个必需外部输入可用，无法生成最终 CNY 值”；`UNAVAILABLE` 表示没有足够的有效输入或资产不支持参考估值。它们不能与 STALE 混用。

## 16. single-flight 与额度保护

### 16.1 key

```text
Quote single-flight: (market, symbol)
FX single-flight: (baseCurrency, quoteCurrency)
```

两者使用独立 in-flight map 和独立额度计数，继续明确为单进程能力。

### 16.2 刷新决策

| Quote | FX | 刷新动作 |
|---|---|---|
| FRESH | FRESH | 直接 CACHE_HIT |
| STALE / missing | FRESH | 只刷新 Quote |
| FRESH | STALE / missing | 只刷新 FX |
| STALE / missing | STALE / missing | 先确保 Quote 可用，再按其 currency 刷新 FX |

原因：当 Quote 从未获取时，系统不能信任前端传入币种，必须先从受信 Provider / 快照得到 quote currency。

额度规则：

- 只有 single-flight leader 在真正调用 Provider 前消费额度。
- 等待同一 key 的请求不重复消费额度。
- cache hit 不消费额度。
- Quote 和 FX 分别维护每用户/每分钟与全局/每分钟额度。
- 任一失败都必须清理自己的 in-flight key，后续可以重试。

## 17. stale fallback

### 17.1 单组件

- Provider 或额度失败且存在旧快照：保留旧快照，返回 `STALE_FALLBACK`。
- Provider 失败且无快照：返回映射后的 404、429、502 或 503。
- 持久化失败不能返回 UPDATED；旧快照保持不变。

### 17.2 组合估值

- Quote 与 FX 都仍有快照，即使任一刷新失败，仍计算 CNY 参考估值，整体为 STALE。
- 只有 Quote：返回 quote、nativeMarketValue，FX 与 CNY 值为 null，整体 PARTIAL。
- 只有 FX：返回 FX 追溯信息；quote、nativeMarketValue、CNY 值为 null，整体 PARTIAL。
- 两者都没有：整体 UNAVAILABLE，金额字段为 null。
- warning 使用结构化列表，不拼接 Provider 原始消息。

建议 warning：

```text
code: QUOTE_STALE | FX_STALE | QUOTE_MISSING | FX_MISSING | REFRESH_FAILED | FEATURE_DISABLED
component: QUOTE | FX | VALUATION
message: 固定、可本地化的用户说明
```

## 18. Reference Valuation

### 18.1 只读 DTO

建议 `ReferenceValuationResponse`：

```text
assetId                         required
symbol                          optional
quantity                        required

quoteCurrency                   optional
quotePrice                      optional
quoteTime                       optional
quoteFetchedAt                  optional
quoteProvider                   optional
quoteFreshness                  required

fxRequired                      required
fxBaseCurrency                  optional
fxQuoteCurrency                 optional
fxRate                          optional
fxRateTime                      optional
fxFetchedAt                     optional
fxProvider                      optional
fxFreshness                     required

nativeMarketValue               optional
baseCurrency = CNY              required
baseCurrencyMarketValue         optional

valuationFreshness              required
calculatedAt                    required
formulaVersion                  required, REFERENCE_VALUATION_V1
warnings[]                      required, empty list allowed
```

Provider ID 可以返回以满足输入追溯，但只返回标准化 ID，不返回 URL、套餐、Key 或原始错误。

### 18.2 null 与部分对象

接口返回一个结构稳定的对象，而不是在缺失时整体返回 null：

- 缺 Quote：quote 字段、nativeMarketValue、baseCurrencyMarketValue 为 null。
- Quote 存在但缺 FX：Quote 和 nativeMarketValue 有值，FX 与 CNY 值为 null。
- Quote 为 CNY：`fxRequired=false`，rate 为 1，Provider 可表示为 `SYSTEM_IDENTITY`，时间字段为 null。
- 资产完全不支持行情时，Asset list/page 的 `referenceValuation` 为 null；显式刷新返回 400。

### 18.3 不持久化最终值

不新增 `reference_valuations` 表，也不向 assets 增加 CNY reference value 列。运行时从当前 quantity、最新成功 quote、最新成功 FX 计算。

收益：避免重复数据；不会出现 quote/FX 已更新但最终值未更新；输入仍可通过响应追溯；批量查询后性能可控。

限制：最新快照被覆盖后不能复原历史页面结果。历史审计需要 v2.2 的快照历史设计，不通过持久化“最终值”补丁解决。

### 18.4 批量性能

Asset list/page 应采用：

1. 一次查询当前页 Assets；
2. 一次批量查询去重后的 `(market, symbol)` 行情；
3. 提取 distinct quote currencies；
4. 一次批量查询 `(quoteCurrency, CNY)` FX；
5. 在后端内存中逐项使用 BigDecimal 计算。

目标是每页固定数量查询，不按 Asset 调用数据库或 Provider。

## 19. API 候选

### 19.1 方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 独立 GET `/assets/{id}/reference-valuation` | 职责明确，单项调试方便 | list/page 容易 N+1；与 Asset detail 重复读取 | 可选，不作为首选列表方案 |
| AssetResponse 新增 `referenceValuation` | additive 兼容；与现有 marketQuote 模式一致；支持批量 | Response 变大；需要控制 Phase 开放时机 | 推荐读取方案 |
| 扩展现有 quote refresh 同时刷新 FX | 前端按钮少 | 静默改变现有 endpoint 语义；Quote 与 FX 生命周期耦合 | 拒绝 |
| 新增 reference valuation refresh | 显式副作用；可按 freshness 分别刷新 | 新增 endpoint 与测试 | 推荐刷新方案 |

### 19.2 推荐契约

读取：

```text
GET /api/v1/assets
GET /api/v1/assets/page
GET /api/v1/assets/{id}

AssetResponse.referenceValuation = nullable
```

普通 GET 只读取数据库，不调用 Provider。list/page 使用批量查询，不允许前端逐行调用独立 GET。

刷新：

```text
POST /api/v1/assets/{id}/reference-valuation/refresh
```

该 POST：

- 从认证 principal 获取 userId；
- 只接收 Asset ID；
- 先验证 Asset 存在、归属、类型、market 和 symbol；
- 根据 Quote/FX freshness 只刷新需要的组件；
- 返回完整 `ReferenceValuationResponse` 及 refresh 结果；
- 使用现有统一错误包装与 400/401/404/429/502/503 映射。

保留现有 `POST /assets/{id}/quote/refresh`，它继续只处理行情，保障 API 向后兼容。

## 20. Dashboard 边界

v2.1 Phase 1-4 均不修改 Dashboard：

- totalAssets 继续等于 CNY Account balance 加 CNY 人工 Asset value；
- investment allocation 继续使用人工 `currentPrice × quantity`；
- monthly income/expense 继续只聚合 CNY Transaction；
- Dashboard 不读取 exchange_rates，不调用任何 Provider。

原因：

- 参考数据可能 STALE、PARTIAL 或 UNAVAILABLE；
- 并非所有 Asset 都有行情或 FX；
- 人工估值是用户确认数据，市场估值是参考数据；
- 静默替换会让总资产口径随 Provider 可用性波动。

最早在 v2.2 或后续独立阶段，通过新 ADR 评估“市场参考总资产”或显式口径切换。新指标必须与现有总资产并列，不能覆盖旧字段。

## 21. 安全边界

- 所有 Asset 和 valuation API 均要求 JWT。
- 他人 Asset 按现有防枚举语义返回 404。
- 在读取缓存、消费额度或调用 Provider 前验证 Asset 归属和支持边界。
- symbol、market 和 quote currency 来自受控 Asset / MarketQuote 数据，不接受客户端覆盖。
- rate、provider、Provider URL 和 API Key 不接受客户端输入。
- FX 快照是公共市场参考数据，不存 `user_id`；Asset ownership 仍决定谁可以触发刷新。
- 用户级额度防止单用户滥用，独立全局额度保护 Provider 套餐。
- Provider 原始错误、响应正文、Secret 和内部堆栈不得进入客户端 warning。

| 风险 | 严重度 | 缓解 |

## 26. Open Questions

以下仅保留真正影响实现的四项：

1. **FX Provider：** 哪个供应商在价格、许可证、USD/CNY 等货币对、rateTime、额度和 SLA 上满足需求？该问题阻塞 Phase 2 adapter，不阻塞 Phase 1 schema 和抽象。
2. **FX TTL 与额度：** 是否接受默认 1 小时；用户级和全局默认额度需要按最终 Provider 套餐确定。
3. **list/page 开放时机：** Phase 3 是否立即在 AssetResponse 返回 nullable `referenceValuation`，还是只先完成内部批量能力并在 Phase 4 开放字段？推荐 Phase 3 完成契约与批量能力，Phase 4 消费。
4. **原生金额展示：** Phase 4 按币种定义小数位，还是统一最多 8 位？后端仍返回精确值，此问题只影响 UI formatter。

## 27. 最终建议

v2.1 应采用方案 B，并按四个阶段实施。设计满足以下 GO 条件：

- 旧 CNY 字段与 API 语义不变；
- Account / Transaction 规则不变；
- 行情币种、FX 币种方向和基础币种明确；
- 原始数据与派生估值分离；
- 汇率包含来源、报价时间和获取时间；
- 全部金额计算使用 BigDecimal；
- GET 和 Dashboard 不隐式联网；
- Provider 失败不修改账务真值；
- 最终 CNY 参考估值不持久化；
- Dashboard 不在 v2.1 接入；
- migration 是单表 additive 变化；
