## 2. 已核实的当前事实

### 2.1 后端权威边界

1. Confirm 只执行服务端冻结的 `PreviewPlan`；客户端 rows 从来不是 Confirm truth。
2. `Transaction`、`Account.balance`、Batch、Items、Account Impacts、receipt 与 Session `CONSUMED` 在同一 PostgreSQL transaction 中提交或回滚。
3. backend 是 amount validation、Account / Category ownership、probable duplicate、warning evidence、最终 balance effect、receipt 和 `resultDigest` 的唯一权威来源。
4. Session TTL 为 15 分钟；首次 Confirm 只允许 `PREVIEW_READY` 且服务端判定仍有效的 Session。
5. `previewToken` 是 signed opaque token，绑定 user、session、batch、revision、plan identity、warning set 和 expiry。
6. Confirm 需要 `Idempotency-Key`，请求 body 只包含 `previewToken` 与 `acknowledgedWarningIds`。
7. committed replay 与 receipt lookup 不依赖客户端继续保存 Preview rows，也不依赖临时 PreviewPlan 仍存在。

### 2.2 当前前端模式

- React 19 + TypeScript + Vite + React Router + Axios；没有 Redux、React Query 或 toast framework。
- 单一 Axios client 的 `baseURL` 是 `/api/v1`；request interceptor 从 `localStorage.token` 注入 Bearer JWT。
- 受保护请求 `401` 会清除 token 与 `finance-os:auth-user-id:v1` 并跳转 `/login`。
- 页面使用本地 React state/hooks、`PageHeader`、`AlertMessage`、`SummaryCard`、`Badge`、`Pagination`、`content-card`、`page-panel` 与 `data-table`。
- 成功和失败反馈是页面内 alert，不是 toast。
- 普通小型危险操作使用 native confirm；高风险 Investment command 使用可访问 modal、复核层、pending localStorage record、Web Locks、401 recovery 和 same-key resend。
- 桌面为暗色账本工作区；移动端在 768px 以下使用顶部栏、底部导航、单列 form 与 bottom-sheet modal。

Import 必须扩展上述模式，不能创建第二套 router、Axios、modal、notification 或 state-management architecture。

## 3. 真实公开 API Contract

Axios wrapper 使用相对 `/api/v1` 的下列 path：

| 操作 | HTTP endpoint | 前端 path | 说明 |
| --- | --- | --- | --- |
| Upload / initial preview | `POST /api/v1/imports/transactions/preview` | `/imports/transactions/preview` | multipart `file` + JSON part `request` |
| Mapping / new revision | `PUT /api/v1/imports/transactions/{sessionId}/preview` | `/imports/transactions/{sessionId}/preview` | multipart JSON part `mapping` |
| Preview rows | `GET /api/v1/imports/transactions/{sessionId}/rows?page=&size=` | `/imports/transactions/{sessionId}/rows` | 1-based；默认 100；后端 clamp 到 1–500 |
| Confirm | `POST /api/v1/imports/transactions/{sessionId}/confirm` | `/imports/transactions/{sessionId}/confirm` | `Idempotency-Key` + exact JSON body |
| Receipt / reconcile | `GET /api/v1/imports/transactions/batches/{batchId}` | `/imports/transactions/batches/{batchId}` | committed receipt only |
| Cancel | `DELETE /api/v1/imports/transactions/{sessionId}` | `/imports/transactions/{sessionId}` | 仅未终结 Session |

所有 response 继续使用：

```ts
interface ApiResponse<T> {
  code: number
  message: string
  data?: T
  errorCode?: string
  retryable?: boolean
}
```

### 3.1 Upload request

前端固定发送 `format: 'AUTO'`，避免由客户端成为格式判断权威：

```text
multipart/form-data
  file: File
  request: application/json Blob
    {
      "format": "AUTO",
      "mapping": null | TransactionImportMapping
    }
```

浏览器不得手写 multipart boundary。

### 3.2 Mapping request

```ts
interface TransactionImportMapping {
  columnMappings: Record<string, string>
  typeMappings: Record<string, 'INCOME' | 'EXPENSE' | 'ADJUSTMENT'>
  accountMappings: Record<string, number>
  categoryMappings: Record<string, number>
}
```

`columnMappings` 的实际形状不是简单的 source-to-target map：

- mapped target 使用 `canonicalTarget -> exact detected header`；
- 每个未使用 source header 使用 `sourceHeader -> 'IGNORE'`；
- required target 为 `date`、`type`、`amount`、`account`、`category`；
- optional target 为 `time`、`description`、`currency`；
- 同一 source header 不得被两个 target 使用。

### 3.3 Preview response

当前 response 实际提供：

```ts
interface TransactionImportPreviewResponse {
  importSessionId: string
  importBatchId: string | null
  sessionStatus: 'MAPPING_REQUIRED' | 'PREVIEW_READY' | string
  revision: number
  detectedColumns: string[]
  mapping: TransactionImportMapping | null
  rows: TransactionImportPreviewRow[]       // PREVIEW_READY 内嵌前 100 条
  summary: {
    totalRows: number
    validRows: number
    warningRows: number
    errorRows: number
    importableRows: number
    duplicateCandidates: number
  }
  fileDigest: string
  mappingDigest: string | null
  optionsDigest: string
  normalizedRowsDigest: string | null
  expiresAt: string
  confirmable: boolean
  previewToken: string | null
}
```

当前 response **没有** file name / size / detected format object、`detectedMappingValues`、row page metadata、top-level warning ID set、server-side row filter 或 Preview Session GET endpoint。前端设计必须在这些真实边界内工作。

### 3.4 Preview row

```ts
interface TransactionImportPreviewRow {
  rowNumber: number
  sourceValues: Record<string, string>
  normalizedValues: Record<string, string>
  mappingStatus: 'MAPPED' | 'INVALID' | string
  errors: TransactionImportValidationMessage[]
  warnings: TransactionImportValidationMessage[]
  duplicateStatus: 'NONE' | 'IN_FILE_PROBABLE' | 'DATABASE_PROBABLE' | string
  importable: boolean
}

interface TransactionImportValidationMessage {
  id: string
  code: string
  scope: string
  field: string | null
  rowNumber: number | null
  message: string
  retryable: boolean
}
```

UI row status 只可按 backend fields 派生：

```text
errors.length > 0    → ERROR
else warnings > 0    → WARNING
else                 → VALID
```

这只是后端状态的显示投影，不是前端重新校验或重新判定 duplicate。

### 3.5 Confirm request

```http
POST /imports/transactions/{importSessionId}/confirm
Idempotency-Key: <crypto.randomUUID()>
Content-Type: application/json
```

```json
{
  "previewToken": "opaque-signed-token",
  "acknowledgedWarningIds": ["backend-warning-id"]
}
```

禁止额外提交 file、rows、normalized values、digests、account/category override、amount、userId、balance、receipt 或 `resultDigest`。

### 3.6 Receipt

Confirm `200` 返回 `{ receipt, idempotentReplay }`；GET batch 返回同一个 persisted receipt：

```ts
interface TransactionImportReceipt {
  importSessionId: string
  importBatchId: string
  status: 'CONFIRMED'
  sourceFileName: string
  fileDigest: string
  totalRows: number
  acceptedRows: number
  createdCount: number
  skippedCount: number
  warningCount: number
  transactions: Array<{ rowNumber: number; transactionId: number }>
  accountImpacts: Array<{
    accountId: number
    rowCount: number
    balanceBefore: DecimalText
    delta: DecimalText
    balanceAfter: DecimalText
  }>
  confirmedAt: string
  contractVersion: string
  resultDigest: string
}
```

`DecimalText` 是前端内部的 lossless decimal string 类型，绝不是 `number`。

当前 Java DTO 的三个 money 字段是 `BigDecimal`，实际默认 wire JSON 为 number，例如：

```json
{"balanceBefore":9999999999999999.99,"delta":-0.01,"balanceAfter":9999999999999999.98}
```

标准 Axios / `JSON.parse` 会先转换为 IEEE-754 `number`，在当前 `NUMERIC(18,2)` 上限内可能丢失分。未来实现必须为 Confirm/Receipt GET 使用 Import 专用的 **lossless response transport adapter**，从原始 response text 保留 decimal lexeme 并经过 runtime validation 转为 `DecimalText`。不得先解析成 JS number 再 `String(...)`；不得用该适配器计算任何余额。若 wire contract 未来改为 string，该 adapter 应同时接受 string 并保持同一内部类型。

### 3.7 Lossless transport 实现边界

当前 Axios 默认 transform 等价于先对 response body 执行 `JSON.parse`；调用方拿到 `response.data` 时精度已经不可恢复。Import 的 Confirm 与 Receipt GET 必须在请求 config 层同时使用 raw text response 和 identity `transformResponse`，保证专用 adapter 在任何标准 JSON parse 之前取得完整 response text。

adapter 必须遵守：

1. 使用维护中的 lossless JSON parser 解析完整 JSON document；不得用 regex、字符串替换或手写局部 JSON parser 抽取 money。
2. 解析后仍按现有 `ApiResponse<T>` envelope 做 runtime validation；success 与 error envelope 都不能绕过现有 `code/message/data/errorCode/retryable` 语义。
3. `balanceBefore`、`delta`、`balanceAfter` 只接受 lossless numeric lexeme 或后端未来返回的 decimal string，并统一转为前端内部 `DecimalText`；科学计数法、非有限值、超出 fixed-scale contract 的值 fail closed。
4. `accountId`、`transactionId` 等整数仍需执行 safe-integer/positive-integer validation；lossless parser 不能把任意超范围整数静默降成 JavaScript `number`。
5. 继续复用当前 Axios client 的 `baseURL`、JWT request interceptor、401 hook 与 error flow；只覆盖这两个 endpoint 的 response decoding，不创建第二套 auth/client architecture。

当前 Import 读取的 decimal scope 冻结如下：

| 数据 | Wire 形状 | Frontend 处理 |
| --- | --- | --- |
| Preview `normalizedValues.amount` | backend 已返回 string | 保持 string；不经过 `Number`，无需 lossless JSON number adapter |
| Mapping 使用的 Account options | Account response 可能包含 JSON number balance | Import 不显示、不计算、不持久化该 balance；只消费 ID/name/type/status/currency |
| Confirm response `receipt.accountImpacts[]` | 三个 `BigDecimal` 当前为 JSON number | 必须使用 raw-text lossless adapter |
| Receipt GET `accountImpacts[]` | 同上 | 必须使用同一 adapter |

若未来 Receipt 或 Preview 新增 JSON number 金融字段，必须先扩展此 runtime schema 和测试，再允许 UI 消费；不得把 standard Axios 已解析的 number 转回 string 冒充 lossless。

## 4. 方案比较与冻结选择

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| `/transactions/import` 单路由分步工作台 + hooks + server-paged rows | 采用 | 符合现有 Router/React state；步骤有共同 Session；不引入全局状态框架 |
| 把 Upload/Mapping/Preview 分散为多个 route | 拒绝 | 浏览器 history 与短 TTL Session 更难收敛，刷新时更依赖不存在的 Session GET |
| 在 Transactions 页内堆叠所有 Import UI | 拒绝 | Preview、warning 与 receipt 信息量会破坏现有流水 CRUD 页层级 |
| 全量下载 10,000 rows 后做 spreadsheet editor | 拒绝 | 隐私/内存成本高，容易形成客户端 plan，且违反 frozen non-goal |
| Preview 使用全局 status tabs / filters | 首版拒绝 | 当前 rows API 不支持 filter；仅过滤当前页会误导用户 |
| Summary + status chips + server-paged table + expandable detail | 采用 | 与当前组件一致，状态清晰，不虚构全局筛选能力 |
| memory-only Confirm intent | 拒绝 | refresh、crash、401 或浏览器重启会丢失 same-key recovery 材料 |
| 所有 Preview rows 永久写入 localStorage | 拒绝 | 暴露原始财务行，不必要且不是 Confirm truth |
| sessionStorage draft + localStorage pending Confirm | 采用 | 同 tab 可恢复编辑；真正发出的金融意图可跨 refresh/restart 恢复；最小化持久数据 |

## 5. 产品入口与页面结构

### 5.1 Route 与导航

- Transactions 页 `PageHeader.actions` 增加“导入流水”，进入 `/transactions/import`。
- Import 是“交易流水”的从属能力，不增加第六个 sidebar/mobile bottom-nav 主入口。
- receipt 使用可刷新 route `/transactions/import/receipts/{importBatchId}`，只调用已有 GET batch API。
- Import 内的 Upload / Mapping / Preview / Warning / Confirm 是同一 route 的内部状态，不各自压入 browser history。
- `/transactions/import` 的 Layout page name 显示“导入流水”，不回退成“财务工作区”。

### 5.2 页面信息架构

页面顶部使用现有 `PageHeader`，下面增加一条与 Import 证据链一一对应的六段状态轨：

```text
上传文件 → 映射字段 → 生成预览 → 复核警告 → 确认导入 → 权威回执
```

它不是装饰性 stepper：每段明确表示当前是否只有客户端选择、是否已有 server Session、是否已有 signed token、是否已 committed。只在这里使用较强的 cyan focus line；其余区域保持现有卡片系统。

视觉继续使用现有 tokens：canvas `#05080d`、panel `#0a0f16`、cyan `#22d3ee`、success `#10b981`、warning `#f59e0b`、danger `#f43f5e`；正文沿用 Inter/system/`Microsoft YaHei`，row number、digest、ID 和 money 沿用 IBM Plex Mono/Consolas fallback。不新增字体、主题或动画体系。

## 6. 完整用户主路径

| 步骤 | 用户看见 | 用户可以 | 用户不能 | 后端权威状态 |
| --- | --- | --- | --- | --- |
| Upload | CSV/XLSX 约束、文件名/大小/type、上传与解析状态 | 选择文件、替换文件、开始上传 | 把扩展名检查当安全验证 | 尚无 Session；成功后 `MAPPING_REQUIRED` 或 `PREVIEW_READY` |
| Mapping | detected headers、8 个 canonical targets、IGNORE、source value mappings | 显式选择 source column、type、Account、Category | 映射 userId/ID/balance；自动创建 Account/Category | Session + raw file；每次成功 PUT 产生新 revision |
| Preview | backend summary、分页 rows、row errors/warnings、expiry | 翻页、跳页、展开详情、返回 Mapping、换文件 | inline edit、删行、跳过 ERROR、修改 amount 后 Confirm | immutable server PreviewPlan + revision + token |
| Warning review | backend warning code/message/row、分组确认 | 逐 warning type 显式确认；查看对应 row | 自行删除 duplicate evidence；伪造 ID | warning IDs / evidence bound to revision/token |
| Confirm | formal modal、counts、all-or-nothing、expiry、server authority notice | 以一个 intent 生成一个 key并确认 | 提交 rows；计算 balance；double submit | POST 在 Session/Account locks 内 revalidate |

## 7. Upload UX

### 7.1 文件选择

- file input `accept=".csv,.xlsx"`，支持点击选择；拖放可作为同一 input 的增强，不另建 upload architecture。
- 选择后显示本地 `File.name`、`File.size`、`File.type` 和扩展名；明确标记为“本机选择信息”。
- 轻量校验：空文件、非 `.csv/.xlsx`、明显超过 5 MiB 时在发请求前提示并禁止上传。
- CSV/XLSX 内容、MIME、OOXML 安全、行列和解压限制最终以后端为准；客户端校验不是安全边界。
- request 始终使用 `AUTO`；不提供 charset、delimiter、sheet、header row、`.xls` 或其他格式 option。

### 7.2 上传状态

状态文案必须区分：

```text
SELECTED
→ UPLOADING（可显示客户端传输进度）
→ SERVER_PROCESSING（服务端解析、安全检查与创建 Session；indeterminate）
→ MAPPING_REQUIRED | PREVIEW_READY | UPLOAD_REJECTED
```

上传/解析期间禁用再次提交。用户选择新的文件形成新 intent；旧 Session 若已创建且 ID 可知，先提供显式“放弃旧导入”，但网络中断且未收到 Session ID 时只能依赖 server TTL cleanup，不能猜测 ID。

### 7.3 文件级错误

当前 Upload/Parser 以及非 Confirm 的 Preview/Mapping/Cancel errors 多数只有 HTTP `code + message`，没有稳定 `errorCode`。前端按 HTTP 状态做粗分类并原样展示脱敏 server message：

| HTTP | UX | 下一步 |
| --- | --- | --- |
| `400` | 文件为空、malformed CSV/XLSX、编码/layout 或 XLSX security rejection | 选择/修正文件后重新上传 |
| `413` | 文件或数据行超过 backend limit | 缩小文件后重新上传 |
| `415` | 扩展名/format/MIME 不支持或不一致 | 使用真实 CSV/XLSX 后重新上传 |
| `401` | 登录失效 | 保存非金融 draft route，重新登录；没有 Confirm pending 时不保留 POST intent |
| `5xx` / network | 服务端或网络未完成 Preview | 不存在可确认 token；重新选择/上传，或在已收到 Session ID 时按 snapshot 恢复 |

Parser timeout 当前 envelope `code` 可能为 `408` 而 HTTP 被映射为 `500`；前端不能仅看 HTTP 文案猜安全原因，应优先展示 envelope message，并提供“使用更小文件重新上传”。

## 8. Mapping UX

### 8.1 Column mapping

使用一张 target-first mapping card：

| Target | 必填 | 允许操作 |
| --- | --- | --- |
| `date` | 是 | 选择一个 detected column |
| `time` | 否 | 选择 detected column 或未映射（backend default `00:00:00`） |
| `type` | 是 | 选择 detected column |
| `amount` | 是 | 选择 detected column |
| `account` | 是 | 选择 detected column |
| `category` | 是 | 选择 detected column |
| `description` | 否；`ADJUSTMENT` row 最终要求非空 | 选择 detected column 或未映射 |
| `currency` | 否 | 选择 detected column 或未映射（backend default `CNY`） |

未被 target 使用的 source column 在“忽略的列”区明确列出；提交时 wrapper 生成 `header -> IGNORE`。内部字段、balance、userId、database ID、createdAt 等只能 IGNORE。

UI 在本地阻止 required unmapped、source column 重复选择和未知 column，但 server response 仍是最终结果。duplicate header、空 header 等文件级问题由 backend 在此前已拒绝。

### 8.2 Source value discovery

当前 backend 没有 `detectedMappingValues`。为不新增 API，也不要求用户手输未知 source values，Mapping 内部采用一个受限的两次 revision 流程：

1. 用户完成 column mapping。
2. 前端 PUT 一份 column mapping 完整、value maps 可为空的 mapping，生成一个 non-confirmable discovery revision。
3. 使用 rows endpoint 以 `size=500` 顺序读取最多 20 页；只提取 mapped `type/account/category` source values 和 row-level message metadata。
4. source key 按与 backend 相同的 Unicode NFC + trim 规则仅用于 UI 去重；保留代表性原文用于展示。
5. 处理完一页后立即丢弃该页完整 `sourceValues/normalizedValues`，不写入 persistent storage。
6. 用户完成 type / Account / Category mapping 后再次 PUT，生成正式 Preview revision；discovery token 和 warning IDs 立即作废。

该 scan 只建立 mapping UI 索引，不创建客户端 financial plan，也不参与 Confirm payload。scan 失败时停留 Mapping，允许重试 GET；Session expiry 时重新上传。

### 8.3 Type mapping

- 每个 normalized source type value 显式映射为 `INCOME`、`EXPENSE` 或 `ADJUSTMENT`。
- source value 恰好等于 canonical enum 时可以预填 deterministic suggestion，但仍显示并要求用户保存；不做 AI/locale 猜测。
- 未映射或 unsupported value 保持错误，不能静默替换。

### 8.4 Account mapping

- options 只来自当前 JWT 用户的 `GET /accounts` response；UI 默认只提供 `status=ACTIVE && currency=CNY` 的 Account。
- value 使用 Account ID，label 显示 `name · type · CNY · #id`，duplicate name 不构成客户端歧义。
- 不提供 ID 自由输入，不自动创建 Account，不根据 source name 静默匹配。
- 选择只是 mapping intent；ownership、ACTIVE、CNY 和最终余额仍由 Preview/Confirm backend revalidate。

### 8.5 Category mapping

- options 只来自 `GET /categories` 的当前 backend-visible list；value 使用 Category ID，不提供 ID 自由输入。
- source category 只出现在 mapped `INCOME` rows 时显示 INCOME categories；只出现在 mapped `EXPENSE` rows 时显示 EXPENSE categories；只用于 `ADJUSTMENT` 时两类都可选。
- 同一 normalized source category 若同时用于 `INCOME` 与 `EXPENSE`，当前 `categoryMappings[sourceValue] -> one ID` 无法表达两种 target。UI 必须明确要求用户修改源文件使 source values 可区分并重新上传；不得按行私自覆盖 mapping。
- 不自动创建 Category。若当前无可用 Category，Import 保持 blocked，并说明必须先准备后端可见 Category。

## 9. Preview UX

### 9.1 采用的布局

```text
┌ Summary: 总行 / 有效 / 警告行 / 错误行 ┐
│ expiry + revision + confirmability       │
├ Issue navigator: 首个错误 / 首个警告     ┤
├ Server-paged row table (100/page)         ┤
│ row # | status | date | type | amount ... │
│                         [展开详情]         │
├ page / total pages / jump / prev / next   ┤
└ actions: 修改映射 | 更换文件 | 继续复核  ┘
```

- 使用 4 张 summary cards：`totalRows`、`validRows`、`warningRows`、`errorRows`；`importableRows` 在确认区域显示。
- `duplicateCandidates` 只可标为“重复风险行”，不得称为匹配到的 existing transaction 数量。
- 不使用全局 tabs 或 status filters；当前 API 无 server filtering，过滤单页会制造错误的全局语义。
- metadata hydration 可保存 issue 的 row number、message、warning ID 与其 ordinal page locator，支持“跳到首个/下一个问题”；不保存完整 row。
- visible table 固定 `size=100`；总页数由 backend `summary.totalRows` 计算。除上一页/下一页外增加页码跳转，避免 10,000 rows 时逐页点击。

### 9.2 Row primary columns

桌面首层只显示：source `rowNumber`、派生显示 status、date/time、type、amount、mapped Account label、mapped Category label、description 摘要、duplicate chip、详情按钮。

- amount 使用 backend `normalizedValues.amount` string 原样格式化，不转 `Number`。
- Account/Category label 来自当前 mapping + option snapshot，只是显示上下文；后端 mapping ID 和 Confirm revalidation 才有权威性。
- description 及所有 source text 按 text node render；不得使用 `dangerouslySetInnerHTML`。

展开详情显示：

- source values；
- backend normalized values；
- errors / warnings 的 code、field、rowNumber、message；
- `mappingStatus`、`duplicateStatus`、`importable`。

不显示 token、digests 的内部 claims、candidate IDs（当前 response 未提供）或客户端计算结果。

### 9.3 Error rows

- 任一 `errors[]` 或 `summary.errorRows > 0` 时 Confirm disabled。
- 首版不支持“导入有效行”“排除当前行”或 inline edit。
- Mapping/Account/Category error：回到 Mapping，PUT 新 mapping，得到新 revision/token。
- amount/date/description/source content error：明确提示修正源文件并重新上传。
- 前端不得修改 row 后直接 Confirm；任何 correction 都必须重新走后端 Mapping/Preview。

当前 row-level code 必须按 backend `field + code + message` 展示，不根据 code 在客户端重跑校验：

| Actual code | 当前 field / UX route |
| --- | --- |
| `INVALID_TRANSACTION_TYPE` | `type`；补齐 type mapping 或修正源文件 |
| `INVALID_AMOUNT` | `amount`；修正源文件 |
| `INVALID_DATE` | `date` 或 `time`；以 `field` 区分后修正源文件 |
| `UNSUPPORTED_CURRENCY` | `currency` 或 `account`；以 `field` 区分，修正源文件或 Account mapping |
| `MISSING_REQUIRED_FIELD` | 当前用于 `ADJUSTMENT` 的 `description`；修正源文件 |
| `ACCOUNT_NOT_MAPPED` | 返回 Account mapping |
| `ACCOUNT_NOT_FOUND` | 当前用户不可见或不存在；返回 Account mapping |
| `ACCOUNT_INACTIVE` | 改选 ACTIVE Account |
| `CATEGORY_NOT_MAPPED` | 返回 Category mapping；也可能表示 target 已不再可见 |
| `CATEGORY_TYPE_MISMATCH` | 改选与 transaction type 兼容的 Category |

`IN_FILE_PROBABLE` 与 `DATABASE_PROBABLE` 是 warning，不归入 error row；未知 code 仍按 backend severity/message 呈现并 fail closed，不将其降级为 valid。

当前 backend 实际共有 **11 个 unique row code**：上表 9 个 error code，加上 2 个 warning code；不存在第 12 个已实现 code。`INVALID_DATE` 可分别以 `field=date/time` 出现，`UNSUPPORTED_CURRENCY` 可分别以 `field=currency/account` 出现，但它们不是新的 code。Frontend 必须覆盖全部 11 个真实 code 与对应 field 分支，不得为满足数量描述而虚构 code。

### 9.4 Metadata hydration gate

正式 Preview 到达后，前端以 `size=500` 顺序扫描 rows，只保留 warning/error metadata。Confirm 还需满足：

- scan 覆盖 `summary.totalRows`；
- observed error-row / warning-row counts 与 summary 一致；
- warning ID 均非空且同 revision 内无异常冲突；
- snapshot revision/token 在 scan 期间未被本 tab 替换。

任一条件不满足只表示客户端尚不能安全构造 acknowledgement；UI 显示“预览元数据尚未完整加载”，允许重新 scan，zero Confirm。客户端检查不是 backend security boundary。

## 10. Warning UX

### 10.1 展示与显式 acknowledgement

当前 warning 主要为：

- `IN_FILE_PROBABLE`：上传文件内可能重复；
- `DATABASE_PROBABLE`：与当前用户已有普通流水可能重复。

Warning review 按 backend code 分组；当前两个具名分组如下。每组显示 warning row 数、逐 row 的 normalized business fields 与 backend message，并提供一个独立 checkbox：

```text
[ ] 我已复核“文件内可能重复”的 N 项警告，仍要保留这些流水
[ ] 我已复核“与已有流水可能重复”的 M 项警告，仍要导入这些流水
```

checkbox 只把该组当前 revision 的 backend warning IDs 加入内存 acknowledgement set；取消勾选即移除。全部 required warning groups 显式确认后才可进入 Confirm modal。

Confirm body 的 `acknowledgedWarningIds` 必须由 hydration 得到的 backend IDs 去重并按字典序冻结；不得根据 row number/code 自行生成 ID，不发送额外 ID，不发送 warning object 或 duplicate evidence。

若后端在当前 contractVersion 下返回未知 warning code，UI 仍以独立“其他服务端警告”分组展示原 code/message 并要求显式确认，绝不自动 acknowledgement 或降级为 valid。ack 集合以 `warnings[]` 为准；`duplicateStatus` 只是单个显示字段，不能替代可能同时存在的多个 warning evidence。

### 10.2 Evidence drift

首次 Confirm 返回：

- `IMPORT_DUPLICATE_EVIDENCE_CHANGED`；或
- 由 authoritative state 变化导致的 `IMPORT_PREVIEW_STALE`

时，UI 必须：

1. 明确显示“本次未完成导入；重复证据或预览依据已变化”；
2. 清空当前 warning acknowledgement 和首次 attempt 的 pending marker；
3. 禁用旧 token 的 Confirm；
4. 提供用户触发的“重新生成预览”，用当前 mapping PUT 创建新 revision；
5. 重新 hydration、重新展示 warnings、重新显式确认；
6. 下一次真正 Confirm 才生成新 idempotency key。

绝不自动重试 Confirm。candidate added、removed、changed、stale/forged warning 都走同一 re-preview 用户路径。

`IMPORT_WARNING_ACK_REQUIRED` 在首次 attempt 中表示 request 未满足当前 frozen plan：返回 warning review、重新 hydration/确认；不篡改 ID。在已经进入 `OUTCOME_UNKNOWN` 的 recovery 中收到任何 4xx 都不能反推更早 attempt 未提交，仍保持 unknown，见第 14 节。

## 11. Preview Token 与 draft persistence

### 11.1 Token rules

前端对 `previewToken` 只执行：

- 从 `PREVIEW_READY` response 接收；
- 作为 opaque string 保存在当前 snapshot；
- 在 Confirm exact body 中原样提交；
- revision 更改、stale、cancel 或明确 expiry 后废弃。

前端不得 decode、读取 claims、生成、修改、重签、写入日志、显示给用户或放入 URL。

`expiresAt` 只用于倒计时和提前阻止明显过期的首次 Confirm；本机时钟不是权威。倒计时到期显示“预览可能已过期”，首次 Confirm disabled，最终仍以后端 response 为准。

### 11.2 Same-tab draft snapshot

Upload 成功后将最小 draft 写入 `sessionStorage`：

```text
finance-os:transaction-import:draft:v1:{userId}
```

允许字段：schemaVersion、userId、active step、client file display metadata、sessionId、batchId、sessionStatus、revision、detectedColumns、mapping、summary、four public digests、expiresAt、previewToken、acknowledged group state、updatedAt。

禁止保存 JWT、完整 Preview rows、source file bytes、receipt、account balances、client-computed amount/delta 或 decoded token claims。

页面刷新/浏览器 Back 后重新进入时：

1. runtime validate snapshot schema、user binding、UUID、status、revision、expiry 和 token presence rules；
2. pending Confirm record 存在时，pending recovery 优先于 draft；
3. `PREVIEW_READY` 通过 GET rows 重新加载当前页并重新 hydration；
4. `MAPPING_REQUIRED` 可恢复 detected columns 与 mapping draft，用户继续 PUT 时由 backend 判断 Session 是否仍可用；
5. `404/409`、expiry 或 snapshot invalid 时显示“此预览无法恢复”，只提供重新上传；不生成 token、不猜 Session state。

当前没有 Preview Session GET endpoint。没有有效 sessionStorage snapshot、换 tab 或浏览器关闭后，首次 Confirm 前的 Mapping/Preview **不能完整恢复**；UI 必须诚实地开始新上传。已经发出 Confirm 的 intent 使用下一节 localStorage record，不受这一限制。

## 12. Confirm UX

### 12.1 Formal confirmation modal

复用 Investment command modal 的 focus trap、Escape/busy 规则、移动端 bottom sheet 和 sticky footer，不使用 `window.confirm`。

modal 至少显示 backend Preview fields：

- total rows；
- valid rows；
- warning rows；
- error rows（必须为 0）；
- importable rows；
- server expiry；
- all-or-nothing 说明。

当前 Preview API 没有 authoritative affected-account summary、balance delta 或 final balance。modal 因此不得显示预计 delta/final balance。可以把 mapping 选择的 Account names 作为“目标映射上下文”列出，但必须明确它不是后端 account-impact receipt。

主按钮使用完整动作文本：`确认导入 {importableRows} 条流水`。进入 modal、返回 Preview、勾 warning 或 render 都不生成 key；只有真正点击该按钮后才 claim intent。

### 12.2 Confirm 不变量

- `confirmable === true`；
- `summary.errorRows === 0`；
- metadata hydration 完成；
- acknowledged IDs 与 hydrated required IDs 完全一致；
- snapshot revision/token 未变化；
- 当前用户没有 unresolved Import pending record；
- 浏览器支持 Web Locks；
- localStorage 可以同步写入 pending record。

任一条件失败：zero POST。

## 13. Idempotency-Key 与 pending record

### 13.1 One intent → one key

首次真正 Confirm 的固定顺序：

```text
sort/dedupe backend warning IDs
→ 构造 exact bodyJson
→ 取得 user-scoped Web Lock
→ 重新扫描并 runtime-validate当前用户 pending namespace
→ 确认没有 pending 且 snapshot 未变
→ crypto.randomUUID() 生成一次 key
→ 同步写 localStorage SUBMITTING record
→ 写入成功后释放 lock
→ 用 exact path/key/bodyJson POST
```

localStorage 写失败或 Web Locks unavailable 时不发送请求。double-click、Enter 重复触发、另一个 tab 同时确认均只能产生一个 record 和一个 POST。

### 13.2 Storage contract

```text
storage key:
finance-os:transaction-import:pending:v1:{userId}:{idempotencyKey}
```

```ts
interface PendingTransactionImportV1 {
  schemaVersion: 1
  userId: number
  state:
    | 'SUBMITTING'
    | 'OUTCOME_UNKNOWN'
    | 'RECOVERING_LOOKUP'
    | 'RECOVERING_CONFIRM'
    | 'COMMITTED_AWAITING_RECEIPT'
    | 'AUTH_REQUIRED'
  resumeState?:
    | 'SUBMITTING'
    | 'OUTCOME_UNKNOWN'
    | 'COMMITTED_AWAITING_RECEIPT'
  method: 'POST'
  path: string
  importSessionId: string
  importBatchId: string
  idempotencyKey: string
  bodyJson: string
  submittedAt: string
  updatedAt: string
}
```

`bodyJson` 必须是首次发送的 exact serialized `{previewToken, acknowledgedWarningIds}`。恢复直接复用 bytes，不从 UI checkbox、rows 或 draft 重新序列化。Authorization 每次由当前 Axios interceptor 注入，不保存 JWT。

runtime validation 至少检查：schema/state allowlist、current user、storage-key suffix、UUID、key 1–100/trim、exact method/path、body closed fields、nonblank token、string warning ID array、state/resumeState 合法组合。invalid record 不得 POST、不得自动修复或删除；派生只读 `RECOVERY_RECORD_INVALID`，可导出 raw evidence 后转人工处理。

### 13.3 Multi-tab lock

锁名：

```text
finance-os:transaction-import-confirm:v1:{userId}
```

当前用户只允许一个 unresolved Import confirm intent。其他 session 可以在 server 存活，但 UI 在 pending 解决前禁止新 Upload/Confirm，避免用户用新 key 绕过 unknown outcome。监听 `storage` event，在其他 tab 写入/清理 pending 时同步显示 recovery banner。

Web Lock、`storage` event 和 UI disable 只用于减少重复操作与协调展示，不是金融 correctness boundary。即使 tab 崩溃、事件丢失或锁在请求后释放，正确性仍只依赖 backend Session revision/row lock、opaque token、warning evidence、exact-duplicate guard 与 idempotency contract；frontend lock 不得被描述为阻止重复金融写入的唯一保障。

## 14. Confirm / Recovery 状态机

### 14.1 Authority 分层与完整外层状态

| 层级 | 状态 | Authority |
| --- | --- | --- |
| frontend transient | `SELECTED`、`UPLOADING`、`SERVER_PROCESSING`、`DISCOVERING_VALUES`、`HYDRATING_METADATA`、`CONFIRMING`、`SUBMITTING`、`RECOVERING_*`、`AUTH_REQUIRED` | 只描述 UI/request progress；refresh 后不得当作 server truth |
| backend Session | `MAPPING_REQUIRED`、`PREVIEW_READY`、`CANCELLED`、`EXPIRED`、`CONSUMED` | 只有 backend transition/response 有权威性；snapshot 只是 identity/cache |
| committed terminal | Batch/Receipt `CONFIRMED` | 只接受 Confirm `200` 或 Receipt GET `200`；React memory/storage 都不是金融真值 |

外层 flow 冻结为：

```text
NO_SESSION
  → SELECTED → UPLOADING → SERVER_PROCESSING
  → MAPPING_REQUIRED
       → DISCOVERING_VALUES → PREVIEW_READY(non-confirmable discovery revision)
       → mapping completed → PREVIEW_READY
  → HYDRATING_METADATA → PREVIEW_REVIEW
       ├─ mapping changed → PREVIEW_READY(new revision; clear token/ack/index)
       ├─ explicit Cancel 200 → CANCELLED
       ├─ authoritative expiry/error → EXPIRED | REPREVIEW_REQUIRED
       └─ warnings complete → CONFIRMING
  → SUBMITTING → OUTCOME_UNKNOWN | CONFIRMED | definite rejection
  → CONFIRMED → receipt route → RECEIPT
```

`CANCELLED`、`EXPIRED` 和 `CONSUMED` 不能由 disabled button、local timeout、snapshot 或 React state自行推断。`CONSUMED` 只通过 authoritative receipt 投影为 UI 的 `CONFIRMED/RECEIPT`；`UNKNOWN_OUTCOME` 永远不能降级为普通 `FAILED`。

### 14.2 Confirm / recovery 子状态机

```text
PREVIEW_REVIEW
  └─ warnings complete → CONFIRMING
       ├─ back → PREVIEW_REVIEW
       └─ claim exact intent → SUBMITTING
            ├─ 200 + valid authoritative receipt → receipt route → RECEIPT + clear pending
            ├─ 200 but receipt cannot be accepted → COMMITTED_AWAITING_RECEIPT
            ├─ first-attempt definite reject → REJECTED / REPREVIEW_REQUIRED
            ├─ 401 → AUTH_REQUIRED(resume=SUBMITTING)
            └─ network / timeout / 5xx / lock conflict → OUTCOME_UNKNOWN

OUTCOME_UNKNOWN
  └─ 用户“查询并恢复原确认” → RECOVERING_LOOKUP
       ├─ GET batch 200 + session/batch match → receipt route → RECEIPT + clear pending
       ├─ GET batch 404 → RECOVERING_CONFIRM
       │                    ├─ same POST/key/body 200 + valid receipt → receipt route → RECEIPT + clear pending
       │                    ├─ 200 but receipt cannot be accepted → COMMITTED_AWAITING_RECEIPT
       │                    ├─ 401 → AUTH_REQUIRED(resume=OUTCOME_UNKNOWN)
       │                    └─ any non-200/unresolved → OUTCOME_UNKNOWN
       ├─ 401 → AUTH_REQUIRED(resume=OUTCOME_UNKNOWN)
       └─ network / 5xx → OUTCOME_UNKNOWN

COMMITTED_AWAITING_RECEIPT
  ├─ GET batch 200 + session/batch match → RECEIPT + clear pending
  ├─ 401 → AUTH_REQUIRED(resume=COMMITTED_AWAITING_RECEIPT)
  └─ GET failure → remain GET-only; never POST
```

reload 规则：

- persisted `SUBMITTING`、`RECOVERING_LOOKUP`、`RECOVERING_CONFIRM` 一律显示为 `OUTCOME_UNKNOWN`；浏览器无法知道中断前请求结果。
- `COMMITTED_AWAITING_RECEIPT` 只允许 GET。
- `AUTH_REQUIRED` 保留合法 resumeState；同 user 重新登录后仍需用户点击对应恢复动作。
- 不存在 pending 记录时不得从 draft 推导一个已发送的 Confirm。

401 resume 规则：首次 Confirm 收到 authenticated request 的 `401` 时，request 尚未进入 Import controller，`AUTH_REQUIRED(resume=SUBMITTING)` 在同 user 重新登录后由用户触发 exact same path/key/body POST；已经处于 `OUTCOME_UNKNOWN` 的恢复流程遇到 `401` 时，恢复为 `OUTCOME_UNKNOWN` 并仍从 GET batch 开始；Receipt GET 的 `401` 恢复为 `COMMITTED_AWAITING_RECEIPT`，只允许 GET。三者均不得生成新 key。

pending 只在两类条件下清理：已验收的 authoritative receipt 已进入 receipt route；或首次 attempt 收到 matrix 明确列出的 definite non-commit rejection，并已转入终止/re-preview UI。`IMPORT_IDEMPOTENCY_CONFLICT` 保留证据等待人工处理，`IMPORT_BATCH_ALREADY_CONFIRMED` 保留到 GET reconcile，任何 `OUTCOME_UNKNOWN` 分支永不清理或换 key。

Confirm `200` 的 receipt 通过 lossless decode 与 runtime validation 后应直接展示，同时先把 route 切换到可刷新的 receipt URL，再清 pending；它已经是 authoritative receipt，不要求额外 GET 才能成立。只有 response 已明确为 `200`、但 receipt body 无法安全接收时，才先持久化 `COMMITTED_AWAITING_RECEIPT` 并进入 GET-only reconcile。

`idempotentReplay=true` 显示“已恢复原确认，未重复导入”；`false` 显示“导入已确认”。两者 receipt authority 相同。通过 GET batch 找回 receipt 时没有该 flag，只显示“已找到已提交的权威回执”，不得推测 replay 值。

## 15. Error / Recovery Matrix

分支必须优先使用当前实现真实 `errorCode`，不得只按旧设计稿中未实际返回的名称分支。

| 场景 / actual code | 首次 Confirm | 已进入 unknown 后的 recovery | 用户动作 |
| --- | --- | --- | --- |
| `400 IMPORT_CONFIRM_REQUEST_INVALID` | definite reject；zero commit | 仍 unknown | 首次回 Preview 修正；recovery 保留原 record |
| `404 IMPORT_SESSION_NOT_FOUND` | definite reject | 仍 unknown | 首次重新上传；recovery 继续 GET batch，不换 key |
| `409 IMPORT_PREVIEW_EXPIRED` | definite reject | 仍 unknown | 首次重新上传；recovery 保留证据 |
| `409 IMPORT_SESSION_CANCELLED` | definite reject | 仍 unknown | 首次结束；recovery 保留证据 |
| `409 IMPORT_PREVIEW_STALE` | definite rollback / re-preview | 仍 unknown | 首次用户触发新 Preview；不自动 POST |
| `409 IMPORT_PREVIEW_UNAVAILABLE` | definite reject / re-preview | 仍 unknown | 首次用当前 mapping 重新 Preview；若 Session 不可用则重新上传 |
| `409 IMPORT_DUPLICATE_EVIDENCE_CHANGED` | definite rollback / re-preview | 仍 unknown | 首次重新 Preview 并重审 warnings；不自动 POST |
| `409 IMPORT_WARNING_ACK_REQUIRED` | definite reject | 仍 unknown | 首次重新 hydration/ack；不伪造 IDs |
| `409 IMPORT_EXACT_DUPLICATE` | 当前 session 未写入 | 仍 unknown | 首次提示 exact batch 已存在；当前 error 未返回 prior batch ID，不能虚构 receipt link |
| `409 IMPORT_BATCH_ALREADY_CONFIRMED` | 当前 batch 已有结果或 intent 冲突 | 仍先 GET | 用本地 preallocated batchId GET；200 展示 receipt |
| `409 IMPORT_IDEMPOTENCY_CONFLICT` | 当前 request 未写入，但 key 已被别的 intent 占用 | 仍 unknown | fail-closed；保留/export evidence，不自动换 key |
| `409 IMPORT_LOCK_CONFLICT` | outcome 视为 unknown | unknown | GET batch → same-key recovery |
| `500 IMPORT_CONFIRM_INCONSISTENT` | unknown | unknown | GET batch；保留 evidence；不新建 intent |
| generic `503` / `500` / timeout / reset | unknown | unknown | GET batch → same-key recovery |
| `401` | pending 先持久化 AUTH_REQUIRED；token 清除 | 同左 | 同 user 登录后用户继续原动作 |

Receipt lookup 的实际 `404 IMPORT_BATCH_NOT_FOUND` 有两种上下文：unresolved pending 的首次 GET 404 才进入 exact same POST/key/body recovery；普通 receipt URL 在没有 pending evidence 时只显示“回执不存在或不可见”，绝不据此构造 Confirm。

一旦进入 `OUTCOME_UNKNOWN`，后续 recovery 的 4xx/409 只描述 recovery attempt，不能证明更早 attempt 没有 commit。因此 record 不清理、token/body 不修改、新 key 不生成。

Confirm pending 存在时禁止 Cancel Session。DELETE 可能与 in-flight Confirm 竞争，前端不得用“放弃”替代 reconcile。

## 16. Receipt UX

### 16.1 Authority 与展示

receipt page 只接受：

- Confirm `200` 中的 backend receipt；或
- `GET /batches/{importBatchId}` 重建的 backend receipt。

默认展示：

1. 成功/恢复 banner；
2. `sourceFileName`、`confirmedAt`、status；
3. total / accepted / created / skipped / warning counts；
4. Account Impacts：account ID、row count、`balanceBefore`、`delta`、`balanceAfter`；
5. source row → created transaction ID；
6. `importBatchId`、`contractVersion`、`resultDigest`、`fileDigest` 的 audit detail / copy controls。

Account name 可以由当前 `GET /accounts` 作“当前名称”辅助 join，但 ID 和 receipt values 必须始终显示；账户后续改名不能改写历史 receipt。找不到当前 Account 时显示 `Account #id`，不隐藏 impact。

`transactions[]` 最多 10,000 项。receipt endpoint 当前一次返回完整数组；UI 只做 display pagination/折叠，不把它重新提交或持久化为 truth。

### 16.2 禁止重算

前端不得：

- 从 Preview rows 计算 createdCount；
- 求和 row amounts 得出 delta；
- 用当前 Account.balance 反推 balanceBefore；
- 验证或重新生成 `resultDigest` 后才决定是否相信 receipt；
- 用 `idempotentReplay` 改写 immutable receipt。

可以做的只有 runtime shape validation、receipt session/batch ID 与 pending target 一致性检查、`resultDigest` 格式检查、lossless display 和 copy。pending 没有预存权威 digest，前端不得假装“验证”其内容；只有已经接受过同一 receipt 时，后续 GET/replay 才可把 digest 作为 opaque value 比较相等性。

## 17. Browser navigation、refresh、Cancel 与 401

### 17.1 Browser Back / route change

- 内部“上一步”只改变同 route UI state，不调用 browser history。
- browser Back 离开 Import 时不自动 DELETE Session；sessionStorage snapshot 保留，重新进入时尝试恢复。
- 用户显式“放弃本次导入”且没有 pending Confirm 时，确认后调用 DELETE；只有 DELETE `200` 才直接进入 `CANCELLED` 并清理 draft。
- DELETE `409` 的当前 API 没有稳定 terminal state/errorCode，不能直接当作“已取消”。若 snapshot 有 preallocated `batchId`，先 GET receipt：`200` 进入 Receipt；`404` 后才把该 Session 视为不可继续并清 draft。`MAPPING_REQUIRED` 尚无 response batch identity，DELETE `409` 只能显示 Session 不可继续并清 draft，不得声称具体是 cancelled/expired/consumed。
- DELETE network/timeout/`5xx` 是 cancel outcome unknown：保留 draft，先用已知 batch identity GET receipt；未找到 receipt 时允许用户重试同一 DELETE。不得自动创建 Session 或把本地按钮状态当 authoritative Cancel 结果。
- `SUBMITTING/OUTCOME_UNKNOWN/RECOVERING/COMMITTED_AWAITING_RECEIPT` 时不提供 Cancel；离页/关闭 tab 触发 `beforeunload` warning，但安全性依赖 persistent record，不依赖用户留在页面。

### 17.2 401

继续复用单一 Axios instance。在 global 401 清 token/redirect 前，Import request config 提供与现有 Investment command 相同的 pre-redirect persistence hook：

- Upload/Mapping/rows GET：保存 return target 与可恢复 draft，不创建 pending financial intent；
-首次 Confirm/recovery POST：原子写 `AUTH_REQUIRED + resumeState`；
- receipt GET：写 `AUTH_REQUIRED + COMMITTED_AWAITING_RECEIPT`，保持 GET-only。

Login 继续以 response userId 写 `finance-os:auth-user-id:v1`。同 user 登录后回到 Import recovery target；不同 user 只扫描自己的 namespace，不删除或显示其他 user record。JWT 从不写入 Import draft/pending record。

### 17.3 Logout

显式 Logout 与被动 `401` 必须分开处理：

- 被动 `401` 按 17.2 保留最小 pending，供同 user 重新认证后恢复；它不是一次已完成的显式 Logout。
- 显式 Logout 前扫描当前 user 的 Import namespace。存在 unresolved Confirm 时必须阻止完成 Logout，并把用户带到 recovery UI；不得提供“继续退出但把 previewToken/idempotency intent 留在 localStorage”的旁路，也不得清掉 key 后让 outcome 永久未知。
- 没有 unresolved Confirm 后，Logout 必须清除当前 user 的 draft Session identity、previewToken、warning acknowledgement、issue index、idempotency intent record、任何 receipt/UI cache 与 return target，再清 JWT 与 auth user ID。
- 清理只针对当前 authenticated user 的 namespace；Login 后也只扫描当前 response userId。User A 完成显式 Logout 后，User B 不得看到、加载或恢复 A 的 Import state。

当前设计不持久化 receipt；若实现阶段增加任何 receipt cache，必须放在上述 Logout 清理范围内，且仍不得作为 financial truth。

## 20. Future implementation test contract

### 20.1 API / mapping

- multipart part names、JSON Blob content type、`AUTO`、relative paths 与 1-based page 参数准确。
- required/optional/IGNORE、duplicate source column、normalized source-key collision。
- discovery revision 对 1、100、101、10,000 rows 分别产生正确 bounded GET 数，处理后不持久化完整 rows。
- source category 跨 INCOME/EXPENSE conflict fail closed。
- Account options 只来自 current backend response；不允许自由输入/foreign ID。

### 20.2 Preview / warning

- summary counts 完全使用 backend response；ERROR 永远禁用 Confirm。
- warning 在 page 1 之外仍被 hydration 收集；两种 warning group 分别显式 ack。
- acknowledged body 只含 sorted distinct backend IDs。
- mapping revision 后旧 token、旧 ack 和旧 issue index 被清空。
- duplicate evidence added/removed、`IMPORT_DUPLICATE_EVIDENCE_CHANGED`、stale/forged warning 均 zero automatic retry 并进入 re-preview。
- XSS-like description/source values 只作为 text render。

### 20.3 Idempotency / recovery

- opening modal、typing、ack、render 均 zero key；真正 Confirm one intent → one UUID。
- double-click/Enter → one pending record + one POST。
- two tabs → Web Lock winner only；loser zero key/zero POST；storage event 可见。
- Web Locks unavailable 或 localStorage write failure → zero POST。
- pending exact `bodyJson` 保留 token/warning IDs；recovery path/key/body bytes 不变。
- reload `SUBMITTING/RECOVERING_*` → `OUTCOME_UNKNOWN`；COMMITTED marker → GET-only。
- unknown recovery 固定 GET batch；404 后才 same POST。任何 recovery non-200 保持 unknown。
- first-attempt evidence-changed 允许用户 re-preview；unknown attempt 的相同 409 不清 pending。
- Confirm pending 时 Cancel button 不存在且 zero DELETE。
- 401 的三种 resumeState、same-user login、different-user namespace、logout preservation。
- invalid pending JSON/schema/user/key/path/body/state 保留 raw evidence且 zero POST。
- `IMPORT_IDEMPOTENCY_CONFLICT` fail closed，保留 evidence，不换 key、不自动 POST。
- DELETE `409` 先 receipt reconcile；DELETE network/timeout 不得直接显示 cancelled。
- 显式 Logout 在 unresolved pending 时被阻止；完成 Logout 后当前 user Import storage 为零；被动 401 仍可 same-user resume。

### 20.4 Money / receipt

- raw JSON number `9999999999999999.99`、`-0.01`、`9999999999999999.98` 经 lossless adapter 保持 exact decimal lexeme。
- 测试必须证明 Axios adapter 在标准 `JSON.parse` 前取得 raw response text，并由 lossless parser 解析完整 `ApiResponse`；禁止 `response.json()/response.data object → String(value)` 的伪保真路径。
- 若 backend 返回 string，同一 adapter 保持原 string；科学计数法、NaN/Infinity、unsafe JS number 均 fail closed。
- receipt、replay、GET 的 batch ID/resultDigest 一致；不在客户端重算 digest。
- account impacts 按 backend order/value display；Account rename/missing 不改历史 money。
- 10,000 transaction references 使用 display pagination，不写回 request。

### 20.5 UX / E2E

- CSV/XLSX happy path：Upload → Mapping → Preview → Confirm → GET receipt。
- malformed、unsupported、oversize、XLSX security rejection。
- row errors、warning acknowledgement、expired/stale/cancelled。
- duplicate evidence changed、idempotency conflict、Cancel-vs-Confirm reconciliation。
- committed response lost：pending unknown → GET/retry → same receipt，无第二个 POST intent。
- Confirm/recovery/receipt GET 三种 `401` resume path、显式 Logout block/cleanup、User A → User B isolation。
- receipt refresh route、browser Back、same-tab refresh、no-snapshot cannot-restore。
- stale/multi-tab path：frontend coordination 失效时 backend 仍保证只存在一个 committed Batch/effect。
- modal focus trap/return focus、keyboard-only、screen reader status、375px layout、reduced motion。
- frontend `npm test`、lint、build 与 Import E2E；后端已有 121 suites / 641 tests 是基线证据，不替代前端状态机/E2E。

## 22. 当前 API 限制与设计处理

| 当前限制 | 本设计处理 | 不得假装 |
| --- | --- | --- |
| 无 `detectedMappingValues` | Mapping 内部 bounded row metadata scan | 不声称 server 已直接返回 distinct values |
| 无 top-level warning ID set | 正式 Preview hydration 只保留 warning metadata | 不只确认第一页 warnings |
| 无 Preview Session GET | sessionStorage same-tab restore；无 snapshot 时重新上传 | 不承诺 browser restart 前置流程恢复 |
| rows API 无 filter/total page object | summary 计算 pages；不做全局 tabs/filter | 不把当前页 filter 叫全局结果 |
| Preview 无 affected-account summary | Confirm modal 不显示 delta/final balance | 不从 rows 自算 account impacts |
| Preview 无 server file display object | 上传阶段显示 client File metadata；receipt 显示 server filename | 不把 client filename 当 receipt |
| actual exact-duplicate error 无 prior batch ID | 明确冲突但无 receipt link | 不猜 existingBatchId |
| Import parse errors 多数无 stable errorCode | HTTP coarse category + server message | 不按英文 message 建业务状态机 |
| actual Confirm error names与旧 draft 有差异 | 使用 `IMPORT_EXACT_DUPLICATE`、`IMPORT_LOCK_CONFLICT`、`IMPORT_DUPLICATE_EVIDENCE_CHANGED` | 不分支到未返回的旧名称 |
| receipt money 当前为 JSON number | raw-text lossless adapter → DecimalText | 不经过 JS Number |

上述限制均不授权本轮修改 backend。若未来实现不接受这些降级/adapter，必须停止 frontend implementation 并另行评审 API contract，不能在组件中偷偷补金融真值。
