# V3.0 Transaction Import Frontend — Sub-phase C Review

**Status: GO — Ready for Independent Re-Review**

This closes **Frontend Sub-phase C only**. It does not close the entire Transaction Import Frontend and does not authorize Sub-phase D.

## Scope and decision

Sub-phase C adds the final confirmation, durable pending-confirm recovery, authoritative receipt route, lossless receipt transport, and confirm-modal accessibility behavior for the transaction-import frontend.

The remediation candidate is **GO — Ready for Independent Re-Review**. The final gate has `P0 = 0` and `P1 = 0`; this document does not claim independent verification.

## Closing history retained

### NO-GO 1 — coverage was incomplete

The core implementation was initially not ready to close because the domain matrix, four 401 paths, logout, user switch, multi-tab behavior, and modal focus handling did not all have complete automated evidence. Closing was blocked until those gaps were covered by automated unit/component and browser tests.

### NO-GO 2 — fallback POST 401 recovery was unsafe

The fallback path previously degraded as follows:

```text
OUTCOME_UNKNOWN → extra Receipt GET
```

The final behavior is instead:

```text
POST unknown → Receipt GET 404 → fallback POST 401 → same-user auth → same fallback POST
```

The state is persisted as `RECOVERING_CONFIRM`; recovery resumes the exact frozen fallback POST, without an additional Receipt GET. Browser evidence asserts `GET → POST → POST`, one idempotency key, one path, and byte-identical `bodyJson`.

### Final closing correction — rejected initial Confirm could rehydrate a stale token

During this closing review, the new domain-error browser matrix found that clearing a rejected initial Confirm could allow the draft-restoration effect to restore the earlier confirmable snapshot. The final implementation clears that user's import draft and invalidates the in-memory preview token before removing the pending record. `IMPORT_SESSION_NOT_FOUND` returns to upload; terminal and re-preview actions remain non-confirmable. This prevents a rejected intent from being silently made confirmable again.

### NO-GO 3 — committed state was not monotonic

An independent closing review found three P1 issues after the earlier C closure:

- **P1-1:** Confirm transport discarded an HTTP 200 fact when lossless receipt decoding failed. The decoder surfaced an ordinary error, so the coordinator incorrectly entered `OUTCOME_UNKNOWN`.
- **P1-2:** `COMMITTED_AWAITING_RECEIPT` Receipt GET failures called `markUnknown()`. A subsequent 404 could then reopen the fallback POST path.
- **P1-3:** The fresh full domain matrix waited for a pre-existing alert and heading rather than for its Confirm request, so its `IMPORT_SESSION_NOT_FOUND` request-count assertion raced the actual request.

The remediation keeps Confirm transport status separate from receipt decoding. HTTP 200 with an absent or malformed receipt now persists `COMMITTED_AWAITING_RECEIPT`, then performs authoritative Receipt GET recovery only. While in that state, 404, network failure, malformed Receipt GET, and retryable failures retain the same committed record; 401 resumes the same GET after same-user authentication. Startup, remount, and storage scanning keep that persisted state unchanged. `OUTCOME_UNKNOWN` remains separate: its Receipt GET 404 still permits the exact frozen fallback POST.

Successful receipt handling now navigates to the durable batch-id Receipt URL before clearing the pending record and draft. Receipt contents are still never persisted locally. The domain matrix now waits for `confirmPosts === 1` before state and count assertions.

### NO-GO 4 — final full-suite evidence was timing-sensitive

The second Sol production-invariant review reported `P0 = 0` and confirmed the monotonic committed invariant, malformed HTTP 200 handling, committed GET-only recovery, genuine unknown GET 404 fallback, the four 401 paths, idempotency/lossless transport, and user boundaries. Its final browser evidence was nevertheless NO-GO: the first full E2E run was `44 / 44 PASS`, while the second was `43 / 44 PASS`.

The failed assertion used one `receiptGets` total for two distinct request meanings: the recovery coordinator's Receipt lookup and the authoritative Receipt page GET after navigation. In development StrictMode, the Receipt page effect may run more than once. A URL assertion also does not guarantee that this GET has completed. Therefore a total endpoint count cannot prove that recovery issued an extra lookup.

The E2E observer has been remediated without production changes. It explicitly records recovery lookup and Receipt-page GET phases, changes phase only through the mock scenario's expected recovery transitions, waits for the authoritative Receipt UI, and preserves the key/path/exact-body, Confirm-count, GET-404-to-fallback-POST, and committed-zero-POST assertions. The historical `43 / 44` result remains retained; the closure section below is updated only after fresh stability runs complete.

### NO-GO 5 — reconciliation action and authentication continuation were incomplete

The latest independent Sol review found `P0 = 0`, `P1 = 2`:

- **P1-1:** `confirmDomainAction()` classified both `IMPORT_BATCH_ALREADY_CONFIRMED` and `IMPORT_LOCK_CONFLICT` as `RECONCILE_RECEIPT`, but the coordinator did not consume that action and fell through to `markUnknown()`. This incorrectly allowed an already-confirmed batch to reach `GET 404 → fallback POST`.
- **P1-2:** The coordinator resumed `AUTH_REQUIRED(resumeState=OUTCOME_UNKNOWN)` directly into Receipt GET without first consuming `resumeState`. A later `404`, network failure, or malformed Receipt response could therefore attempt to persist a non-auth state with forbidden resume metadata, which the fail-closed storage validator correctly rejected.

The mapper remains the sole domain-classification boundary. `RECONCILE_RECEIPT` is now consumed explicitly: `IMPORT_BATCH_ALREADY_CONFIRMED` maps to `COMMITTED_AWAITING_RECEIPT` and stays GET-only after 404/network/decode failure; `IMPORT_LOCK_CONFLICT` explicitly enters unknown-outcome Receipt-first reconciliation, where only a 404 can trigger the same frozen POST. Authentication recovery now atomically restores the saved source state, clears `resumeState`, persists that clean record, and only then performs the resumed GET or POST. The storage validator was not relaxed.

### Build and test closure

- Node 22 ESM test runtime required explicit `.ts` extensions for runtime value imports. The production source now works in Node ESM, Vite, and TypeScript without a test-only branch or duplicate implementation.
- `ImportConfirmDialog` cleanup uses an explicit `void` cleanup function. Event lifecycle and focus restoration are retained; focus-trap tests remain green.

## Engineering evidence

### Confirm and idempotency

```text
one user intent → one Idempotency-Key → one frozen bodyJson
```

The pending record is written before POST and contains only the owner, session/batch identifiers, key, confirm path, exact JSON body, timestamps, and recovery state. It does not persist files, preview rows, frozen plans, receipts, or balances. The double-click test issues one POST and asserts the generated key and exact serialized body. All recovery attempts reuse the same key, path, and exact body bytes.

### Unknown outcome, committed recovery, and auth recovery

```text
POST unknown → Receipt GET
GET 200         → authoritative receipt
GET 404         → same frozen POST
```

Once HTTP 200 has been observed, the state is instead monotonic:

```text
HTTP 200 + undecodable Receipt → COMMITTED_AWAITING_RECEIPT
COMMITTED_AWAITING_RECEIPT + Receipt GET 404/network/decode → same committed state
COMMITTED_AWAITING_RECEIPT + Receipt GET 401 → same GET after same-user auth
```

`COMMITTED_AWAITING_RECEIPT` never sends Confirm POST.

The browser suite covers all four 401 paths:

| Path | Verified result |
| --- | --- |
| Initial Confirm POST 401 | Same-user login resumes the same POST; recovery Receipt GET count is zero. |
| Unknown-outcome Receipt GET 401 | Same-user login resumes the same GET; Confirm POST count is zero. |
| Fallback POST 401 | `GET → POST → POST`; no second Receipt GET; both POSTs have the same key and exact body. |
| `COMMITTED_AWAITING_RECEIPT` Receipt GET 401 | Same-user login resumes the same GET; Confirm POST count is zero. |

In continuation tests, unknown GET `401 → 404` produces a valid clean `RECOVERING_CONFIRM` record and the same frozen POST; unknown GET `401 → network` remains a valid clean `OUTCOME_UNKNOWN` record; committed GET `401 → 404` remains a valid clean GET-only record. Initial POST 401 and fallback POST 401 retain their original POST semantics with the same key, path, and body.

### Domain error matrix

All 14 real Confirm/Receipt codes are triggered in browser automation, not merely listed in a table:

`IMPORT_CONFIRM_REQUEST_INVALID`, `IMPORT_SESSION_NOT_FOUND`, `IMPORT_PREVIEW_EXPIRED`, `IMPORT_SESSION_CANCELLED`, `IMPORT_PREVIEW_STALE`, `IMPORT_PREVIEW_UNAVAILABLE`, `IMPORT_DUPLICATE_EVIDENCE_CHANGED`, `IMPORT_WARNING_ACK_REQUIRED`, `IMPORT_EXACT_DUPLICATE`, `IMPORT_BATCH_ALREADY_CONFIRMED`, `IMPORT_IDEMPOTENCY_CONFLICT`, `IMPORT_LOCK_CONFLICT`, `IMPORT_CONFIRM_INCONSISTENT`, and `IMPORT_BATCH_NOT_FOUND`.

Each case asserts the actual state behavior, pending intent clearing or retention, and one Confirm POST with zero hidden Receipt GETs. Re-preview and terminal outcomes remove the unsafe draft/token; reconcile/conflict/unknown outcomes retain the original intent for explicit safe recovery. `IMPORT_BATCH_ALREADY_CONFIRMED` has an additional browser test proving Receipt GET-only behavior after two 404 responses and one total Confirm POST. `IMPORT_LOCK_CONFLICT` has an additional browser test proving the explicit `POST → GET → same POST` path with the identical frozen request. Responses with `retryable: true` still do not trigger a new key or an automatic unsafe resend.

### User boundary, logout, and multi-tab

- A user switch from User A (with unresolved pending Confirm) to User B never POSTs or GETs User A's intent, never displays User A's receipt, and does not restore User A's draft/token/warnings.
- Logout with an unresolved Confirm is deliberately blocked: it navigates back to transaction import and preserves the owner-bound pending record. It does not blindly clear or send the intent.
- A second tab receives the storage update, shows recovery instead of a competing confirmation, sees exactly one pending key, and does not produce another Confirm POST. Browser locking is a client-side guard; backend idempotency remains the correctness authority.

### Lossless transport and authoritative receipt

`lossless-json@4.3.1` is the only intentional new runtime dependency. Confirm and Receipt GET alone use raw response text before normal JSON number parsing. Receipt financial fields remain exact digit strings, including:

```text
9007199254740993.01
-0.01
9007199254740993.00
999999999999999999.999999
```

The independent `/transactions/import/receipts/:batchId` route reloads its authoritative receipt via GET. Account impact amounts are displayed as strings, `resultDigest` is displayed rather than recalculated, and transaction references are display-paginated only.

### Modal accessibility

Browser evidence covers `role="dialog"`, `aria-modal`, accessible title, focus entering the modal, Tab and Shift+Tab trapping, safe Escape close, focus restoration, and Escape/close being blocked while `CONFIRMING`.
