## 2. 本阶段交付

- Flyway `V14` 创建 `transaction_import_sessions`、`transaction_import_batches` 与 `transaction_import_items`，并以复合外键和唯一约束保护用户隔离、Batch/Item 审计关联与幂等基础。
- Session 由服务端预分配 Batch ID，并强制 15 分钟 TTL；未来 Confirm 必须经 PostgreSQL 行锁的 60 秒事务 guard。
- Batch 持久化 file/mapping/options/normalised/request digest、用户域 idempotency key 与确认状态；`GET /api/v1/imports/transactions/batches/{importBatchId}` 仅返回本用户已确认 Batch 的基础状态。
- 临时文件存储以随机引用名、SHA-256、5 MiB 流式限制、原子移动和受限读取/删除接口提供基础能力；原始文件名不参与路径。
- 通过 Testcontainers 验证 Flyway 全新迁移、V9/V10 升级、用户隔离、唯一约束、跨用户 Item-to-Transaction 拒绝，以及同一 Session 的并发 guard 单赢家。

## 3. 明确未实现

- 没有上传 API、CSV / XLSX parser、格式探测、Mapping、Preview 或 Preview 过期策略。
- 没有 Confirm HTTP 端点、`Transaction`/余额财务写入、余额联动或完整 receipt；没有前端页面。
- 没有触碰真实数据库 `finance_os`，测试只使用 PostgreSQL Testcontainers；未修改前端或冻结的 Architecture 文档。

## 4. 已知后续前置条件

- 3D Confirm 必须在 60 秒 guard 内完成 Session-to-Batch 绑定、同 key 不同 payload 的冲突判定、完整持久化 receipt 与金融原子写入。
- `markExpired` 在 guard 事务中随后抛出运行时异常时可能回滚状态更新；现有 `expires_at` 仍会拒绝后续 Confirm。应在启用 Confirm 前将过期状态持久化与事务边界收敛。
- 启用上传流程前，应完成 HTTP `413`/`415` 映射、临时文件过期/取消/启动时孤儿清理，以及完整 receipt 状态响应。

## 5. 阶段边界

Phase 3B 没有改变金融真值：导入模块不写 `transactions`、不写 `accounts.balance`，也不引入第二套余额或流水真值。后续功能必须遵守 [Phase 3A Transaction Import Contract](../design/V3.0-Phase3A-Transaction-Import-Contract.md)。
