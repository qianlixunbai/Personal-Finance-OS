## 验证证据

- `AccountBalanceServiceTest`、`AccountServiceTest`、`TransactionServiceTest` 与 `GlobalExceptionHandlerTest` 通过。
- `TransactionBalanceConcurrencyPostgresIntegrationTest` 使用 `postgres:17-alpine`、两个真实执行线程、一个 barrier 和有界 future；从余额 100 开始并发创建 `+10` / `+20`，最终余额为 130，并存在两条事实。
- `updateThenDelete_reversesLatestUpdatedEffect` 从余额 100 和一条 EXPENSE 20 事实开始。外层 `TransactionTemplate` 将事实更新为 EXPENSE 50，使用 `CountDownLatch` 在提交前暂停，第二个执行线程随后删除它。PostgreSQL 确认更新释放前第二个事务处于等待状态。两个有界 future 均完成；事实不存在且余额为 100，证明删除操作冲正的是已提交的 50，而不是过期的 20。
- `deleteThenUpdate_returnsNotFoundWithoutSecondReversal` 使用相反的受控顺序。外层事务删除 EXPENSE 20 事实并在提交前暂停；更新操作等待真实 PostgreSQL 锁。释放后删除成功，更新返回现有 404 语义，事实保持不存在，余额为 100 且只发生一次冲正。
- `createRollsBackTransactionWhenBalanceUpdateFails`、`updateRollsBackFactWhenBalanceMutationFails` 与 `deleteRollsBackFactWhenBalanceReversalFails` 仅为测试账户安装唯一命名的 PostgreSQL `BEFORE UPDATE OF balance` trigger。Trigger 在 `finally` 中删除，并确认未出现在 `pg_trigger` 中。数据库异常分别回滚：新事实及其增量（无事实，余额 100）；EXPENSE 20 到 EXPENSE 50 的更新（事实仍为 20，余额 80）；删除冲正（事实仍存在，余额 80）。
- `lockTimeout_returnsHttp409WithoutPartialCommit` 在独立 JDBC 事务中持有 Account 行，再提交一个 MockMvc Transaction 创建请求。使用仅供测试的事务本地 `lock_timeout=750ms` 时，PostgreSQL 锁等待超时经 Spring 数据访问异常转换为 HTTP 409 / code 409，消息为 `并发操作冲突，请重试`；响应不暴露 SQL state、PostgreSQL 类、表或 SQL，事实与余额均未部分写入。
- `lockReleasedBeforeTimeout_allowsRequestToSucceed` 使用同样的独立持有行锁，并通过 `pg_stat_activity` 确认 HTTP 请求处于 PostgreSQL 锁等待。750ms 前释放锁后，请求返回 200；存在一条事实，余额为 20。
- 新增验证后，并发测试类执行了两次：每次 13 tests、0 failures、0 errors。完整命令 `cd backend; .\\mvnw.cmd clean test` 完成了 63 test classes、272 tests、0 failures、0 errors、0 skipped，Surefire 累计时间为 125.68s。
