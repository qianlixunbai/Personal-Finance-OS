## 2. 权威事实核对

设计逐项交叉核对了 Roadmap、Business Rules、Financial Rules、API、Database、ADR-007/011/012/013/014/015、Phase 2B 与 Phase 2C-3 Closing Review，以及当前 Controller、DTO、transactional service、V10–V13 和 PostgreSQL integration tests。

核实结论：

- 六个 command endpoint 与 `Idempotency-Key` header 均与 Controller 一致；前端相对路径符合 `/api/v1` baseURL。
- key 为 1–100 字、非空、无首尾空格，并在各自后端幂等存储域内按用户唯一；replacement correction 与其他 investment transaction 使用不同表级 namespace。所属域内 same key + same hash 返回 immutable receipt，same key + different hash 为 409；前端每 intent 仍生成全新 UUID。
- First BUY 与所有 BUY 要求 ACTIVE Account / Instrument 并校验 CNY/类型兼容；SELL、DIVIDEND 与 reversal 允许 ACTIVE/INACTIVE，仍由后端校验所有权和既有 binding（reversal 还复核兼容性）。replacement 允许 ACTIVE/INACTIVE，实际只复核 ownership、original/Position/Account/Instrument binding identity 与 replay/correction invariants，不宣称它重新执行当前 CNY/类型兼容检查。
- DIVIDEND 支持 OPEN/CLOSED Position，要求更早有效 BUY/OPENING，不改变 quantity/cost/status/PnL。
- Reversal reason 实际为 1–500、non-blank、无首尾空格，closed request schema 拒绝未知字段。
- Replacement 根据 original 自动选择同类型 schema；quantity/unitPrice 或 grossAmount 必须完整提供，fee/tax 省略时为 `0.00`，reference/note trim 后 blank→null，reason 为 1–500、non-blank、无首尾空格。
- OPENING、physical correction fact、REVERSED 和 REPLACED logical transaction 不可再次纠正；一个 original 最多一次 standalone reversal 或 replacement。
- 收到命令 500 不能作为“未提交”证据：replacement unknown-commit PostgreSQL 测试覆盖 commit 后结果丢失和 commit 前回滚；后端修复 `4c0831aa…` 新增 First BUY PostgreSQL 证据，覆盖 committed 后 Account inactive、Instrument inactive、两者同时 inactive仍恢复 immutable receipt，以及 actually-uncommitted retry 仍按新命令前置条件处理。

## 3. 安全与幂等审查

通过项：

1. Key 只在确认后的首次真正提交生成；double click 复用同一个 in-flight command。
2. localStorage 在 POST 前同步保存 exact path/body/key，存储失败则不发送。
3. Web Locks 在跨 tab 的“复查 pending → 生成 key → 持久化”之间提供原子 claim；不支持时写操作 fail-closed，不能让两个 tab 以不同 key 同时穿透。
4. `SUBMITTING`、`OUTCOME_UNKNOWN`、`RECOVERING` 和 `AUTH_REQUIRED` 均冻结 payload；恢复只能 same key + same endpoint + same exact body。
5. 5xx/timeout/network ambiguity 不会产生“提交失败后新建命令”的危险路径；recovery 4xx 同样不能宣告原 attempt 未提交。
6. 只要存在 unresolved command，所有投资写入口全局禁用；401 清 token、page reload、导航、tab 关闭和主动 logout 均保留 pending，且不保存 JWT 副本。
7. 首次提交 409 没有按 message 字符串做脆弱分类，不自动 retry；逐命令 reconcile 成功后才允许新 intent；unknown recovery 的 409 继续保留原 record 和写锁。
8. 写回执与 read current truth 分层；200 时 success state 与 response-derived refresh IDs 原子持久化，崩溃发生在 marker 前后都有确定恢复路径。
9. 未列明 HTTP status 默认 unknown；损坏 storage record fail-closed 且保留原始 bytes。导出、read-model 核对、确认短语或普通 storage cleanup 均不能删除/解锁；只能恢复 valid exact request 后 same-key recovery，或等待权威 server/operator 裁决。
10. `AUTH_REQUIRED` 持久化 `resumeState`，明确区分首次 POST、unknown recovery POST、success refresh GET 与 409 reconcile GET；同 user 重登后只恢复原来源状态，GET-only marker 永远 zero POST，避免认证中断把已成功写入或已明确回滚的命令错误重发。

结论：UI 状态机没有使用新 key 恢复 unknown outcome，也没有覆盖 original 或提交前端权威计算结果。First BUY 修复后，same user + same key + exact same request 可先于可变 ACTIVE precondition 恢复 persisted receipt；无 receipt 时仍按 genuinely new command 校验当前状态。pending 生命周期可按既定状态机收敛。

## 4. 产品与资格审查

- Empty portfolio 与非空 Portfolio 都有 first BUY 入口。
- 当前没有 Instrument creation UI；契约选择把最小 Instrument 创建/选择能力纳入未来写 UI，避免普通用户必须手工调用 API。
- Account/Instrument selector 使用可读名称和状态，不要求输入 ID。
- CLOSED → BUY reopening、full SELL → CLOSED、CLOSED DIVIDEND 和 CLOSED historical correction 均与后端规则一致。
- Correction 入口只在 logical transaction detail，使用“冲正 / 更正”而非 CRUD“删除 / 编辑”。
- REVERSED / REPLACED detail 隐藏两个 correction 按钮并显示只读状态 banner，不留“隐藏或禁用”的实现歧义。
- SELL、reversal、replacement 使用分级确认；BUY/DIVIDEND 使用轻量 review，而不是相同的通用“确定吗”。
- 375px、keyboard focus、focus trap/return focus、screen-reader label 和非颜色风险表达均有冻结要求。

## 5. 字段与金融边界审查

- 八类 command 均有 UI/API/type/required/scale/default/editability/server-calculated/confirmation/success matrix。
- 前端金融状态为 string，统一拒绝 scientific notation、JSON number、NaN、Infinity 和超 scale；不经过 JavaScript floating point。
- First BUY/BUY/SELL 的 fee/tax 显式发送；DIVIDEND 和 replacement 的省略/default 行为与 service 一致。
- gross/net/cash delta/released cost/realized PnL/average cost/total cost/balance/final Position 全部保持 server-authoritative。
- 用户可见 receipt、frontend internal identifiers 与应忽略字段已经区分；correctionGroupId、projectionVersion、lastTransactionId 和物理关系 ID 不向普通用户展示。

## 7. Review findings

### P0

无。

### P1

#### Original finding

`InvestmentCommandTransactionalService.firstBuy` 原先在查询 existing `Idempotency-Key` receipt 前先锁定并校验 ACTIVE Account/Instrument。若 First BUY 已提交但响应未知，随后 Account 或 Instrument 被停用，same-key/same-body recovery 会先返回 409，无法取得 immutable receipt。普通 GET 又不能证明更早 POST 永远不会提交，因此该路径会使 pending record 无法权威收敛。

#### Resolution

后端提交 `4c0831aa63f48e398c7c74f0476f21917f370e75` 将 persisted receipt lookup 移到可变锁与 ACTIVE precondition 之前；首次未命中后仍保持 Account → Instrument 锁顺序，再执行 fresh receipt lookup，只有仍无 receipt 才验证 genuinely new First BUY 的当前前置条件。

#### Evidence

- committed + Account later inactive：同 user、同 key、同 canonical request 返回 `200 + idempotentReplay=true`；
- committed + Instrument later inactive：同样恢复 immutable receipt；
- committed + both later inactive：同样恢复且 transaction、Asset、balance、projection version、last transaction 不产生第二次 effect；
- same key + different hash：先返回 `409`，不被 ACTIVE precondition 遮挡且无第二次 effect；
- actually uncommitted：无 persisted receipt，retry 仍遵守当前 Account / Instrument ACTIVE 等新命令前置条件；
- 独立后端复审结论：`GO，P0 = 0，P1 = 0，P2 = 1`。

#### Current status

`CLOSED`。原 finding 保留为审计历史，不再阻塞 UI Contract。

#### Re-review finding: AUTH_REQUIRED continuation

重新终审的 fresh-reader 测试发现：原候选稿把首次 POST、unknown recovery POST、success refresh GET 与 409 reconcile GET 的 401 都压入单一 `AUTH_REQUIRED`，却没有持久化来源状态。整页跳转登录后无法判断应恢复哪类 POST/GET 及对应错误语义，存在错误重发已成功或已明确回滚命令的风险，因此在本轮一度判定为新的 P1 / NO-GO。

#### Resolution and evidence

Contract 已增加仅供 `AUTH_REQUIRED` 使用的持久化 `resumeState`，严格允许 `SUBMITTING`、`OUTCOME_UNKNOWN`、`SUCCEEDED_AWAITING_REFRESH`、`REJECTED_AWAITING_RECONCILE` 四种来源；runtime validation 拒绝缺失、非法或与 refresh 不一致的组合。同 user 重登后仍保留 AUTH_REQUIRED/source 配对；只有用户动作取得 Web Lock、重读并验证 record 后，才在紧邻实际请求前原子转换，转换失败则 zero request。前两类仍须用户显式动作才可按各自语义 POST，后两类只能继续 GET、永远 zero POST；登录后动作前的 reload/new tab/storage event 不丢失“已知未提交”或 GET-only 证据。未来测试契约覆盖四类 401、登录后动作前崩溃窗口、新 tab、非法 record 和 GET-only refresh IDs。

#### Current status

`CLOSED`。该修复只澄清前端 pending 状态机，不改变 backend、API、幂等、账本或 read truth。
