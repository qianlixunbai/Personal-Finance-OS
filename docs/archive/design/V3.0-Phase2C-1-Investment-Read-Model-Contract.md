# v3.0 Phase 2C-1 投资读取模型契约

## 1. 状态与结论

- 阶段：`v3.0 Phase 2C-1 Investment Read Model Contract`
- 状态：`CLOSED — GO`
- 决策：只冻结读取语义和候选 API，不实现任何读取代码。
- 长期决策：[ADR-015：投资读取模型、逻辑交易视图与审计时间线](../../ADR/ADR-015-investment-read-model-contract.md)
- 验收：[Phase 2C-1 Closing Review](../review/V3.0-Phase2C-1-Closing-Review.md)

本契约选择直接组合现有事实表与受控投影，不新增持久化 Portfolio / Position read-model。Portfolio 只表示 `TRANSACTION_DRIVEN` 投资 Position，不包含 Legacy Asset。默认交易列表按逻辑业务事件展示，审计时间线单独展示不可变物理事实和 correction command。

## 2. 背景

Phase 2B 已实现不可变投资事实、当前 Position 投影、standalone reversal 和 replacement 写路径，但尚无 Portfolio、Position、投资交易查询或审计时间线 API。读取契约必须在不改变写路径、不复制真值、不重写历史事实的前提下，将内部账本表达转换为用户可理解且可审计的模型。

事实优先级为：当前代码与 V4–V13 migration → 已接受 ADR → Phase 2B Closing Review → 当前活文档。冻结的 `Architecture.md`、历史 ADR 和历史 Closing Review 不因本阶段改写。

## 3. 当前事实模型

| 数据 | 当前含义 | 读取用途 |
| --- | --- | --- |
| `InvestmentTransaction` | 不可变投资物理事实 | 审计、逻辑事件派生、canonical replay |
| transaction-driven `Asset` | 唯一当前 Position 受控投影 | Position 当前值的主要读取来源 |
| `Account.balance` | 当前现金余额投影 | 账户当前值；不得按 Position 重复汇总 |
| `InvestmentTransactionCorrection` | replacement 命令的不可变完整封装 | replacement 关系、原因、纠正时间和最终回执 |
| posting-time receipt | 某次命令提交时的历史结果快照 | 幂等恢复和审计；不是当前真值 |
| canonical replay | 应用有效纠正后的规范账本结果 | 当前 Position 的事实校验来源 |
| Market Quote / FX | 已缓存的外部参考快照 | 可选参考估值，不是账务真值 |

当前事实类型为 `OPENING_POSITION`、`BUY`、`SELL`、`DIVIDEND`、`REVERSAL`。不存在独立 `REPLACEMENT` transaction type。Replacement 由 grouped `REVERSAL`、同类型 replacement fact 和 correction envelope 共同表达；original fact 永不更新或删除。

Position 模式严格区分：

- `LEGACY`：用户手工维护的资产快照，可以没有 Account / Instrument binding；
- `TRANSACTION_DRIVEN`：由投资事实驱动、绑定 Account 与 Instrument 的可审计 Position。

## 4. 目标

1. 冻结 Portfolio、Position、逻辑交易、纠正和审计的业务语义。
2. 冻结候选读取 API、认证、过滤、排序、分页、错误与所有权边界。
3. 区分当前真值、历史入账回执、correction final receipt 与参考估值。
4. 冻结字段可见性、金融值格式和后续实现约束。

## 5. 非目标

本阶段不实现 Controller、Service、Mapper、SQL、DTO、OpenAPI 代码、Flyway migration、前端、Portfolio 查询、InvestmentTransaction 查询或 Dashboard 修改；不引入新表、缓存、Redis、MQ、Elasticsearch、CQRS 或第二套 Position 真值。

## 6. 术语

| 术语 | 定义 |
| --- | --- |
| 物理事实 | `investment_transactions` 中不可变的一行 |
| 逻辑业务事件 | 后端将 original、reversal、replacement 关系折叠后提供给普通用户的一条业务记录 |
| logical transaction ID | 逻辑事件的稳定标识；使用 original fact ID，未纠正事实则使用自身 fact ID |
| current truth | canonical replay 与当前受控 `Asset` 投影共同表达的纠正后当前结果 |
| posting-time receipt | 原命令提交时保存的不可变历史回执 |
| correction final receipt | replacement envelope 或 standalone reversal receipt 表达的纠正命令提交结果 |
| effective trade time | 逻辑事件在 canonical replay 中占据的业务时间；replacement 继承 original 的 trade time |
| correction createdAt | 实际执行纠正命令的物理时间 |

## 7. 核心读取原则

1. `Asset` 继续是唯一当前 Position 投影，不创建第二套持仓真值。
2. 普通读取优先读取受控投影；只有一致性检查、详情组合或明确审计需要才读取事实关系。
3. 默认交易列表由后端折叠为逻辑业务事件，前端不得拼接 correction 关系或重算 Position。
4. posting-time receipt 永不被解释为纠正后的当前值。
5. 普通 GET 不调用 Provider、不加行锁、不修改 `lastViewedAt` 或任何附带状态。
6. 所有用户资源查询在 SQL 条件中包含 `user_id`；不得全局查出后再在 Java 判断所有权。
7. 多来源组合必须满足单请求内一致读取；这不是新的写入一致性机制。

## 8. Portfolio 边界

### 8.1 正式定义

Portfolio 是当前用户全部 `TRANSACTION_DRIVEN` Position 的后端聚合读取视图。它不是“全部资产”或净资产，不包含 Legacy Asset，也不按 Position 重复计入绑定 Account 的现金余额。

Portfolio summary 至少表达：

- transaction-driven Position 总数、OPEN 数、CLOSED 数；
- OPEN Position 的当前账面总成本；
- 所有 transaction-driven Position 的累计已实现盈亏；
- 固定的 OPEN Position CNY 参考估值摘要、覆盖数量、freshness 和 warning；估值 value 可以缺失。

`Account.balance` 可继续从 Account API 读取。Portfolio 不把同一 Account 的余额按多个 Position 重复汇总，也不将现金与持仓成本相加为未定义的“总价值”。

### 8.2 Legacy Asset 决策

Legacy Asset 继续仅由现有 Asset API 表达，不进入 Portfolio、Position list 或投资交易逻辑列表。原因：Legacy Asset 可能没有 Instrument / Account binding，是手工快照而非可审计投资账本；混合会模糊 Portfolio 的审计语义和排序字段。

现有 Asset API 仍可同时返回 Legacy 与 transaction-driven Asset，这是当前已实现能力；未来 Portfolio UI 必须明确其范围为“投资账本持仓”，不能声称覆盖全部资产。

## 9. Position 读取模型

### 9.1 当前值来源

| 对外字段 | 当前来源 | 是否公开 |
| --- | --- | --- |
| `quantity` | `Asset.quantity`，由 canonical replay 控制 | 是 |
| `averageCost` | `Asset.avg_cost`，由当前 quantity / total cost 推导并投影 | 是 |
| `totalCost` | `Asset.total_cost` | 是 |
| `cumulativeRealizedProfitLoss` | `Asset.realized_profit_loss` | 是 |
| `status` | `Asset.position_status`：`OPEN` / `CLOSED` | 是 |
| `projectionVersion` | `Asset.projection_version` | 否，仅内部一致性 |
| `lastTransactionId` | `Asset.last_transaction_id` | 否，仅内部投影关联 |

Position response 还可公开用户拥有的 `positionId`、Account ID / display name、Instrument ID / symbol / name / market / asset class / quote currency。`positionId` 是当前 Asset ID 的公共别名，但契约不暴露其数据库表含义。

客户端不得根据交易列表、回执或参考行情自行重算 quantity、cost、average cost、status 或累计已实现盈亏。

### 9.2 Position 列表范围

默认返回 `OPEN` Position；可通过 `status=OPEN|CLOSED|ALL` 明确选择。为避免可变显示名影响 cursor 边界，列表排序为：

```text
instrumentId ASC, accountId ASC, positionId ASC
```

三个字段共同构成 cursor key，`positionId` 是最终唯一 tie-breaker。Account display name 和 Instrument symbol 只用于展示，不参与 v1 cursor 排序。

## 10. 投资交易逻辑事件模型

默认交易列表只返回逻辑业务事件。每个 original replay slot 最多一条列表记录：

| 事实形态 | 默认逻辑记录 |
| --- | --- |
| 未纠正事实 | 原业务值，`correctionStatus=UNCHANGED` |
| standalone reversal | original 业务值，`correctionStatus=REVERSED`，`effective=false` |
| replacement | replacement 后的有效业务值，`correctionStatus=REPLACED`，logical ID 仍为 original ID |
| grouped reversal | 不单独出现在默认列表 |
| replacement fact | 不作为第二笔普通交易出现 |

面向用户的纠正状态冻结为：

```text
UNCHANGED
REVERSED
REPLACED
```

它是只读派生值，不是数据库可变 transaction status。`CORRECTION` 不作为 correction status，因为它描述事件类别而非 original 的最终状态。

默认列表的 `transactionType` 只可能是 `OPENING_POSITION`、`BUY`、`SELL`、`DIVIDEND`。`REVERSAL` 只在审计事实中出现。

## 11. Standalone reversal 展示

默认业务列表不显示两笔可计入交易；它显示 original 的单一逻辑记录，并标记：

- `correctionStatus=REVERSED`；
- `effective=false`；
- `correctionCreatedAt`。

交易详情和审计时间线显示 original fact、standalone reversal fact、关联 ID、reason、真实纠正时间、standalone reversal 的 correction final receipt，以及请求时的 current Position。Original 的 `status`、金额和 posting-time receipt 均保持不变。

## 12. Replacement 展示

默认业务列表在 original 的 logical replay slot 显示 replacement 后的有效业务值：

- `logicalTransactionId` 使用 original fact ID；
- `correctionStatus=REPLACED`；
- `effective=true`；
- `effectiveTradeTime` 继承 original；
- 不把 original BUY、grouped REVERSAL 和 replacement BUY 显示为三笔普通交易。

交易详情同时区分：original business values、effective replacement values、original posting-time receipt、correction final receipt 与 current Position。审计时间线显示 correction envelope，并在其内部列出 grouped reversal 和 replacement fact。

Grouped reversal 是内部不可变事实，不是 standalone reversal 命令。其 receipt 为空表示 `NOT_APPLICABLE`，不是缺失数据；完整 replacement 命令结果由 correction envelope 表达。

## 13. 审计时间线

审计时间线是逻辑交易详情的审计层，不是普通交易列表。当前“一项 original 最多纠正一次”的约束使时间线天然有界，因此 v1 候选契约不分页。

时间线事件顺序为：

```text
eventCreatedAt ASC, eventRoleOrder ASC, physicalFactId ASC
```

其中 `eventRoleOrder` 固定为 `ORIGINAL_POSTING=0`、`STANDALONE_REVERSAL=1`、`REPLACEMENT_COMMAND=1`；replacement command 内物理事实固定为 `GROUPED_REVERSAL=0`、`REPLACEMENT_FACT=1`。Correction timeline 按真实纠正时间展示，不把 correction createdAt 回填到 original trade time。

审计层可以公开同一用户域内必要的 original / reversal / replacement physical IDs，但不公开 correction group UUID、request hash、幂等键、replay digest 或内部 trace。

## 14. 当前真值与历史回执

| 表达 | 来源 | 语义 |
| --- | --- | --- |
| `currentPosition` | canonical replay + 当前 `Asset` 投影 | 纠正后的当前真值 |
| `postingReceipt` | original 或普通 fact 的 receipt | 入账时历史快照 |
| `correctionFinalReceipt` | standalone reversal receipt 或 replacement envelope | 纠正命令提交时快照 |
| `currentAccountBalance` | 当前 `Account.balance`，若具体 endpoint 明确返回 | 当前现金投影 |

旧 SELL 的 released cost、realized PnL 和 receipt 永远保留其入账时含义。读取不得使用旧 SELL receipt 作为纠正后的当前成本或累计 PnL，不得修改历史 receipt 追平当前值，也不得用 correction envelope 替代完整历史事实。

## 15. 排序与分页

### 15.1 时间语义

- `tradeTime`：原始业务事实的服务端入账时间，也是普通事实的 `effectiveTradeTime`；
- `settlementTime`：当前写路径与 tradeTime 为同一服务端 Instant，但在详情/审计中保持独立字段，不能推断永远相等；
- `createdAt`：物理事实实际插入时间，只用于审计，不作为默认业务列表顺序；
- `correctionCreatedAt`：standalone reversal fact 或 replacement envelope 的实际纠正时间；
- `effectiveTradeTime`：canonical replay 和默认业务列表使用的逻辑时间，replacement 继承 original 的 tradeTime。

所有公共时间使用 ISO-8601 UTC Instant 字符串并带 `Z`，例如 `2026-07-25T09:40:00Z`。不返回无时区的本地时间。

### 15.2 Canonical replay

Position 计算继续使用升序规范键：

```text
(effectiveTradeTime ASC, effectiveAnchorId ASC, replaySequence ASC, factId ASC)
```

Replacement 占据 original 的 logical slot；被纠正 original 与 `REVERSAL` 不进入 calculator。

### 15.3 默认逻辑交易列表

列表按业务有效时间倒序，而不是按物理创建时间倒序：

```text
(effectiveTradeTime DESC, logicalTransactionId DESC)
```

`logicalTransactionId` 是稳定唯一 tie-breaker。Replacement 不因纠正时间较晚而跳到列表顶部；真实纠正时间在详情和审计时间线表达。

### 15.4 Cursor 决策

交易列表采用不透明 cursor，而不复用 offset `page/size`。Cursor 编码最后一项的稳定逻辑排序键、过滤条件版本和服务端校验信息；客户端不得解析或构造。请求字段为 `cursor` 与 `size`，`size` 默认 20、范围 1–100。响应为：

```text
records, nextCursor, hasMore, size
```

Cursor seek 条件必须严格落在最后一项之后，倒序比较所有排序分量。新交易插入列表顶部时，不会使后续 cursor 页重复已返回记录。跨请求不承诺数据库快照冻结；每个请求内部必须一致。

Position list 同样采用 cursor，cursor 编码其三段排序键。Portfolio summary 与有界 audit timeline 不分页。

## 16. API 候选契约

这些 endpoint 是后续实现必须遵守的候选契约，当前尚未实现，也不得写入当前 `API.md`。

所有 endpoint 均使用 Bearer JWT、`ApiResponse<T>`，user ID 只来自 principal。

| 方法 | 路径 | 能力 | 参数 / 分页 | 返回 DTO |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/investment/portfolio` | transaction-driven Portfolio summary | 无 | `InvestmentPortfolioResponse` |
| GET | `/api/v1/investment/positions` | Position list | `status`、`accountId`、`instrumentId`、`cursor`、`size` | `CursorPage<InvestmentPositionListItem>` |
| GET | `/api/v1/investment/positions/{positionId}` | Position detail | path ID | `InvestmentPositionDetail` |
| GET | `/api/v1/investment/transactions` | 逻辑交易列表 | `positionId`、`accountId`、`instrumentId`、`type`、`correctionStatus`、`from`、`to`、`cursor`、`size` | `CursorPage<InvestmentTransactionListItem>` |
| GET | `/api/v1/investment/transactions/{logicalTransactionId}` | 逻辑交易详情 | path ID | `InvestmentTransactionDetail` |
| GET | `/api/v1/investment/transactions/{logicalTransactionId}/audit-timeline` | 物理事实与纠正审计 | path ID | `InvestmentTransactionAuditTimeline` |

路径采用 `positionId` 和 `logicalTransactionId`，避免把 API 契约绑定到数据库表名。不会另增 Portfolio position list、correction list 或按类型重复的查询 endpoint。

六个 endpoint 均排除 Legacy Asset。Portfolio / Position endpoint 不返回 correction events；transaction list 只返回折叠后的 correction status；transaction detail 返回纠正关系摘要；只有 `audit-timeline` 返回物理 correction facts 和 command 事件。

### 16.1 过滤规则

- `type`：`OPENING_POSITION|BUY|SELL|DIVIDEND`；
- `correctionStatus`：`UNCHANGED|REVERSED|REPLACED`；
- `from` / `to`：过滤 `effectiveTradeTime`，使用包含下界、排除上界 `[from,to)`；
- 所有 account、instrument、position 过滤都必须先按当前 user ownership 约束；
- 未知枚举、无效时间区间、非法 cursor 或 size 返回 400。

### 16.2 错误

| HTTP | 读取语义 |
| --- | --- |
| 400 | 非法过滤、枚举、cursor、分页或时间区间 |
| 401 | JWT 缺失或无效 |
| 404 | 资源不存在或跨用户资源，响应一致 |
| 500 | 脱敏的投影/关系一致性错误或未知内部错误 |

普通 GET 不产生业务 409，也不直接产生 Provider 429/502/503。

## 19. 安全与错误

1. 所有查询在数据库层使用 `(user_id, resource_id)` 或等价复合所有权条件。
2. 跨用户和不存在资源均返回相同 404；过滤器引用跨用户资源也不泄露其存在性。
3. 500 只返回稳定、脱敏的公共错误，不含 SQL、类名、hash、constraint、堆栈或内部 ID。
4. Read DTO 不接受 user ID、currency、projection 元数据或任何服务端计算字段。
5. 用户文本只在已认证且具备所有权的详情/审计 response 中返回。

## 20. 查询与性能约束

1. 列表不得为每行执行完整历史 replay。
2. Position 当前值读取受控 `Asset` 投影；必要时以批量/组合查询派生 correction status。
3. Account、Instrument、Position 与 correction 关系必须批量加载或通过组合 SQL 获取，禁止明显 N+1。
4. transaction list 在 SQL 层生成稳定逻辑行和 cursor seek；前端不做去重或折叠。
5. transaction detail / audit timeline 可以组合 original、reversal、replacement 和 envelope，但不修改事实。
6. 普通 GET 不获取 `FOR UPDATE` 行锁，不写访问时间，不刷新 Provider。
7. 不以缓存替代 PostgreSQL 事实，不新增持久化 read-model。
8. 单 SQL endpoint 依赖语句级一致快照；需要多次查询组合的 endpoint 使用只读 `REPEATABLE READ` 事务，保证单请求内一致读取。该要求不改变任何写事务规则。

## 21. 参考估值边界

Portfolio response 必须包含 `referenceValuation` 摘要对象；没有可用缓存时对象仍返回 `freshness=UNAVAILABLE`、coverage 和 warning，但 value 为 null。Position list 返回精简摘要，Position detail 返回分离的 reference sources。具体边界为：

- Portfolio 聚合只使用已有 cached Market Quote + cached FX 形成的 CNY reference valuation，不把 manual current price 混入同一合计；
- Position detail 可以分别公开 `manualReference` 与 `cachedReferenceValuation`，不设置隐式来源优先级；
- 普通 GET 只读取已缓存 Market Quote / FX 和已有 manual reference fields，绝不调用 Provider；
- 核心 Position 即使没有 quote 或 FX 也必须正常返回；
- stale / partial / unavailable 必须显式标记 freshness 和 warning；
- reference valuation 使用独立对象并标记 `accountingTruth=false`；
- reference valuation 不覆盖 quantity、averageCost、totalCost 或 cumulative realized PnL；
- Portfolio 只汇总可转换为 CNY 的 OPEN Position 参考值，同时返回覆盖数量，不能把部分覆盖伪装为完整总值；
- 前端不得自行执行跨币种汇总。

Position detail 可以同时展示 manual current price、cached quote 与 cached FX 的来源和时间；默认 Position list 只返回 cached reference valuation 精简摘要。Provider 名称等非敏感参考元数据可以公开，Provider credential 永不公开。

## 22. 备选方案

### 22.1 Portfolio 数据来源

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 组合当前表与当前投影 | 无第二真值；与 ADR-007 一致；migration 风险最低；查询可解释 | 需要设计组合查询和批量 correction 派生 | 采用 |
| B. 新增持久 read-model 表 | 查询直接 | 复制 Position 真值；新增同步、migration 和恢复风险 | 拒绝 |
| C. 每次请求完整 replay | 直接从历史重建 | 列表成本高、易 N+1、复杂且与受控投影重复 | 拒绝 |

### 22.2 交易列表表达

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 全部物理事实 | 审计最直接 | 普通用户会把 original / reversal / replacement 重复视为交易 | 拒绝默认使用 |
| B. 仅逻辑业务事件 | 易理解且不重复 | 若没有专门审计层会损失细节 | 单独不足 |
| C. 双层模型 | 默认逻辑事件清晰，审计层保留完整物理事实 | DTO 设计稍多 | 采用 |

### 22.3 Legacy Asset

| 方案 | 风险 | 结论 |
| --- | --- | --- |
| Portfolio 只含 transaction-driven Position | 需明确“不代表全部资产” | 采用 |
| Portfolio 混合 Legacy Asset | 绑定、排序和审计语义不一致 | 拒绝 |
| Legacy 继续由 Asset API 表达 | 保持现有能力边界 | 采用 |

### 22.4 分页

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `page` / `size` offset | 复用 `PageResult` | 顶部并发插入可能导致重复/漏项，审计稳定性较弱 | 拒绝用于本契约列表 |
| opaque cursor seek | 对稳定复合键分页；顶部新增不移动既有 cursor 边界 | 新增 cursor DTO 与校验 | 采用 |

## 23. 最终决策

1. 直接组合现有表与受控投影；不新增持久 read-model。
2. Portfolio 只含 transaction-driven Position，Legacy Asset 继续使用 Asset API。
3. 默认交易列表是逻辑业务事件；审计时间线展示物理事实与 correction command。
4. Public correction status 为 `UNCHANGED|REVERSED|REPLACED`。
5. current truth 来自 canonical replay + 当前 Asset projection；receipt 永远是历史快照。
6. 交易与 Position 列表使用 opaque cursor 和稳定复合排序。
7. 参考估值摘要对象固定存在，但估值 value 可缺失；它具有显式 freshness，且始终不是账务数据。
8. projectionVersion、lastTransactionId、request hash、幂等键、digest、group ID 和 trace 不公开。

## 24. 后续实现验收标准

- 六个候选能力按冻结路径、DTO 与 ownership 实现，或通过新 ADR 明确变更；
- 跨用户/不存在资源均为安全 404；非法过滤/cursor 为 400；普通读取无 409；
- replacement 在默认列表只有一个逻辑事件，grouped reversal 不作为普通交易；
- current Position 与受控 Asset projection 一致，前端不重算；
- cursor 分页在同时间交易、replacement 和顶部并发新增场景无重复；
- 列表无逐行 replay 和明显 N+1；组合读取满足单请求内一致性；
- 金融 JSON string、scale、ISO-8601 UTC 和字段禁止公开边界有契约测试；
- 普通 GET 不调用 Provider、不加行锁、不写任何状态；
- 没有第二套 Position 真值或新持久 read-model。
