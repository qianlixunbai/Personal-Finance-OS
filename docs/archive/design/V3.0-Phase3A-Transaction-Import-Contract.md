## 2. Scope

首版仅设计当前普通流水的批量创建入口：

- 支持 `CSV` 与 `XLSX`；
- 支持 `INCOME`、`EXPENSE`、`ADJUSTMENT`；
- 支持字段映射、Account / Category 显式值映射、只读 Preview、逐行校验、重复候选提示、warning 确认；
- Confirm 采用整批原子写入，复用正式 Transaction 领域规则和账户余额受控写路径；
- 提供批次级幂等、unknown-outcome 恢复、权威回执和最小审计。

核心原则：

> CSV / Excel Import 只是批量创建现有 `Transaction` 财务事实的入口，不是第二套账务系统。

## 3. Non-goals

首版不设计或实现：

- `InvestmentTransaction`、`BUY`、`SELL`、`DIVIDEND`、`OPENING_POSITION`、reversal、replacement 导入；
- `TRANSFER`、`REFUND`；
- 多币种账务、汇率换算、FIFO / lot、公司行动；
- 银行或券商 API 自动同步、scheduled/background import；
- PDF statement parsing、OCR、AI 自动字段映射；
- 自动创建 Account 或 Category；
- Excel-like inline editor；
- Batch Undo、批量 DELETE 或绕过现有 Transaction 修改/删除语义的纠正机制；
- 真实支付、资金划转、证券交易或投资建议。

## 4. Current System Invariants

本契约继承以下当前事实，来源包括 [业务规则](../../domain/business-rules.md)、[金融规则](../../domain/financial-rules.md)、[API 当前契约](../../architecture/api.md) 与真实 `TransactionService`：

1. user ID 只来自 JWT principal；客户端不得声明或覆盖 user ID。
2. 普通流水只支持 `INCOME`、`EXPENSE`、`ADJUSTMENT`；`TRANSFER`、`REFUND` 当前拒绝。
3. `INCOME` / `EXPENSE` 的 amount 必须为正；`ADJUSTMENT` 为非零有符号金额且 description 必须非空白。
4. `categoryId` 对三种类型均为必填。`INCOME` 只能使用收入分类，`EXPENSE` 只能使用支出分类；`ADJUSTMENT` 可使用当前用户可见的收入或支出分类，不按金额正负推导分类类型。系统分类的共享谓词冻结为 `user_id IS NULL AND is_system = true`；当前 `TransactionService` 只检查 `isSystem=true` 的实现差异必须在 Import 实现前通过共享校验原语收紧，Import 不得复制较宽松谓词。
5. 新增流水的目标 Account 必须属于当前用户、状态为 `ACTIVE`、币种为 `CNY`。
6. 当前账务仅支持 `CNY`。缺失 currency 默认 `CNY`，非 `CNY` 拒绝。
7. `Transaction.amount` 与 `Account.balance` 使用 `BigDecimal` / `NUMERIC(18,2)`；导入不得使用 `double`、`float` 或 JavaScript `Number` 作为金融真值。
8. 创建 Transaction 与应用 balance effect 必须处于同一数据库事务。
9. `AccountBalanceService` 是 `Account.balance` 的唯一生产写入者；Import 不得直接计算最终余额并执行 `UPDATE accounts`。
10. 普通流水的 balance effect 为：`INCOME → +amount`、`EXPENSE → -amount`、`ADJUSTMENT → amount`。
11. 账户锁按去重后的 account ID 升序获取；并发冲突使用当前 `409` 语义。
12. 资源不存在和跨用户资源统一使用安全 `404`，不得泄露其他用户资源是否存在。

## 5. Terminology

| 术语 | 定义 |
| --- | --- |
| Source row | 文件中的一个非空数据记录；CSV 的 `rowNumber` 是逻辑 record 起始物理行号，XLSX 的 `rowNumber` 是 worksheet 物理行号 |
| Canonical row | 按字段映射、类型映射和格式规则标准化后的普通流水候选 |
| Preview Session | 仅用于解析、映射、校验和确认绑定的短生命周期服务端会话 |
| Preview revision | 同一 Session 中由一组确定 mapping 生成的不可变预览版本；新 mapping 使旧 token 失效 |
| Import Batch | Confirm 成功后持久化的整批审计与权威回执；不是 Preview Session |
| Exact batch duplicate | 与已确认批次具有相同 file、mapping、options 与 normalized plan digest |
| Probable duplicate | 与已有流水或同文件其他行高度相似，但不足以证明是同一真实交易 |
| Idempotent replay | 同 user、同 idempotency key、同 request hash 的 Confirm 重试返回既有权威回执，不产生第二次 effect |

## 6. Supported File Formats

### 6.1 支持矩阵

| 项目 | CSV | XLSX |
| --- | --- | --- |
| 扩展名 | `.csv` | `.xlsx` |
| MIME type | `text/csv`、`application/csv`、`application/octet-stream` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`、`application/octet-stream` |
| 内容校验 | 严格 UTF-8 文本，无 NUL | ZIP signature + 合法 OOXML workbook 结构 |
| 最大上传大小 | 5 MiB | 5 MiB |
| 最大数据行 | 10,000 个非空数据记录 | 10,000 个非空数据行 |
| 最大列数 | 32 | 32 |
| worksheet | 不适用 | 恰好 1 个且必须可见 |
| header | 第一个 record，必须存在 | 第 1 行，必须存在 |

扩展名、允许的 MIME 与内容必须一致。客户端 MIME 只作为提示，不可单独作为格式判断。`.xls`、`.xlsm`、`.xlsb`、ODS、压缩包内嵌工作簿和伪装扩展名均拒绝。

### 6.2 Header 与行规则

- header 单元格按 Unicode NFC 和首尾空白 trim 后比较；空 header 或规范化后重复 header 使整个文件失败。
- header 名最长 128 个 Unicode code point；单个源值在字段解析前最长 4,096 个 code point。
- 未映射列必须在 mapping 中显式标记 `IGNORE`；额外或未知列不得被静默忽略。
- CSV 中 header 前的空 record 不允许；XLSX 中 header 固定为第 1 行。
- header 后的完全空记录忽略且不计入 10,000 行限制；`rowNumber` 始终保留文件物理位置，因此可以不连续。
- 只有空白数据行的文件或 worksheet 视为空文件并拒绝。
- 数据区域再次出现与 header 完全相同的行，按普通数据校验，不会被自动视为新 header 或静默跳过。

## 7. Canonical Row Schema

首版 source-to-canonical 字段如下。名称表示 canonical target，不要求源文件使用相同 header。

| 字段 | 状态 | 规则 |
| --- | --- | --- |
| `date` | required | 交易本地日期，见第 8 节 |
| `time` | optional / default | 缺失或空值默认为 `00:00:00` |
| `type` | required | 通过显式值映射得到 `INCOME`、`EXPENSE` 或 `ADJUSTMENT` |
| `amount` | required | 普通定点十进制字符串，规范化为 scale 2 |
| `account` | required | 源账户值；必须显式映射到当前用户 Account ID |
| `category` | required | 源分类值；必须显式映射到当前用户可见 Category ID |
| `description` | optional | 最长 500 个 Unicode code point；`ADJUSTMENT` 时为 required |
| `currency` | optional / default | 缺失或空值默认为 `CNY`；只接受 `CNY` |
| `transactedAt` | derived | `date + time` 形成无时区 `LocalDateTime`，不是源列 |
| `externalReference` | unsupported | 当前 `Transaction` 契约无此字段，首版不得保存为第二套业务真值 |
| `userId` | derived | 仅来自 JWT principal，源列不得映射 |
| `accountId` / `categoryId` | derived | 由显式 mapping 得到，源文件数字不得直接作为可信 ID |

任一源列只能映射到一个 canonical target；每个 required target 必须恰好有一个源列。`userId`、数据库 ID、balance、createdAt、updatedAt 等内部字段若出现在源文件中，只能显式 `IGNORE`，不得成为 authoritative input。

## 8. Parsing Rules

### 8.1 CSV

- 编码只支持 UTF-8；UTF-8 BOM 可存在且只在文件开头移除。
- 不支持 GBK、UTF-16、系统默认 charset 或自动编码猜测。
- delimiter 固定为逗号 `,`；semicolon 与 tab delimiter 不支持。
- quoted field 使用双引号；字段内双引号以两个双引号转义；quoted field 可包含逗号和换行。
- 接受 LF 与 CRLF；裸 CR 行结束符拒绝。quoted field 内的 CRLF / CR 规范化为 LF。
- empty field 保留为空字符串；完全空 record 按第 6 节忽略。
- malformed quote、列数不一致或超过资源限制使文件级 Preview 失败。

### 8.2 XLSX

- workbook 必须恰好包含一个可见 worksheet；多 sheet、hidden/very-hidden sheet 均拒绝。
- worksheet 第 1 行为 header；数据区隐藏行或隐藏列拒绝，避免 Preview 与用户可见内容不一致。
- merged cell、formula cell、array formula、data table formula 均拒绝，即使位于显式忽略列中。
- Parser 不计算 formula，也不使用 cached formula value。
- macro、external relationship、external link、embedded object、OLE package、ActiveX 与 workbook encryption 拒绝。
- string cell 按文本读取；boolean/error cell 作为业务字段时拒绝。
- amount 可来自 numeric cell，但必须可无损转为满足 amount contract 的普通定点十进制；不得经 `double` 中转。
- date/time 可来自 ISO 字符串或由 OOXML cell type 与 date style 明确标识的日期/时间单元格。无 date style 的裸 Excel serial number、1904 date system 或无法无歧义识别的 serial date 拒绝。
- `date` 单元格若同时携带非零时间且又映射了 `time` 列，作为歧义输入拒绝；否则可拆分为 date 与 time。

### 8.3 Amount

解析前只移除 ASCII leading/trailing spaces，随后必须是普通定点十进制：最多 16 位整数、最多 2 位小数、无千位分隔符、无货币符号、无科学计数法、无括号负数。允许负号，不接受显式正号。

- `INCOME`、`EXPENSE`：`0 < amount <= 9999999999999999.99`；保存正数。
- `ADJUSTMENT`：金额位于 `NUMERIC(18,2)` 范围且不为 0。
- 一位或零位小数规范化为 scale 2；超过两位直接拒绝，不执行 rounding。
- Preview / Confirm DTO 使用 fixed-scale decimal string；服务端转换为 `BigDecimal` 后进入正式规则。

### 8.4 日期、时间与 timezone

- 文本 date 只接受 `YYYY-MM-DD`。
- 文本 time 只接受 `HH:mm` 或 `HH:mm:ss`；`HH:mm` 规范化补秒为 `HH:mm:00`。
- 不接受 `01/02/2026`、locale date、timezone offset、`Z` 或带时区名称的值。
- 当前 Transaction 使用 `LocalDateTime`；导入不做 timezone conversion，`transactedAt` 精确等于源 date 与 time 的组合。
- 无效日历日期拒绝。未来日期沿用当前 API 的可写语义，允许导入且不额外产生 warning；Import 不得暗中收紧现有 Transaction 业务规则。

### 8.5 Description 与自由文本

- description 不自动 trim；除换行规范化外保留用户文本，避免悄然改变财务说明。
- CRLF / CR 规范化为 LF；允许换行。
- 除 LF 外的 C0 control character 与 DEL 拒绝。
- 空或 whitespace-only description 对 `INCOME` / `EXPENSE` 允许，对 `ADJUSTMENT` 拒绝。
- HTML/script-like text 与以 `=`、`+`、`-`、`@` 开头的文本按普通数据原样保存，不执行、不解释；前端必须按 text render 并进行上下文转义。
- 未来导出为 spreadsheet 时必须使用 CSV injection-safe serializer；不得为了未来导出而在当前 Transaction 中静默添加前导 apostrophe。

## 9. Mapping Model

Mapping 是显式、用户可见且纳入 Preview binding 的契约，包含：

1. `columnMappings`：canonical target → source header，或 source header → `IGNORE`；不做 AI 猜测。
2. `typeMappings`：规范化后的源 type 值 → `INCOME` / `EXPENSE` / `ADJUSTMENT`；canonical enum 值也必须形成明确 identity mapping。
3. `accountMappings` / `categoryMappings`：规范化后的源值 → 当前系统资源 ID。

源 mapping key 使用 Unicode NFC 与首尾空白 trim 后的值。不同原值若规范化为同一 key 但意图不同，Preview 返回 mapping conflict，不自动选择。

Account mapping 必须满足：

- 只按用户显式选择的 Account ID 绑定，不按 account name 静默匹配；
- Preview 校验属于当前用户、状态 `ACTIVE`、币种 `CNY`；
- duplicate name 不构成歧义，因为 ID 是 authoritative target；
- account not found、wrong user、inactive 或 currency mismatch 为 row `ERROR`。

Category mapping 必须满足：

- 只映射已存在 Category，不自动创建；
- 可见范围是当前用户 Category，或 `user_id IS NULL AND is_system = true` 的系统 Category；
- `INCOME` 必须映射 `INCOME` Category，`EXPENSE` 必须映射 `EXPENSE` Category；
- `ADJUSTMENT` 可映射当前可见的 `INCOME` 或 `EXPENSE` Category，沿用当前正式 Transaction contract；
- category not found、wrong user 或 type mismatch 为 row `ERROR`。

## 10. Preview Lifecycle

```text
Upload → Safe Parse → Detect Columns / Values → Explicit Mapping → Normalize
→ Validate / Duplicate Detection → Read-only Preview → User Review
→ Confirm → Atomic Import → Authoritative Receipt
```

Preview 绝不创建 Transaction、修改 Account.balance、创建 Account/Category 或修改任何金融事实。它可以创建非金融的短生命周期 Session metadata 和私有临时文件。

首次 Preview 上传可以携带完整 mapping，也可以省略 mapping：

- mapping 完整时直接生成 `PREVIEW_READY` revision；
- mapping 缺失或不完整时生成 `MAPPING_REQUIRED` Session，返回 detected columns 与 distinct mapping values；
- 客户端提交 mapping 后生成新的不可变 revision、token 和 digest；旧 token 立即失效；
- Session TTL 固定 15 分钟。过期后不可 Confirm，必须重新 Preview。

Session 状态只允许 `MAPPING_REQUIRED`、`PREVIEW_READY`、`EXPIRED`、`CANCELLED`、`CONSUMED`。成功 Confirm 后在金融事务内原子转为 `CONSUMED`；它们均不是 Import Batch 状态。Batch 首版只持久化 `CONFIRMED`。

每个 Session 必须有 user-scoped durable database metadata row，作为 Confirm mutex 与 unknown-outcome reconciliation guard；不得仅依赖进程内状态。该 row 保存 session/batch ID、状态、revision、四类 digest、expiresAt 与 consumedAt，不保存完整源行。原始文件和 normalized plan 的敏感 payload 仍按 15 分钟 TTL 清理；最小 guard metadata 保留 24 小时，且长于 60 秒 Confirm 事务上限。

Preview rows 默认按 source row number 升序分页返回，默认 100、最大 500；首个 Preview response 内嵌第一页。服务端 Session 保存完整 immutable normalized plan，客户端分页不是 authoritative plan。

## 11. Validation Model

每个 Preview row 至少包含：

```text
rowNumber
sourceValues
normalizedValues
mappingStatus
errors[]
warnings[]
duplicateStatus
importable
```

| 状态 | 含义 | Confirm 行为 |
| --- | --- | --- |
| `VALID` | 无 error、无 warning | 可导入 |
| `WARNING` | 无 error，但存在需用户知情的风险 | 只有全部 warning ID 被显式确认后可导入 |
| `ERROR` | 解析、mapping 或业务校验失败 | 整批 Confirm disabled |

`errors` / `warnings` 使用结构化对象：`id`、`code`、`scope`、`field`、`rowNumber`、`message`、`retryable`。自由文本只用于人类说明，不作为客户端分支依据。

首版不支持在 Confirm 时排除错误行。用户必须修正源文件或 mapping 并形成新的 Preview revision；前端不得静默跳过 ERROR row。

## 12. Duplicate Semantics

Duplicate detection 不等于自动删除：

| 类型 | 证据 | 处理 |
| --- | --- | --- |
| 同一 Confirm 重放 | 同 user、同 idempotency key、同 request hash | 返回既有 receipt，`idempotentReplay=true` |
| `EXACT_BATCH_DUPLICATE` | 与当前用户已确认批次的 fileDigest、mappingDigest、optionsDigest、normalizedRowsDigest 全部相同 | `409`，返回既有 batch ID；不创建第二批 |
| `IN_FILE_PROBABLE` | 同一 plan 中 canonical row fingerprint 相同 | `WARNING`，每个候选组必须显式确认 |
| `DATABASE_PROBABLE` | 当前用户已有普通流水在 account、category、type、amount、transactedAt、description 上相同 | `WARNING`，不得静默跳过 |
| 合法相同交易 | 用户显式确认 probable duplicate | 每行仍创建独立 Transaction |

canonical row fingerprint 只用于候选检测，不能成为永久业务唯一键。当前没有 source-specific transaction ID，`externalReference` 又不属于正式 Transaction contract，因此首版不宣称存在 row-level exact identity。

same file digest 但 mapping 或 normalized plan 不同，只产生 `FILE_REUSED_WITH_DIFFERENT_PLAN` warning，不能自动判定为 exact duplicate。

首版不提供绕过 `EXACT_BATCH_DUPLICATE` 的开关；这不是静默丢弃，用户会收到 prior batch ID 与明确冲突。若真实业务确需再次录入完全相同批次，应使用现有逐条 Transaction 入口，或在后续独立契约中重新评审该边界。

`transaction_import_batch` 必须有 `(user_id, file_digest, mapping_digest, options_digest, normalized_rows_digest)` 唯一约束。Confirm 在取得 Session guard 与全部 Account lock 后重新查询 exact batch；若已存在，返回既有 batch receipt，不写新事实。并发插入最终仍由该唯一约束兜底；命中唯一冲突后必须按同一 user 与 digest 组合读取既有 receipt，不能把未知 unique violation 误判为 replay。

## 13. Confirm Contract

Confirm 只接受服务端 Preview Session，不接受客户端重新发送或修改 normalized rows。

Preview binding 采用：

- `importSessionId`：user-scoped opaque identifier；定位服务端 Session；
- `importBatchId`：在 `PREVIEW_READY` 时预分配并返回，供 unknown-outcome 查询；
- `fileDigest`：原始上传 bytes 的 SHA-256；
- `mappingDigest`：canonical JSON mapping 的 SHA-256；
- `optionsDigest`：format options 与 contract version 的 SHA-256；
- `normalizedRowsDigest`：按 source row order 序列化完整 canonical plan 后的 SHA-256；
- `previewToken`：服务端签名的 opaque token，绑定 user、session、batch、四类 digest、revision 与 expiresAt；
- `expiresAt`：15 分钟 Session 期限。

Confirm body 只包含 `previewToken` 与 `acknowledgedWarningIds`；header 必须携带 `Idempotency-Key`。warning ID 集合必须与该 revision 要求确认的集合完全一致，不得少报或伪造额外 ID。

Confirm 的检查顺序：

1. 先验证 token 签名、user、session、batch、revision 与 digest binding，但暂不因 expiry 拒绝；`acknowledgedWarningIds` 去重、排序后进入 canonical request hash。
2. 开启唯一外层数据库事务，按 user + session ID 锁定 durable Session guard row；同 batch 的并发 Confirm 必须在此串行化，事务 timeout 固定 60 秒。
3. 持 guard lock 按 user + idempotency key / batch ID 查找已提交结果；同 hash 则恢复 receipt，即使 Session 已过期或 payload 已删除；同 key 不同 hash 返回 `409`。
4. 未找到已提交结果时，才执行 Session ownership、状态、latest revision、expiry、完整 warning acknowledgment 与 ERROR-free 检查。
5. 获取全部目标 Account lock，重新校验 Account / Category authoritative state，并重新执行 exact batch 与 database probable duplicate detection。
6. 若 Confirm-time warning 集合与 Preview revision 绑定的集合在 code、fingerprint、candidate transaction ID 任一维度不同，返回 `409 IMPORT_PREVIEW_STALE` 并整体回滚，要求新 Preview；集合相同才校验 acknowledgment。
7. 按 source row order 执行共享 Transaction domain rule，创建事实并通过 `AccountBalanceService` 应用每行 effect 的确定性汇总。
8. 写入 batch / item audit 与 authoritative receipt，并把 Session guard 原子更新为 `CONSUMED`，随后提交。

## 14. Idempotency

Confirm 使用 batch-level idempotency，不把每行拆成独立客户端 POST。

- `Idempotency-Key` 在 user 域内唯一，trim 后长度 1–100，客户端值本身不得带首尾空白。
- canonical request hash 由 contract version、fileDigest、mappingDigest、optionsDigest、normalizedRowsDigest、warning acknowledgment 与预分配 batch ID 组成，不包含短生命周期 token 文本。
- 同 key、同 hash：返回已持久化 immutable receipt，不产生任何新 Transaction 或 balance effect。
- 同 key、不同 hash：返回 `409 IMPORT_IDEMPOTENCY_CONFLICT`。
- 同 batch ID、不同 key：返回 `409 IMPORT_BATCH_ALREADY_CONFIRMED`。
- 并发 Confirm 必须依赖数据库唯一约束与锁收敛，不能仅依赖进程内 mutex。

Unknown-outcome 恢复顺序冻结为：客户端保存 Preview 返回的 `importBatchId`、`importSessionId`、原 `previewToken` 与本次 idempotency key；Confirm 超时或 connection reset 后先 `GET batch`。`CONFIRMED` 以 receipt 为准；`404` 只表示当前尚无可见 committed batch，不证明没有 in-flight Confirm。客户端随后必须用同一 token 和同一 key 重试原 Confirm；重试在 durable Session guard lock 上等待原事务完成，再返回 committed replay，或在确认无 batch 后返回 `IMPORT_PREVIEW_EXPIRED_NOT_COMMITTED` / 原始失败。客户端不得换 key 或重新 Preview 后盲目并发提交。24 小时 guard retention 与 60 秒事务上限保证 reconciliation 窗口内结果可判定。

## 15. Atomicity

首版冻结为 `All-or-Nothing`：

- 任一 row 在 Confirm authoritative revalidation 或写入阶段失败，整个批次回滚；
- Transaction facts、Account.balance、batch audit、item audit 和 receipt 位于同一数据库事务；
- 成功批次的 `acceptedRows = createdCount = totalRows`，`skippedCount = 0`；
- Preview 存在 ERROR 时禁止 Confirm；不存在“部分成功”或“静默跳过”。

选择 atomic batch 的原因是它最符合当前 Transaction + balance 一致性、幂等、审计和用户恢复模型，也避免客户端猜测哪些行已经写入。

## 16. Concurrency

Confirm 与 manual Transaction create/update/delete 共享当前锁协议：

1. Import 是新建事实，不预锁不存在的 Transaction；先完成 token 与非权威格式检查。
2. 在唯一外层事务内，收集所有目标 Account ID，去重后按升序一次性获取 owned Account row lock。
3. 持锁后重新读取 Account 与 Category authoritative state、exact batch 与 database probable duplicate candidates，再执行 row domain validation；warning evidence 变化即 stale Preview，不写任何事实。
4. Account metadata update/deactivate 与普通流水写使用相同 Account row lock，因此不会覆盖并发 balance 或在状态变化后错误导入。
5. 分类在 Confirm 事务中重新按 owner/system/type 校验；若未来引入 Category 更新/停用，必须先把其并发协议纳入同一契约，不得只信 Preview cache。
6. lock timeout / deadlock 映射为可重试 `409`；服务端不自动重试金融写入，客户端使用同一 idempotency key 恢复。

## 17. Account.balance Invariant

Import 不得直接提交“最终余额”或直接更新 `accounts.balance`。

后端实现必须复用正式 Transaction domain/service rule，并在 Import 外层事务中：

- 为每个 accepted row 计算一次且仅一次 `balanceDelta(type, amount)`；
- 按 source row order 创建 Transaction；
- 对同一 Account 的 row delta 可在内存中精确 `BigDecimal` 汇总，但每行必须恰好贡献一次；
- 只通过 `AccountBalanceService.applyDeltas` 写入受控余额；
- receipt 的 account impact 从锁定前余额、权威 delta 和提交后余额产生，前端不得重算。

不得循环调用 public HTTP endpoint，也不得在 Import 模块复制 amount/type/category/currency 规则。实现阶段若当前 `TransactionService` 缺少批量复用边界，应提取共享内部 domain primitive；该内部重构不改变本契约和公开 API。

## 18. Error Contract

### 18.1 分类

| 类别 | 示例 | HTTP / Preview 表达 |
| --- | --- | --- |
| File / Parse Error | invalid CSV/XLSX、unsupported encoding/layout、formula、oversize | `400`、`413` 或 `415`，无 Session 或 Session 不可 Confirm |
| Row Validation Error | amount/date/type/mapping/category mismatch | Preview `200`，row `ERROR` |
| Preview Conflict | ambiguous mapping、exact batch duplicate | row/top-level structured error；exact batch 为 Confirm `409` |
| Confirm Conflict | expired/stale token、inactive account、deleted category、same batch different key | `409`；跨用户保持 `404` |
| Runtime Failure | lock timeout、DB unavailable、unexpected failure | lock/deadlock `409`，DB unavailable `503`，脱敏 unexpected `500` |

### 18.2 响应形状

Import endpoint 继续使用 `ApiResponse<T>`。实现阶段必须增加 Import 专用异常/响应映射，使 `413`、`415` 不退化为 `500`，并允许错误携带下列结构化 `data`；当前只返回空 data 的 `ApiResponse.error` 不足以直接复用。

```text
errorCode
scope
rowNumber
field
retryable
importSessionId
importBatchId
```

字段按错误上下文可空。响应不得包含 SQL、堆栈、服务器路径、raw file content、request hash、idempotency key、token 签名材料或其他用户资源信息。

## 19. Receipt

成功或 idempotent replay 返回 server-authoritative receipt：

```text
importBatchId
status = CONFIRMED
sourceFileName
fileDigest
totalRows
acceptedRows
createdCount
skippedCount = 0
warningCount
transactions[]: rowNumber + transactionId
accountImpacts[]: accountId + balanceBefore + delta + balanceAfter
confirmedAt
idempotentReplay
contractVersion
```

所有 money 均为 scale-2 string。`transactions[]` 以 source row order 表达；前端不得根据 Preview 自行计算最终创建数或余额。

## 20. Audit Model

首版需要持久化最小 `ImportBatch` 审计和 `ImportItem` 关联，但它们不是第二套账务真值。

### `transaction_import_batch`

- batch ID、user ID、sanitized original filename；
- file / mapping / options / normalized plan digest；
- contract version、row/warning counts；
- idempotency key 与 canonical request hash；
- `CONFIRMED`、confirmedAt；
- immutable receipt 所需 account impacts。

### `transaction_import_item`

- batch ID、source row number、created transaction ID；
- canonical row fingerprint、warning codes；
- 不保存完整 sourceValues、normalized description 或文件内容。

不使用永久完整 staging table。业务当前真值仍是 `transactions` 与 `Account.balance`；item 只提供来源关联、审计和 duplicate candidate evidence。Batch / item 必须受 user ownership 和不可变约束保护。

Batch / item 与其关联 Transaction 的审计生命周期一致，不参加 15 分钟 Session cleanup；具体用户数据删除策略必须遵循未来统一 retention/delete policy，不得由 Import 私自删除审计关联。

## 21. File Lifecycle

- 上传 bytes 只写入 server-managed private temporary storage，不使用客户端路径，不置于 web root，不按原始文件名创建路径。
- 临时文件与 Session 只允许当前 user 通过 opaque ID 访问。
- 原始 bytes 最长保留到 Session TTL 15 分钟；Confirm 成功或用户取消后立即撤销 Session 文件访问并在返回响应前尝试删除。删除失败不回滚已提交金融事务，但必须进入 cleanup 重试，并在 5 分钟内再次处理。
- 正常过期 cleanup 在过期后 5 分钟内删除；进程异常后，启动 cleanup 删除年龄超过 20 分钟的孤儿临时文件。
- 删除失败需记录脱敏 operational log 并重试，但日志不得包含文件内容或完整金融行。
- 持久化审计只保留 sanitized basename、digest、counts、mapping target summary 与 Transaction IDs；不永久保存原始 CSV/XLSX。

## 22. Security

### 22.1 通用文件边界

- 最大 raw upload 5 MiB；流式计数，超过限制立即终止。
- 单次 safe parse 的 wall-clock 上限为 10 秒，整个 Preview 请求上限为 15 秒；Parser 必须流式计数，单请求解析工作集预算上限为 64 MiB。达到任一预算即终止并返回资源限制错误，不生成可 Confirm Session。
- 文件名只作显示 metadata：取 basename、移除 control character、最长 255 code point；从不参与路径解析。
- 不记录 raw row、description、token、idempotency key 或完整 mapping source value。

### 22.2 XLSX / ZIP 防护

- ZIP entry 数最多 128；单 entry 解压后最大 20 MiB；全部 entry 解压总量最大 50 MiB；压缩比不得超过 100:1。
- `sharedStrings` 解压后最大 10 MiB，最多 100,000 个 entry；单 cell 文本仍受 4,096 code point 限制。
- entry path 含 absolute path、drive prefix、反斜杠绕过或规范化后的 `..` 时拒绝；Parser 不把 archive entry 解压到文件系统。
- malformed central directory、overlap、duplicate critical OOXML part、decompression bomb 均拒绝。
- external relationship、macro、formula、embedded object 全部拒绝，不执行、不解析其目标。

### 22.3 OOXML / XML parser hardening

- 任一 XML part 含 `DOCTYPE` 或 entity declaration 时整个 workbook fail-closed；不允许依赖 entity resolver 忽略后继续解析。
- XML parser 必须启用 secure processing，禁用 external general entity、external parameter entity、XInclude、外部 DTD/schema resolution，并使用拒绝所有 network、本地文件和自定义 URI 的 resolver。
- 全 workbook XML node 总数最多 1,000,000，单元素 attributes 最多 64，嵌套深度最多 64；达到限制立即终止。
- OOXML relationship target 在解析前完成 internal-only allowlist 校验；禁止解析器主动访问任何 URL、UNC path 或本地文件。
- hostile corpus 必须覆盖 XXE、parameter entity、XInclude、Billion Laughs、深层嵌套、超量 node/attribute 与 schema/network resolution。

### 22.4 CSV injection 与 UI

以 `= + - @` 开头的自由文本不是服务端公式，不执行；输入保存其数据含义。所有 UI 按文本渲染。未来导出必须做 spreadsheet context escaping，这一义务不能转嫁给当前入库变形。

## 23. API Draft

路径遵循当前 `/api/v1` 与复数资源风格：

| 方法 | endpoint | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/imports/transactions/preview` | multipart 上传；创建 Session，可选一次提交 mapping |
| `PUT` | `/api/v1/imports/transactions/{importSessionId}/preview` | 对已上传 Session 提交/替换 mapping，生成新 revision |
| `GET` | `/api/v1/imports/transactions/{importSessionId}/rows` | 分页读取当前 Preview rows；只读 |
| `POST` | `/api/v1/imports/transactions/{importSessionId}/confirm` | Confirm server-side plan；需要 `Idempotency-Key` |

`GET batch` 只返回已提交 `CONFIRMED` batch；`404` 不能单独排除 in-flight Confirm，必须按第 14 节用同 token/key 重试并在 Session guard 上收敛。首版 Confirm 是同步事务，不设计 `PENDING` / `FAILED` 异步 job state machine。

## 24. Data Model Considerations

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 永久完整 staging rows | 拒绝 | 隐私与清理成本高，容易形成第二套流水真值 |
| 仅进程内临时 Session | 拒绝 | 无法提供 durable Confirm mutex、unknown-outcome 收敛与重启清理 |
| 私有临时文件 + durable Session guard + 最小 batch/item audit | 采用 | 在 Preview 可用性、隐私、并发、幂等、审计和实现复杂度之间最平衡 |

实现阶段需要新增前向 migration 才能建立 durable Session guard 与 batch/item audit，但 Phase 3A 不创建 migration。Session guard 必须位于 PostgreSQL 并提供 row lock；原始 bytes 与完整 normalized plan 的私有临时 payload 存储介质属于 P2 实现选择，只要满足 user scope、15 分钟 TTL、immutable revision、原子消费和清理约束。

Batch 状态首版只持久化 `CONFIRMED`。失败尝试通过脱敏日志与 HTTP error 表达，不在主事务之外制造可能误导的 `FAILED` 金融批次。

## 25. Frontend Implications

未来 UI 至少包含：

- 文件选择与格式/资源限制说明；
- detected columns 与显式 field mapping；
- source account/category/type values 到系统资源的显式 mapping；
- Preview table、分页、row-level error/warning/duplicate 标识；
- 总行数、有效行、错误行、warning、duplicate candidate、目标 Account/Category、预计创建数；

| 领域 | 必测场景 |
| --- | --- |
| CSV Parser | UTF-8/BOM、quote、escaped quote、multiline、LF/CRLF、empty field/record、坏 quote、GBK/UTF-16、错误 delimiter |
| XLSX Parser | string/numeric/date cells、single sheet、hidden row/sheet、merged cell、formula、macro/external relationship、malformed OOXML、XXE/DTD/entity/XInclude/Billion Laughs/deep nesting |
| Resource Limits | 5 MiB、10,000 行、32 列、sharedStrings、ZIP entry/count/ratio、decompression bomb、timeout |

| Binding | 文件、mapping、normalized plan、warning set 任一改变均不能 Confirm；cross-user Session 为 404 |
| Duplicate | same Confirm、并发不同 Session/key 的 same file/plan、same rows in one file、Confirm-time 新增 database probable、合法相同交易经确认后均创建 |
| Idempotency | double click、并发 Confirm、same key/same hash、same key/different hash、connection reset、in-flight GET 404、expired Session 后恢复已提交 receipt |

| E2E | CSV/XLSX happy path、mapping-required flow、validation failure、warning acknowledgment、confirm、receipt、status recovery、cancel/expiry cleanup |

## 27. Acceptance Criteria

- Import 不产生第二套账务真值，不复制正式 Transaction 业务规则；
- CSV / XLSX 支持矩阵、解析规则和资源上限已冻结；
- canonical row、amount、date/time、CNY 与 mapping 已冻结；
- Preview 纯只读，不写金融事实；
- Confirm 绑定同一 user、file、mapping、options、normalized plan 和 warning acknowledgment；
- Confirm 在锁内重新校验 Account / Category ownership、状态与兼容性；
- probable duplicate 只警告并要求显式确认，不静默丢弃真实交易；
- exact batch duplicate 与 batch idempotency 有确定语义；
- unknown outcome 可通过预分配 batch ID、status lookup 与同 key 重试恢复；
- Confirm 为 atomic batch，任何失败整体回滚；
- batch order 与 account lock order 确定；
- `Account.balance` 只通过 `AccountBalanceService` 受控更新；
- receipt、最小 audit、原始文件生命周期与 security 边界已冻结；
- Investment import、`TRANSFER` / `REFUND`、多币种等明确排除；
- Phase 3A 不包含业务代码、测试、Migration、前端或 workflow 变更；
- 最终 Review 为 `P0 = 0`、`P1 = 0`。
