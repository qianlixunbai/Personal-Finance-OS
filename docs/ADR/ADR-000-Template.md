# ADR-000：Architecture Decision Record Template

**项目名称：** Personal Finance OS

**ADR 编号：** ADR-XXX

**标题：**

**状态：**

- Draft（草案）
- Accepted（已采纳）
- Deprecated（已废弃）
- Superseded（被替代）

**日期：**

YYYY-MM-DD

**负责人：**

项目维护者

------

# 一、背景（Context）

描述当前面临的问题。

说明为什么需要做出本次架构决策。

应包括：

- 当前情况；
- 存在的问题；
- 项目需求；
- 技术背景；
- 业务背景。

本章节应回答：

> 为什么需要做这个决定？

------

# 二、决策目标（Decision Goal）

明确本次决策希望达到的目标。

例如：

- 提高开发效率；
- 提高系统性能；
- 提高可维护性；
- 提高扩展能力；
- 降低复杂度。

------

# 三、备选方案（Options）

列出所有可行方案。

每个方案均应说明：

- 优点；
- 缺点；
- 适用场景。

示例：

方案 A

方案 B

方案 C

禁止只记录最终方案。

必须保留完整决策过程。

------

# 四、最终决策（Decision）

明确最终采用的方案。

说明：

为什么选择该方案。

为什么放弃其它方案。

此部分应避免简单描述，应结合项目实际情况进行分析。

------

# 五、影响分析（Consequences）

说明本次决策带来的影响。

包括：

正面影响：

- 开发效率；
- 可维护性；
- 性能；
- 扩展能力。

负面影响：

- 学习成本；
- 开发成本；
- 运维成本；
- 技术限制。

所有影响应真实记录。

------

# 六、实施计划（Implementation）

说明：

为了落实该决策，需要完成哪些工作。

例如：

- 修改数据库；
- 新增模块；
- 修改接口；
- 更新文档；
- 增加测试。

------

# 七、风险分析（Risks）

说明：

本方案可能带来的风险。

例如：

- 技术风险；
- 性能风险；
- 数据风险；
- 后续维护风险。

同时给出对应缓解措施。

------

# 八、是否需要回滚（Rollback）

说明：

如果未来发现该决策不合适：

是否可以回滚？

如何回滚？

回滚成本如何？

不是所有 ADR 都必须支持回滚，但应进行评估。

------

# 九、相关文档（References）

列出与本次决策相关的项目文档。

例如：

- Project Vision
- Development Guide
- Architecture
- SRS
- Financial Rules
- Business Rules

如引用外部资料，也应注明来源。

------

# 十、后续行动（Follow-up）

列出因本次决策而产生的后续任务。

例如：

- 更新架构图；
- 更新数据库设计；
- 修改 API；
- 补充测试；
- 更新开发规范。

确保决策真正落地，而不是停留在文档中。

------

# 十一、审批记录（Approval）

记录决策确认情况。

包括：

- 提出时间；
- 确认时间；
- 是否正式生效。

个人项目可由项目维护者确认。

------

# 十二、变更记录（Change Log）

记录 ADR 自创建以来的重要修改。

建议格式：

| 日期       | 修改内容 | 修改人     |
| ---------- | -------- | ---------- |
| YYYY-MM-DD | 创建文档 | 项目维护者 |

保持决策历史可追溯。

------

# 使用原则

1. 一个 ADR 只记录一个重要决策。
2. ADR 一经 Accepted，不应随意修改内容。
3. 如需改变已采纳的决策，应新增新的 ADR，并说明替代关系。
4. 所有重要架构决策均应形成 ADR。
5. ADR 是项目技术决策的正式记录，应长期保留。
