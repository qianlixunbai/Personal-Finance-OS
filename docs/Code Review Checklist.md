# Code Review Checklist（代码审查清单）

**项目名称：** Personal Finance OS

**版本：** v1.0

------

# 一、文档目的

本文档用于规范 Personal Finance OS 的代码审查流程。

所有功能开发完成后，在合并代码前，应按照本清单逐项检查。

Code Review 的目标不是挑错，而是保证：

- 功能正确；
- 架构一致；
- 代码可维护；
- 长期可扩展。

------

# 二、需求检查（Requirement Review）

请确认：

-  是否完全满足 SRS 中的需求？
-  是否超出本次需求范围？
-  是否遗漏需求？
-  是否修改了未授权的功能？
-  是否影响其它模块？

------

# 三、业务规则检查（Business Rules Review）

请确认：

-  是否符合 Business Rules？
-  是否符合 Financial Rules？
-  是否违反系统业务边界？
-  是否存在业务逻辑冲突？
-  是否保持业务行为一致？

------

# 四、架构检查（Architecture Review）

请确认：

-  是否符合项目整体架构？
-  是否遵守模块边界？
-  是否引入循环依赖？
-  是否新增不必要的耦合？
-  是否遵守分层架构？

------

# 五、代码质量检查（Code Quality）

请确认：

-  命名是否清晰？
-  是否存在重复代码？
-  方法是否过长？
-  类职责是否单一？
-  是否遵循 SOLID 原则？
-  是否存在魔法数字或硬编码？
-  是否保持良好的可读性？

------

# 六、Java 规范检查

请确认：

-  是否合理使用 Java 21 新特性？
-  是否避免使用过时 API？
-  是否存在空指针风险？
-  是否合理使用 Optional？
-  是否合理使用 Stream？
-  是否存在资源未释放问题？

------

# 七、Spring Boot 检查

请确认：

-  Controller 是否仅负责请求处理？
-  Service 是否承担业务逻辑？
-  Repository/Mapper 是否只负责数据访问？
-  是否合理使用事务（@Transactional）？
-  是否避免在 Controller 中编写业务代码？

------

# 八、数据库检查（Database Review）

请确认：

-  SQL 是否正确？
-  是否存在 N+1 查询？
-  是否缺少索引？
-  是否存在全表扫描风险？
-  是否符合数据库设计规范？
-  是否修改数据库结构？
-  是否同步更新数据库文档？

------

# 九、API 检查（API Review）

请确认：

-  REST 风格是否一致？
-  URL 是否规范？
-  HTTP 方法是否正确？
-  返回结构是否统一？
-  错误码是否统一？
-  是否保持向后兼容？

------

# 十、安全检查（Security Review）

请确认：

-  是否进行了参数校验？
-  是否存在 SQL 注入风险？
-  是否存在 XSS 风险？
-  是否存在权限绕过风险？
-  是否正确使用 JWT？
-  是否避免敏感信息泄露？
-  是否避免日志输出敏感数据？

------

# 十一、性能检查（Performance Review）

请确认：

-  是否存在重复查询？
-  是否存在低效循环？
-  是否存在不必要对象创建？
-  是否可以缓存？
-  是否存在明显性能瓶颈？

------

# 十二、异常处理检查

请确认：

-  是否统一异常处理？
-  是否返回明确错误信息？
-  是否记录必要日志？
-  是否避免吞掉异常？
-  是否保证事务一致性？

------

# 十三、日志检查（Logging Review）

请确认：

-  是否记录关键业务日志？
-  是否避免打印敏感信息？
-  是否合理使用日志级别？
-  是否避免无意义日志？

------

# 十四、测试检查（Testing Review）

请确认：

-  是否完成单元测试？
-  是否验证主要业务流程？
-  是否覆盖异常场景？
-  是否验证边界条件？
-  是否影响已有功能？

------

# 十五、文档检查（Documentation Review）

请确认：

-  是否更新相关文档？
-  是否更新 API 文档？
-  是否更新数据库文档？
-  是否更新 Roadmap（如有必要）？
-  是否更新 ADR（如涉及重要技术决策）？

------

# 十六、Git 提交检查

请确认：

-  Commit Message 是否规范？
-  是否包含无关文件？
-  是否删除调试代码？
-  是否删除临时注释？
-  是否保持提交内容聚焦于单一目标？

------

# 十七、最终确认

代码可以合并前，应确认：

-  功能已完成；
-  Review 已完成；
-  测试已通过；
-  文档已同步；
-  不影响已有功能；
-  满足发布标准。

只有全部检查通过后，方可合并代码并进入下一阶段开发。

------

# 审查原则

1. Review 的目标是提升代码质量，而不是追求完美。
2. 所有问题应基于事实和项目规范提出。
3. 对同类问题应保持一致的审查标准。
4. 如发现文档与实现不一致，应优先修正文档或实现，避免长期偏离。
5. 任何重大修改都应经过 Code Review 后再合并。

------

# 持续改进

本 Checklist 将随着项目发展持续完善。

每一次 Review 中发现的新问题，都应评估是否需要补充到本清单中，使其成为项目长期维护的重要质量保障工具。
