# 架构审查（2026-07-06）

## 审查目标

对 `docs/03-Architecture/Architecture.md` 进行冻结前 Review，确认其是否满足当前阶段的架构设计要求。

## 审查范围

本次 Review 仅覆盖架构文档本身，包括：

- 架构目标
- 系统总体架构
- 技术架构
- 分层架构
- 模块划分
- 模块职责
- 模块依赖关系
- 包结构
- Mermaid 架构图
- 后续扩展能力

本次 Review 不覆盖：

- 数据库设计
- API 设计
- Java 实现细节
- SQL
- 具体业务代码

## 结论

Architecture 文档可以作为当前阶段的架构基线冻结。

该文档已经覆盖项目当前所需的架构视角，能够为后续模块开发、Review、Database 设计与 API 设计提供方向约束。

## 主要优点

- 架构边界清晰，符合模块化单体的当前阶段定位。
- 分层结构明确，便于约束 Controller、Service、Mapper、Entity 等职责边界。
- 模块职责划分较完整，覆盖用户、认证、账户、分类、流水、预算、资产、Dashboard、AI 分析等核心领域。
- 依赖方向相对清晰，有助于避免模块之间形成随意调用。
- 保留了后续扩展能力，没有过早进入数据库、API 或实现细节。

## 可能存在的问题

### P2：模块边界仍需在代码阶段持续校验

架构文档定义了模块职责，但实际代码中仍需要持续检查跨模块调用、公共类膨胀、DTO 泄露等问题。

建议后续在代码 Review 中重点关注：

- 模块之间是否出现反向依赖。
- Service 是否承担过多非本模块职责。
- Controller 是否直接处理业务规则。
- Mapper 是否泄露到非持久化层以外。

### P2：后续 Database 与 API 设计需要继续受架构约束

当前架构文档按要求没有设计数据库和 API。后续进入 Database 与 API 阶段时，需要保持与该架构一致，避免数据库表结构或接口边界反向破坏模块边界。

### P3：AI 模块需要明确权限边界

架构中保留了 AI 分析能力。根据项目金融规则，AI 只能提供分析与建议，不能直接修改财务数据。后续实现时需要在权限、服务边界与操作审计中继续强化该约束。

## 后续建议

- Database 设计开始前，先确认模块边界与核心业务对象。
- API 设计开始前，先确认外部访问边界与认证策略。
- 每完成一个核心模块后，进行一次代码 Review，并将重要问题沉淀到 `docs/review/`。
- 重大架构变化需要新增 ADR，不直接覆盖历史结论。

## 冻结状态

Architecture 文档已冻结。

冻结后原则：

- 不因普通代码实现调整而修改 Architecture。
- 如果发现架构级问题，应先形成 Review 或 ADR。
