# Architecture Review（2026-07-06）

## Review 目的

`docs/03-Architecture/Architecture.md` を凍結前に Review し、現在の段階に必要なアーキテクチャ設計要件を満たしているか確認する。

## Review 範囲

今回の Review はアーキテクチャ文書そのものだけを対象とする。

- アーキテクチャ目標
- システム全体アーキテクチャ
- 技術アーキテクチャ
- レイヤードアーキテクチャ
- モジュール分割
- モジュール責務
- モジュール間の依存関係
- パッケージ構成
- Mermaid アーキテクチャ図
- 今後の拡張能力

今回の Review では以下を対象外とする。

- データベース設計
- API 設計
- Java 実装詳細
- SQL
- 具体的な業務コード

## 結論

Architecture 文書は、現在段階のアーキテクチャ基準として凍結可能。

この文書は、現時点で必要なアーキテクチャ観点をすでにカバーしており、今後のモジュール開発、Review、Database 設計、API 設計に対する方向性の制約として利用できる。

## 主な良い点

- アーキテクチャ境界が明確で、現在段階の Modular Monolith 方針に合っている。
- レイヤー構造が明確で、Controller、Service、Mapper、Entity の責務境界を制約しやすい。
- モジュール責務が比較的完整で、ユーザー、認証、口座、カテゴリ、取引、予算、資産、Dashboard、AI 分析などの主要領域を含んでいる。
- 依存方向が比較的明確で、モジュール間の無秩序な呼び出しを避けやすい。
- 今後の拡張余地を残しており、データベース、API、実装詳細へ早く入りすぎていない。

## 懸念点

### P2: モジュール境界はコード段階で継続的に確認する必要がある

アーキテクチャ文書ではモジュール責務を定義しているが、実際のコードでは、横断的な呼び出し、共通クラスの肥大化、DTO の漏れなどを継続的に確認する必要がある。

今後のコード Review では、以下を重点的に確認する。

- モジュール間に逆向き依存が発生していないか。
- Service が担当モジュール以外の責務を持ちすぎていないか。
- Controller が業務ルールを直接処理していないか。
- Mapper が永続化層以外へ漏れていないか。

### P2: 今後の Database / API 設計もアーキテクチャ制約に従う必要がある

現在のアーキテクチャ文書は、要求どおりデータベースと API を設計していない。今後 Database / API 設計に進む際は、このアーキテクチャと整合させ、テーブル構造やインターフェース境界がモジュール境界を逆に壊さないようにする。

### P3: AI モジュールは権限境界を明確にする必要がある

アーキテクチャでは AI 分析機能を残している。金融ルールに従い、AI は分析と提案のみを行い、財務データを直接変更してはならない。実装時には、権限、サービス境界、操作監査でこの制約を強化する必要がある。

## 今後の提案

- Database 設計を始める前に、モジュール境界と主要業務オブジェクトを確認する。
- API 設計を始める前に、外部アクセス境界と認証方針を確認する。
- 主要モジュールが完成するたびにコード Review を行い、重要な問題を `docs/review/` に蓄積する。
- 重大なアーキテクチャ変更は ADR を追加し、過去の結論を直接上書きしない。

## 凍結状態

Architecture 文書は凍結済み。

凍結後の原則:

- 通常の実装調整だけでは Architecture を変更しない。
- アーキテクチャ級の問題を発見した場合は、先に Review または ADR を作成する。
- アーキテクチャの進化が明確に必要と確認された場合にのみ、Architecture 文書を変更する。
