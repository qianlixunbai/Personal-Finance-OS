## Implementation and invariants confirmed

- `POST /api/v1/investment/transactions/{transactionId}/replacement` resolves the original fact's type and rejects unknown fields before calling the replacement command path.
- The transactional service locks the original fact, account, instrument, asset, and same-key correction command in a deterministic order. It validates the canonical request hash and immutable receipt before any duplicate-key recovery path is exposed.
- A successful replacement inserts the grouped reversal and replacement facts, applies exactly one combined account cash delta, calculates and persists the Asset projection from replay, inserts the correction command last, and runs the consistency checker before commit.
- The checker verifies grouped facts, receipt links, trace/digest, account balance, asset projection, reference values, and correction-command receipt fields. Checker-triggered failures roll back the whole transaction.
- PostgreSQL `55P03` lock-not-available and `40P01` deadlock errors are mapped to HTTP 409. Exact named-constraint handling distinguishes a same-key/same-hash receipt replay from a same-key/different-body conflict.
- A production race found by the price-update concurrency case is closed by locking the owned Asset before calculating its reference market value. The related unit test now mocks the same locked lookup; the behavior remains reference-price-only and does not rewrite transaction-driven projections.

## PostgreSQL concurrency and recovery evidence

All integration coverage uses Testcontainers `postgres:17-alpine`; observed servers reported PostgreSQL **17.10**. Concurrency tests use latches at a real replay boundary and verify PostgreSQL lock waits through `pg_stat_activity`; they do not use sleep-only race assertions. Each test reads final state through a fresh connection, verifies the replayed projection, and checks that no waiting locks remain.

- `InvestmentReplacementConcurrencyIntegrationTest` covers same key/same hash receipt replay; same key/different hash conflict; different keys on one original; races with reversal, buy, sell, dividend, reference-price update, account deactivation, instrument inactivation, and two originals sharing an asset. It also covers a candidate that becomes an oversell after the competing command.
- `InvestmentReplacementLockIntegrationTest` covers original-fact, account, instrument, asset, and existing-correction-command lock timeouts plus a real PostgreSQL deadlock. Each verifies HTTP 409 / SQLSTATE behavior, rollback, lock release, and a successful retry.
- `InvestmentReplacementUnknownCommitIntegrationTest` covers a committed transaction whose response is lost, a rolled-back transaction whose response is masked, and different-body behavior after uncertain completion. Committed retries return the old immutable receipt rather than current balances or asset state.
- `InvestmentReplacementFailureIntegrationTest` injects failures across replay, grouped-fact persistence, account mutation, second replay/trace/digest, projection, command persistence, database constraints, and consistency-checker tampering. Fresh-connection snapshots prove exact rollback and no waiting locks.
