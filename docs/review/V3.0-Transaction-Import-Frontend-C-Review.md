# V3.0 Transaction Import Frontend — Sub-phase C Review

**Status: CLOSED — GO**

This closes **Frontend Sub-phase C only**. It does not close the entire Transaction Import Frontend and does not authorize Sub-phase D.

## Scope and decision

Sub-phase C adds the final confirmation, durable pending-confirm recovery, authoritative receipt route, lossless receipt transport, and confirm-modal accessibility behavior for the transaction-import frontend.

The closing decision is **GO**. The final gate has `P0 = 0` and `P1 = 0`.

## Closing history retained

### NO-GO 1 — coverage was incomplete

The core implementation was initially not ready to close because the domain matrix, three 401 paths, logout, user switch, multi-tab behavior, and modal focus handling did not all have complete automated evidence. Closing was blocked until those gaps were covered by automated unit/component and browser tests.

### NO-GO 2 — fallback POST 401 recovery was unsafe

The fallback path previously degraded as follows:

```text
OUTCOME_UNKNOWN → extra Receipt GET
```

The final behavior is instead:

```text
POST unknown → Receipt GET 404 → fallback POST 401 → same-user auth → same fallback POST
```

The state is persisted as `RECOVERING_CONFIRM`; recovery resumes the exact frozen fallback POST, without an additional Receipt GET. Browser evidence asserts `GET → POST → POST`, one idempotency key, one path, and byte-identical `bodyJson`.

### Final closing correction — rejected initial Confirm could rehydrate a stale token

During this closing review, the new domain-error browser matrix found that clearing a rejected initial Confirm could allow the draft-restoration effect to restore the earlier confirmable snapshot. The final implementation clears that user's import draft and invalidates the in-memory preview token before removing the pending record. `IMPORT_SESSION_NOT_FOUND` returns to upload; terminal and re-preview actions remain non-confirmable. This prevents a rejected intent from being silently made confirmable again.

### Build and test closure

- Node 22 ESM test runtime required explicit `.ts` extensions for runtime value imports. The production source now works in Node ESM, Vite, and TypeScript without a test-only branch or duplicate implementation.
- `ImportConfirmDialog` cleanup uses an explicit `void` cleanup function. Event lifecycle and focus restoration are retained; focus-trap tests remain green.

## Engineering evidence

### Confirm and idempotency

```text
one user intent → one Idempotency-Key → one frozen bodyJson
```

The pending record is written before POST and contains only the owner, session/batch identifiers, key, confirm path, exact JSON body, timestamps, and recovery state. It does not persist files, preview rows, frozen plans, receipts, or balances. The double-click test issues one POST and asserts the generated key and exact serialized body. All recovery attempts reuse the same key, path, and exact body bytes.

### Unknown outcome and auth recovery

```text
POST unknown → Receipt GET
GET 200         → authoritative receipt
GET 404         → same frozen POST
```

The browser suite covers all three 401 paths:

| Path | Verified result |
| --- | --- |
| Initial Confirm POST 401 | Same-user login resumes the same POST; Receipt GET count is zero. |
| Unknown-outcome Receipt GET 401 | Same-user login resumes the same GET; Confirm POST count is zero. |
| Fallback POST 401 | `GET → POST → POST`; no second Receipt GET; both POSTs have the same key and exact body. |

### Domain error matrix

All 14 real Confirm/Receipt codes are triggered in browser automation, not merely listed in a table:

`IMPORT_CONFIRM_REQUEST_INVALID`, `IMPORT_SESSION_NOT_FOUND`, `IMPORT_PREVIEW_EXPIRED`, `IMPORT_SESSION_CANCELLED`, `IMPORT_PREVIEW_STALE`, `IMPORT_PREVIEW_UNAVAILABLE`, `IMPORT_DUPLICATE_EVIDENCE_CHANGED`, `IMPORT_WARNING_ACK_REQUIRED`, `IMPORT_EXACT_DUPLICATE`, `IMPORT_BATCH_ALREADY_CONFIRMED`, `IMPORT_IDEMPOTENCY_CONFLICT`, `IMPORT_LOCK_CONFLICT`, `IMPORT_CONFIRM_INCONSISTENT`, and `IMPORT_BATCH_NOT_FOUND`.

Each case asserts the actual state behavior, pending intent clearing or retention, and one Confirm POST with zero hidden Receipt GETs. Re-preview and terminal outcomes remove the unsafe draft/token; reconcile/conflict/unknown outcomes retain the original intent for explicit safe recovery. Responses with `retryable: true` still do not trigger a new key or an automatic unsafe resend.

### User boundary, logout, and multi-tab

- A user switch from User A (with unresolved pending Confirm) to User B never POSTs or GETs User A's intent, never displays User A's receipt, and does not restore User A's draft/token/warnings.
- Logout with an unresolved Confirm is deliberately blocked: it navigates back to transaction import and preserves the owner-bound pending record. It does not blindly clear or send the intent.
- A second tab receives the storage update, shows recovery instead of a competing confirmation, sees exactly one pending key, and does not produce another Confirm POST. Browser locking is a client-side guard; backend idempotency remains the correctness authority.

### Lossless transport and authoritative receipt

`lossless-json@4.3.1` is the only intentional new runtime dependency. Confirm and Receipt GET alone use raw response text before normal JSON number parsing. Receipt financial fields remain exact digit strings, including:

```text
9007199254740993.01
-0.01
9007199254740993.00
999999999999999999.999999
```

The independent `/transactions/import/receipts/:batchId` route reloads its authoritative receipt via GET. Account impact amounts are displayed as strings, `resultDigest` is displayed rather than recalculated, and transaction references are display-paginated only.

### Modal accessibility

Browser evidence covers `role="dialog"`, `aria-modal`, accessible title, focus entering the modal, Tab and Shift+Tab trapping, safe Escape close, focus restoration, and Escape/close being blocked while `CONFIRMING`.
