## PostgreSQL findings and implementation correction

Real PostgreSQL validation exposed two defects that the earlier Docker-unavailable run could not exercise:

- V13 built a temporary expected-V12 table with foreign keys to permanent `assets` and `accounts`; PostgreSQL rejects this because a temporary-table constraint may reference only temporary tables. V13 now validates the five cross-table V12 foreign keys directly from `pg_constraint`, including referenced table and ordered local/referenced columns, while retaining the existing fail-fast requirement.
- MyBatis did not have a handler for the PostgreSQL `UUID` correction-group parameter/result mapping. `PostgresUuidTypeHandler` is now explicit on `correction_group_id` so application-context migration verification uses the real PostgreSQL UUID value.

The fixture fixes use generated correction fact identifiers instead of sequence-sensitive literals, preserve the deferred foreign-key assertion, and update the two historical-upgrade tests whose "latest migration" assertion was still V12. No constraint, trigger, deferred relationship, or fail-fast behavior was relaxed.

The first final read-only review then found a P1 gap in the new catalog-based foreign-key verifier: it did not compare the target schema or FK action/match/deferrability/validation semantics. V13 now additionally requires `public` target schema, `NO ACTION` update/delete behavior, `MATCH SIMPLE`, non-deferrable/non-initially-deferred behavior, and validated constraints for all five V12 foreign keys. A PostgreSQL regression recreates `fk_investment_transactions_user_asset` with `ON DELETE CASCADE` and proves V13 refuses before any schema change.
