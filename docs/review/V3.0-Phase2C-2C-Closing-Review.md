## 3. 逻辑交易与 ID 边界

- 默认列表按冻结契约折叠物理事实，只返回逻辑业务事件：`UNCHANGED`、`REVERSED`、`REPLACED`。
- `logicalTransactionId` 始终是原始业务事实 ID；standalone reversal、grouped reversal 和 replacement fact ID 不成为公开逻辑 ID。
- 真实 PostgreSQL 用例分别把 standalone reversal、grouped reversal、replacement fact 的 physical ID 传给详情和 audit 端点，两者均返回安全 `404`。
- 不存在 ID 和其他用户的原始 ID 在详情与 audit 上同样为 `404`，不泄漏资源存在性。
- replacement 保留原始逻辑槽位和原始排序锚点；有效业务值来自 replacement fact，列表不会额外出现两条 correction facts。

## 4. 详情语义与三层快照

详情明确分离：

- `originalBusinessValues`：原始不可变业务事实；
- `effectiveBusinessValues`：仅 `REPLACED` 时存在，来自 replacement fact；
- `postingReceipt`：原交易入账完成时的不可变历史回执；
- `correctionFinalReceipt`：纠正命令完成时的命令快照，`UNCHANGED` 时不存在；
- `currentPosition`：请求时点直接读取受控 `Asset` 投影，不从历史事实重新聚合。

真实 PostgreSQL 断言证明这些层次可实际不同：

| 场景 | 原始/入账时数量 | 有效/纠正完成数量 | 请求时点 currentPosition | 其他断言 |
| --- | ---: | ---: | ---: | --- |
| UNCHANGED | `1.00000000` | 不适用 | `4.00000000` | current total cost `50.00` |
| REVERSED | `1.00000000` | `0.00000000` | `2.00000000` | 原始 net amount `10.00` |
| REPLACED | `1.00000000` | `3.00000000` | `7.00000000` | effective net amount `34.00`，current total cost `70.00` |

因此 posting receipt、correction final receipt 与 currentPosition 是三个不同的语义层，而不是同一值的别名。

## 5. Audit timeline

- `UNCHANGED`：只有 `ORIGINAL_POSTING`，回执适用性为 `POSTING_TIME`。
- standalone reversal：`ORIGINAL_POSTING` 后跟 `STANDALONE_REVERSAL`，后者关联原始 physical fact，回执适用性为 `CORRECTION_FINAL`。
- replacement：`ORIGINAL_POSTING` 后跟一个 `REPLACEMENT_COMMAND`；命令内 physical facts 固定为 `GROUPED_REVERSAL`、`REPLACEMENT_FACT`。
- grouped reversal 的 receipt applicability 为 `NOT_APPLICABLE`，不伪造不存在的独立最终回执。
- 事件按 `createdAt` 及稳定角色顺序排列；同一时间戳下仍保持 original 在 command 前、grouped reversal 在 replacement fact 前。
- 响应允许审计所需的 physical fact ID，但不暴露 correction group ID、request hash、idempotency key、digest、trace、投影内部字段或数据库约束信息。

## 6. 所有权、关系完整性与一致性

- 所有公开查询在 SQL 层同时约束 `user_id`，Account、Instrument、Asset 与 transaction/correction 关系也按同一用户连接。
- V12 已提供 reversal 到 original 的外键、每个 original 的 standalone reversal 唯一性和 append-only 保护。
- V13 已提供 fact-to-command、command-to-fact 的 deferred 外键，以及两侧 deferred completeness trigger；测试证明不完整 replacement group 在提交时失败，不能进入读取模型。
- 详情与 audit 的公开 Service 方法均经 Spring 代理进入 `@Transactional(readOnly = true, isolation = REPEATABLE_READ)`。
- 并发 PostgreSQL 用例在读取原始事实后提交另一个连接对 `Asset` 的更新；拦截到的第二次 Mapper 查询确认事务已激活、只读且为 REPEATABLE READ，详情和 timeline 均保持同一请求快照。

## 7. 读取副作用与查询规模

- 100 条逻辑交易列表只调用一次 folded list Mapper 查询，没有逐行详情或 relation 查询。
- replacement timeline 使用固定 5 次关系读取：original、current position、standalone reversal lookup、correction command、replacement facts；查询次数不随列表长度增长。
- 生产读取路径未依赖行情/FX Provider 或刷新服务。
- SQL 与依赖复核未发现 `INSERT`、`UPDATE`、`DELETE`、`FOR UPDATE` 或显式写锁；PostgreSQL 测试还比较读取前后 Asset 行版本与账户余额，确认普通 GET 不写状态。
- 未引入持久化 read model，也未产生第二套 Position 真值。

## 8. HTTP 与 OpenAPI

- 三个 transaction/audit 路径均受 Bearer JWT 保护；未认证为 `401`。
- 查询参数、日期时间、page size 与正整数 path ID 的非法输入覆盖 `400`。
- 不存在、跨用户和 physical correction ID 覆盖安全 `404`。
- 三个端点的非预期异常均映射为脱敏 `500`，不返回内部 secret。
- 运行时 OpenAPI 覆盖六个 Phase 2C 公开读取端点、参数、枚举、分页边界和 `200/400/401/404/500` 响应。
- detail/audit 顶层及嵌套 Account、Instrument、BusinessValues、Receipt、CurrentPosition、AuditEvent、PhysicalFact schema 引用非空且按语义分离；测试显式检查嵌套 schema 不暴露内部字段，防止嵌套 record 名称碰撞或错误复用。
