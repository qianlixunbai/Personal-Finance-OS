## 1. 阶段目标

本阶段为投资事实、持仓重建、成本计算和后续一致性校验建立独立基础，同时保持现有 Asset、Account、普通 Transaction、Dashboard 与 v2.1 Reference Valuation 的行为不变。Phase 1 只完成领域、计算和持久化基础，不开放真实用户写入链路。

## 2. 实际完成范围

- `InvestmentTransaction` 表达投资事实，`Asset` 作为当前持仓受控投影，`Account.balance` 仍是现金余额投影。
- 第一版交易类型为 `BUY`、`SELL`、`DIVIDEND`、`OPENING_POSITION`；这些类型已具备领域、数据库和计算基础，但尚未开放真实用户写入。
- 完成 BigDecimal 计算内核、内存 replay、InvestmentTransaction Entity / Mapper、用户范围查询、Asset 有效交易顺序查询和幂等键查询。
- 完成 V4 Investment Ledger Foundation 与 V5 Investment Ledger Constraint Hardening，并通过 PostgreSQL Testcontainers 验证 Flyway V1→V5、V4→V5 路径。

## 3. 关键领域决策

- 投资事实独立于普通 `Transaction`，不新增与 `Asset` 重复的持仓真值表。
- Market Quote、FX 和 Reference Valuation 只是外部或只读参考输入，不修改投资事实、成本或现金余额。
- 事实不物理删除；`REVERSED` 由 replay 跳过，replacement 只记录关联关系。
- 第一版保持 CNY-only；加权平均成本用于产品内持仓成本与收益展示，不作为跨国税务申报结论。

## 4. BigDecimal 与成本计算规则

- 数量、单价和平均成本使用 `BigDecimal`，数量与平均成本最终 scale 为 8；现金金额、成本和已实现盈亏最终 scale 为 2。
- 所有除法显式使用 `HALF_UP`；输入 scale 超限、低名义金额和会留下正数量零成本的非法结果必须拒绝。
- BUY 将 `gross + fee + tax` 计入成本；SELL 按比例释放成本，全部卖出时释放全部剩余成本；`realizedProfitLoss = net - releasedCost`。
- DIVIDEND 不改变数量、总成本或平均成本；OPENING_POSITION 不产生现金 delta，并且只能用于受控迁移或内部流程。

## 5. V4 数据模型与 V5 加固

V4 新增 `investment_transactions`，保存交易类型、状态、数量、单价、金额、时间、来源、幂等键、request hash、冲正与 replacement 关联及审计时间。Asset 通过 additive 字段兼容投资投影，旧 Asset 保持 `LEGACY` 模式，不自动生成 Opening Position。

V5 保持 V1-V4 不变，并增加：

- 各交易类型的金额恒等式 CHECK；
- `(user_id, asset_id, id)` 幂等唯一键；
- Asset / Account 的组合用户外键；
- replacement 同用户、同 Asset 的组合外键；
- replacement 禁止自引用；
- 既有矛盾事实升级时 fail-fast，不静默修改投资事实。

## 8. 已验证不变量

- replay 按 `tradeTime ASC, id ASC`，跳过 `REVERSED`；
- 中途超卖整体失败；
- Opening 只能是第一个非 REVERSED 事实且最多一次；
- 全部卖出后可以再次 BUY，但不能再次 Opening；
- 有效事实可以重建持仓；
- `quantity > 0` 必须对应 `totalCost > 0`；
- V4 合法数据可安全升级，V4 矛盾数据升级时 fail-fast；
- replacement 不得跨用户、跨 Asset 或自引用。

## 9. 已知限制

以下为独立复验确认的 P2 或既有技术债，不构成 P0/P1，也不阻塞 Phase 1 关闭：

1. Opening 输入 quantity 不足 8 位 scale 时，Calculator 的 `newQuantity` 暂时保留输入 scale；进入 `InvestmentPositionState` 后会规范化为 scale 8。后续规范化 Opening 输出并增加实际 scale 断言。
2. 永久数据库测试尚未覆盖全部非法交易组合；PostgreSQL 聚焦复验已验证约束有效，属于测试覆盖缺口。
3. 缺少完整的 V4 合法/非法 replacement 升级永久回归测试；聚焦复验已确认合法关系保持不变、非法关系 fail-fast，且不会留下半完成 V5。
4. V5 fail-fast 异常信息未输出具体 transaction id，排障能力有限。
5. `InvestmentReplayEntry` 使用 `LocalDateTime`，事实 Entity 和 PostgreSQL 使用 `Instant` / `TIMESTAMPTZ`；`BaseMapper` 仍暴露裸 `selectById` / `selectList`；Phase 2 需要建立明确的 Service / Repository 用户隔离边界。

## 10. 最终边界

Phase 1 关闭不代表整个 v3.0 完成。当前仍未实现：公开 InvestmentTransaction API、投资交易 Controller、真实 BUY / SELL / DIVIDEND 写入、`Account.balance` 联动、`AccountBalanceService`、`SELECT FOR UPDATE`、真实幂等写入 Service、Opening Position 实际迁移、自动创建 Brokerage Account、普通用户 Opening 入口、投资交易前端、Dashboard 改动、FIFO、税务申报模型、公司行动、多币种现金账户，以及普通 Transaction 行为变更。

## 11. 下一阶段

Roadmap 当前阶段为 **v3.0 Phase 2A — Account Balance Concurrency Foundation**，尚未开始实施。Phase 2A 目标是统一 `AccountBalanceService`、使用 PostgreSQL `SELECT FOR UPDATE`、让普通 Transaction 使用统一余额更新路径、避免并发收入/支出丢失更新、固定账户锁顺序并保证事务失败全部回滚。

Phase 2A 暂不接入 InvestmentTransaction，不做 Opening Position 迁移，不实现 BUY / SELL，不新增前端。Phase 2B 再处理 Opening Position Migration、Legacy Asset Preflight、Projection Rebuild 和 Consistency Check。
