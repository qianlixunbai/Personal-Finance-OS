# v3.0 Phase 2B-1 Closing Review — Investment Projection Safety and Precision

## Scope

This phase aligns the controlled Asset projection with the existing investment ledger without adding any investment write API, Opening Position migration, Account.balance coupling, Portfolio UI, or historical snapshots.

## Acceptance evidence

| Requirement | Result | Evidence |
| --- | --- | --- |
| Fresh database migration | PASS | PostgreSQL 17 Testcontainers applies V1 through V6. |
| V5 upgrade migration | PASS | A V5 schema upgrades to V6 while retaining the existing LEGACY Asset row. |
| quantity precision | PASS | `assets.quantity` is `NUMERIC(28,8)` and retains an eight-decimal boundary value. |
| avgCost precision | PASS | `assets.avg_cost` is `NUMERIC(28,8)` and retains an eight-decimal boundary value. |
| Money precision | PASS | Ledger fact amount columns remain `NUMERIC(28,2)`; no formulas or money scales changed. |

| Transaction-driven delete protection | PASS | Asset delete returns business conflict `409` before physical deletion. |
| Reference price boundary | PASS | Transaction-driven assets may still update reference price without changing controlled projection fields. |
| Replay time | PASS | Replay boundary is `Instant`; persistence is already `TIMESTAMPTZ`. |

| User scope | PASS | Mapper queries include `user_id`; PostgreSQL integration tests prove cross-user rows are not returned. |

## Scope confirmation

Not implemented in this phase: `investment_instruments`, Instrument-to-Position binding, Legacy Asset Opening Migration, InvestmentTransaction write/reversal APIs, idempotency write workflow, Account.balance coupling, Portfolio API/UI, Dashboard changes, `sites-demo` changes, historical prices, snapshots, multi-currency accounting, FIFO/LIFO, Redis, MQ, microservices, or AI.

## Known limitations

- Transaction-driven projection writes remain intentionally deferred to a future investment command and replay path; this phase only blocks the existing Asset API from overriding or deleting those projections.
- `trade_time` is the existing schema name for the replay timestamp; it remains a PostgreSQL `TIMESTAMPTZ` value ordered with `id` as the deterministic secondary key.

GO. No P0 or P1 issues remain for the defined Phase 2B-1 scope.
