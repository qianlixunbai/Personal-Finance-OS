# v1.0 Closing Review

本文档用于记录 Personal Finance OS v1.0 阶段收尾 Review 结论，作为当前阶段的“阶段验收单”。

## 1. Review 背景

截至本次 Review，项目已经完成 v1.0 作品集展示所需的主要闭环：

- 根目录 `README.md` 已作为 GitHub 作品集入口；
- `Architecture.md` 已 Review 并冻结；
- `Database.md`、`API.md` 已完成并持续同步实现状态；
- 默认系统分类启动初始化已完成；
- 后端统一异常响应闭环已完成；
- Spring Security `401` / `403` 统一响应已完成；
- Transaction / Ledger 后端 API 与前端页面已完成；
- Dashboard 最近流水展示增强已完成；
- Accounts / Assets 前端主列表分页已接入；
- `docs/README.md` 已改为文档导航页。

本次 Review 不引入新功能，不修改架构，只记录当前阶段状态、剩余问题分级和下一阶段建议。

## 2. Review 范围

- 后端模块结构与核心业务闭环；

3. 用户登录；
4. 创建账户；

## 9. 面试风险点与建议回答方向

### 9.1 为什么使用模块化单体，而不是微服务？

当前项目处于 v1.0 阶段，业务规模和团队规模不需要微服务。模块化单体可以保留清晰边界，同时降低部署、调试和数据一致性复杂度。后续如出现独立扩展需求，再评估拆分。

### 9.2 JWT 安全如何处理？

当前使用 JWT 做登录态，前端保存 token 并通过请求拦截器注入。后端会校验 token，并确认用户仍为 `ACTIVE`。当前尚未实现 refresh token、token 黑名单等增强能力，属于后续安全增强方向。

### 9.3 账户余额并发一致性如何保证？

当前通过事务保证单次流水写入和账户余额更新同提交同回滚。但并发下仍存在 lost update 风险，后续需要评估行锁、乐观锁或原子 SQL。这一点已作为 Known Gap 记录。

### 9.4 为什么流水删除是物理删除？

v1 当前为了保持实现简单，删除流水会回滚账户余额并物理删除。金融系统更完整的做法应是软删除、冲销或审计日志，这已放入后续版本方向。

### 9.5 为什么资产还不是完整投资交易模型？

当前资产模块定位为持仓快照管理，记录数量、成本、价格和盈亏。买入、卖出、股息、手续费、税费等属于更复杂的投资交易模型，当前不冒充已实现。

### 9.6 为什么 schema.sql 不是 Flyway？

当前处于开发和作品集阶段，使用 `schema.sql` 便于快速初始化 Fresh DB。正式部署或多人协作演进时，应迁移到 Flyway / Liquibase。

### 9.7 AI 模块为什么未实现？

AI 属于未来增强能力。当前优先保证金融数据、账户余额和流水规则的确定性。AI 只能分析和建议，不应修改核心金融数据。
