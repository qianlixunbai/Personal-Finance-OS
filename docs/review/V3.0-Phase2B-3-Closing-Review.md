# v3.0 Phase 2B-3 Closing Review

## Scope

Phase 2B-3 introduces explicit, single-Asset Legacy preflight, preview, and confirmed opening-position migration. V9 adds fail-fast upgrade checks, the Account/Asset composite foreign key, and the posted-opening partial unique index.

## Verified boundaries

- `totalCost` remains authoritative; calculator reconstruction is exact.
- Preview signs source version and request hash without writing data.
- Confirm uses Account -> Instrument -> Asset locks, replay rebuild, idempotency recovery, and a balance-invariance consistency check.
- `Account.balance` is not mutated; no public BUY, SELL, DIVIDEND, Portfolio, batch migration, or frontend workflow is added.

## Known limitations

Phase 2B-4 remains out of scope. Legacy zero holdings require a later archive/correction flow rather than an opening transaction.

## Verification Closure history

1. The initial functional implementation was complete, but the dedicated fault-injection and two-thread concurrency evidence was insufficient.
2. The first closing assessment was therefore **NO-GO**.
3. Follow-up rounds added focused rollback, web-sanitization, and concurrent-operation coverage.
4. Those rounds exposed and fixed two production defects:
   - a concurrent request with the same idempotency key could wait for the lock and then be incorrectly rejected as a stale preview;
   - `updatedAt` participated in `sourceVersion`, so a reference-price-only update could incorrectly block migration.
5. The final focused tests cover temporary-binding, opening-insert, projection-write, and Consistency Checker rollback; Web 500 sanitization; lock timeout and release; same-key/different-hash and different-key/same-Asset behavior; and migration races with close, delete, updatePrice, Account deactivation, and Instrument deactivation.
6. `LegacyOpeningMigrationConcurrencyIntegrationTest` passes **12/12** using real threads, `CyclicBarrier`, and bounded `Future.get`; it does not use `Thread.sleep` to define ordering.
7. The Consistency Checker failure path rolls back and returns a sanitized HTTP 500 response.
8. A PostgreSQL Account row-lock timeout returns sanitized HTTP 409, while releasing the lock before its timeout allows migration to succeed.
9. The competing close, delete, price-update, Account-deactivate, and Instrument-deactivate operations leave no partial migration state.
10. `sourceVersion` includes material migration inputs (asset/user identity, quantity, cost fields, currency/type, account/instrument binding, position mode/status, and projection version) and excludes reference-only `currentPrice`, `marketValue`, and generic `updatedAt`; material changes return 409 with no opening or partial binding, while reference-only changes can confirm.
11. The final full command, `backend\\mvnw.cmd clean test`, ran against real PostgreSQL 17 Testcontainers and completed with 73 test classes / 318 tests, 0 failures, 0 errors, and 0 skipped.
12. P0 and P1 findings are zero.
13. The final conclusion is **GO**.
