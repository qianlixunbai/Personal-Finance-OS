## 冻结计划与金融权威

Confirm 只执行服务端冻结的 `PreviewPlan`。客户端不重新提交金融 rows 作为事实，不计算账户影响，也不决定余额。

`Transactions`、`Account.balance`、Batch、Items、Account Impacts 与 Session `CONSUMED` 位于同一 PostgreSQL transaction；任一步失败即整体 rollback。真实 PostgreSQL fault injection 已分别覆盖 Transaction、balance、Batch、Item、Account Impact 和 Session consume 六类写入点。

`AccountBalanceService` 仍是 production balance mutation 的权威路径。Import Confirm 没有形成第二套账户余额算法；Confirm 与手工 `Transaction` 并发已验证，最终余额与已提交的 transaction facts 一致。manual `TransactionService` 尚未完全复用 shared write rules 属于 P2 代码复用问题，不影响本阶段金融语义与锁定验证。

## 锁定、原子性与幂等

锁顺序固定为：

```text
Session FOR UPDATE
→ Account ID ascending
```

真实 PostgreSQL 验证覆盖 deterministic Confirm-vs-Confirm、Confirm-vs-Cancel、Confirm-vs-cleanup、Confirm-vs-manual Transaction、opposite Account ordering 以及 lock timeout。deterministic Confirm-vs-Confirm 通过 `pg_stat_activity` 确认第二请求确实等待 Session row lock；第一请求提交后，第二请求在锁内走 committed replay。

- same key + same intent 返回同一 authoritative receipt；
- same key + different intent 返回 conflict；
- 同一 `Idempotency-Key` 跨用户隔离；
- rollback 不留下假 committed binding；
- committed replay 不重复金融写入。

unknown commit 的真实路径为：DB COMMIT 成功后 result delivery 失败，客户端结果未知；相同请求重试后按 committed Batch lookup 重建同一 authoritative receipt。验证结果为同一 Batch、同一 `resultDigest`、Transaction delta = 0、balance delta = 0。

receipt 是后端权威事实，从 committed persistence 重建，不依赖第一次 HTTP response 的内存对象；temporary `PreviewPlan` cleanup 后仍可 replay，`resultDigest` 可稳定重建。

## Named Constraint Recovery Contract Amendment

Implementation 过程中发现原 Named Constraint Recovery Gate 与正确的 Session serialization 模型存在冲突，因此经独立 Contract Amendment Review 后修订。

原理解要求正常同 Session 并发触发 named unique constraint 后 recovery；但同一 Session 的 Confirm 应先被 `Session FOR UPDATE` 串行，后到请求在锁内完成 committed lookup 并进入 replay/conflict resolution。故 Named Constraint Recovery 的最终定位为 defense-in-depth fallback，而不是正常同 Session 幂等的核心机制。

正常 exactly-once 由以下组合保证：

```text
Session FOR UPDATE
+ locked committed lookup
+ preallocated Batch identity
+ single DB transaction
+ DB constraints
```

fallback 只识别明确命名且与当前 import 语义匹配的预期 constraint；successful replay 必须通过 authoritative committed persistence lookup，并完整匹配 user、Session、preallocated Batch、key 与 `requestHash`。没有可信 committed result 时 fail closed；exact duplicate 不得伪装为 successful replay；unrelated unique、FK、check 与 unknown named constraint 均不得 successful replay。正向 fallback、exact-duplicate authoritative check 与上述 negative matrix 均已验证。

完整 Amendment 历史保留于 [Phase 3D Transaction Import Confirm Contract](../design/V3.0-Phase3D-Transaction-Import-Confirm-Contract.md)，未删除、回滚或改写为旧 Gate。

## Preview、重复语义与用户隔离

Preview token 为 signed / opaque token。tampered token、cross-session token、stale token、foreign-user token 与 digest mismatch 均 fail closed；committed replay 不依赖 temporary `PreviewPlan`。

重复语义覆盖 probable duplicate warning、稳定 warning identity、acknowledgement、candidate added、candidate removed、unrelated transaction、exact duplicate，以及 forged / stale / foreign warning。evidence drift 必须重新 Preview，不能静默继续 Confirm。

已验证的用户域隔离至少包括 foreign Session、foreign Batch receipt、foreign Account、foreign Category、foreign preview token、foreign warning ID，以及跨用户相同 `Idempotency-Key`。
