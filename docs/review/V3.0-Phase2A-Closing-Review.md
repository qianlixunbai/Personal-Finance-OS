- `updateThenDelete_reversesLatestUpdatedEffect` starts from balance 100 and an EXPENSE 20 fact. An outer `TransactionTemplate` updates the fact to EXPENSE 50, stops before commit with a `CountDownLatch`, and a second executor deletes it. PostgreSQL confirms the second transaction is waiting before the update is released. Both bounded futures complete; the fact is absent and balance is 100, proving the delete reversed the committed 50 rather than the stale 20.
- `deleteThenUpdate_returnsNotFoundWithoutSecondReversal` uses the inverse controlled ordering. The outer transaction deletes the EXPENSE 20 fact and pauses before commit; the update waits on the real PostgreSQL lock. After release, delete succeeds, update returns the existing 404 semantics, the fact remains absent, and balance is 100 with one reversal only.
- `createRollsBackTransactionWhenBalanceUpdateFails`, `updateRollsBackFactWhenBalanceMutationFails`, and `deleteRollsBackFactWhenBalanceReversalFails` install a uniquely named PostgreSQL `BEFORE UPDATE OF balance` trigger only for the test account. The trigger is dropped in `finally` and checked absent from `pg_trigger`. The database exception rolls back, respectively: a new fact and its delta (no fact, balance 100); an EXPENSE 20 to EXPENSE 50 update (fact remains 20, balance 80); and a delete reversal (fact remains, balance 80).
- `lockTimeout_returnsHttp409WithoutPartialCommit` holds an Account row in an independent JDBC transaction, then submits a MockMvc transaction-create request. - `lockReleasedBeforeTimeout_allowsRequestToSucceed` uses the same independent held row lock and confirms the HTTP request is in PostgreSQL lock wait via `pg_stat_activity`. Releasing the lock before 750ms lets the request return 200; one fact exists and balance is 20.

## Known risks

There is no idempotency key, so automatic retries remain prohibited. PostgreSQL concurrency semantics require continued real-database coverage.
